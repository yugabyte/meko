# AGENTS.md: the server

The modules under `src/server/`: the server, the session host (`host/`) and the CLI. AgentK's
guide, with the invariants every change here keeps, is [../../AGENTS.md](../../AGENTS.md).

## Map

| Path | What it is |
|---|---|
| `src/server/cli.ts` | Entry point: `serve` (which first lets a move of the home under way finish, or does one itself without services: `moveFirst`), `stop`, `start`, `restart` (the server's service only, which Meko runs after an update: `restartServer` in `health.ts`), `host` (`host stop`, `host restart`), `attach`, `install`, `uninstall`, `status`, `ui` (through Meko), `logs`, `selftest`, `version` (`--json`, which Meko checks a release with), the hidden `_move-home` the move's job runs and `_handoff` Meko runs (`handoff.ts`), `setup-link` (now only a message: Meko signs people in), and `mcp` (unlisted: the session tools' MCP server, which sessions start as `mcpmain.js`). Run by `meko start` and `meko stop` (`MEKO_SUMMARY=1`), `start` and `stop` print one row of Meko's summary. |
| `src/server/summary.ts` | That row: Meko's format (`  ✓ AgentK          started`), colored only on a terminal without `NO_COLOR` (Meko's `docs/install.md`, "The summary rows"), and what the stop row says (`stopRowText`: where the sessions resume, `meko start`, or `agentk serve` without services). |
| `src/server/core.ts` | Wires config, db, the session host, Meko and the services (refusing to start while a tmux-era version's service is installed, unless the host service is too and none of this home's sessions is in tmux); timers; `state()` snapshot for the UI. |
| `src/server/server.ts` | Fastify routes, origin checks (no login: Meko signs people in), WebSockets (`/ws/events`, `/ws/term/:id`), static files, and the page stamped with its `<base href>` (`/ext/agentk/`) and version (`stampPage`). The server listens only on `Paths.webSock` (`cli.ts`, with `listenPrivate` from `hooks.ts`). |
| `src/server/sessions.ts` | Session lifecycle in the session host: create (`begin` answers once the row is in; the worktree and launch follow, and a worktree that can't be made is a failed start; a task on an existing branch or an open PR, a fork's included, works on that branch as it is; a learn session, `CreateSessionRequest.learn`, is a task at Explore marked `purpose = 'learn'` on the `seed` prompt), launch (through the session's harness adapter, `src/server/harness/`; hook payloads normalized by it), hook-driven status (a turn's end: `Stop`, or one the mod reports interrupted, `endTurn`), submitting prompts (through AgentK's mod while it's live, else typed into the terminal), recovery and auto-continue, archive. |
| `src/server/lifecycle.ts` | Stages and gates, moves by hand between stages, the user's instructions sent with a move or Open PR (`checkInstructions`), GitHub polling, the review watchers (by reviewer mode: straight to Claude, or held for the user, and the user's send or dismiss, `decideHeldReviews`), the merge-conflict watcher (`[pr] resolve_conflicts`, also in Settings → General) and CI-fix watcher with their prompt queue, queued gates (Open PR after this turn, with its instructions, Merge when ready: `sessions.queued_gate`, `queued_instructions`), Run to merge (`sessions.auto_run`: `setAutoRun`, Open PR queued at each Code turn's start, `onTurnStart`, and a merge that stays queued through any blocker, `armMerge`, `autoRunWaits`, stopped by an uncheck, a Cancel, an interrupt or a move, `stopAutoRun`), Merge & Close (merge, then cleanup), closing a learn session once Claude wrote its summary (`learnDone`), and a Review a PR session's watch on its PR (new commits, merged or closed) and Update to latest. |
| `src/server/heldreviews.ts` | Reviews held for the user (`held_reviews`): where a review goes in each reviewer mode (`reviewRoute`, the one place that decides), keeping a held review with its inline comments, the list and count the UI shows, marking reviews sent or dismissed, the merge blocker while any are held, and the `review-held` prompt's lines. Polling and sending are in `lifecycle.ts`; the details come from `github.reviewDetails`. |
| `src/server/prreview.ts` | Review a PR and sharing with reviewers: the PRs a review can start on (found on GitHub by the project's datapack ids, in any repo, each matched to a local clone, a fork first), cloning a PR's repo, and who reviews the project's open PRs (with emails remembered per GitHub login). A review's create path (fetching `refs/pull/<n>/head`, a review branch with no upstream) is in `sessions.ts`, its git helpers in `git.ts`. |
| `src/server/ghlinks.ts` | Starting from a GitHub PR or issue pasted into Ask AgentK (`GET /api/github-link`, `POST /api/github-link/start`): reading it (`issueOrPr()` in `github.ts`, one call for both), the project it belongs to (a datapack its description's Meko line names, else the one on screen if it's on its repo, else the first on it; the repo's other projects are offered too) or the one to open (its datapack: the named one, reopening a closed project with it, else none for a PR and a new one for an issue), the clone to work in, and the session (a review, or a task from the issue's prompt). The palette's side is `linkEntries()` in `src/web/palette.ts`; the ref parser is `src/shared/github-refs.ts`. |
| `src/server/askagentk.ts` | Ask AgentK (`POST /api/ask-agentk`): an instruction in plain words from the command palette, answered by one call to the default agent with no tools, MCP servers or hooks, as its adapter's `Asker` says (`claudeAsker`: `claude -p`, `askArgs()`; `kiroAsker`: `kiroAskArgs()`, the `agentk-ask` workspace agent and `readKiroAnswer()`; `openCodeAsker`: `openCodeAskArgs()`, the `agentk-ask` agent in a global config of the ask's own in place of the user's, `XDG_CONFIG_HOME`, so their plugins and MCP servers don't run, and `readOpenCodeAnswer()`; an ask's Kiro or OpenCode session is deleted whether or not it answered), the message (projects, running sessions, what's on screen, the exchange so far) on stdin; reading its JSON answer and errors (`readAnswer()`), checking the proposed actions against the state (`checkActions()` in `actions.ts`) and whether they're the steps of one instruction (`together`, for Do all), each project's GitHub repo in the message (`withGithub`), two asks at a time, and counting asks for the usage report (`agentk_asks`). The palette's side is `askEntries()` in `src/web/palette.ts` and `CommandPalette.tsx`, which runs the picked action through the routes the UI already uses. |
| `src/server/actions.ts` | The actions Ask AgentK proposes and AgentK's session tools take (`start`, `link`, `go`, `move`, `openPr`, `openProject`): checking them against the state (`checkActions()`, at most `ACTIONS_MAX`), running them in order through the core calls the UI's routes make (`runActions()`: Do all's `POST /api/actions/run` and the tools; a `tools` event on the calling session and the one it changed), opening a project for one, and the session tools' side of a call (`SessionTools.call`, the hook socket's `/tools`: refused while `[tools] enabled` is off or from a PR head `repoConfigTrusted()` doesn't trust; no Open PR on the caller; the caller's own move held for its turn's end, `turnEnded`; calls still running answered when the hook socket closes, `pause`). See [docs/design/tools.md](../../docs/design/tools.md). |
| `src/server/tools.ts`, `tooldefs.ts` | The session tools' files each harness launches with (`writeToolFiles` into `run/tools/`: Claude Code's `--mcp-config` file and the hook-less skill plugin, the skill's copy Kiro and OpenCode read; `toolsReady`), how a session's CLI starts the MCP server (`toolsCommand`: `app/current`'s Node on `mcpmain.js`, or a dev server's Node with its loader flags), Kiro's `mcpServers` entry and OpenCode's part of a session's config (`openCodeTools`); and in `tooldefs.ts` (no imports, so the MCP server loads nothing else) the tools' names, descriptions and input schemas, and the read-only ones each harness allows. |
| `src/server/mcp.ts`, `mcpmain.ts` | `agentk mcp`: the session tools as a stdio MCP server, MCP's few messages spoken directly (no SDK: its schemas cost about 30 MB per session), each call forwarded to the hook socket's `/tools` with `AK_HOOK_SOCK` and `AK_HOOK_TOKEN` from the session's environment. `mcpmain.ts` is the entry sessions start, without the CLI's imports. |
| `src/server/workqueue.ts`, `slack.ts` | The work queue (`work_items`, `work_item_links`; [docs/design/work-queue.md](../../docs/design/work-queue.md)): items, their links by `parseWorkLink` key (`src/shared/worklinks.ts`), order, one session per item (`setItemSession`, the only writer; `checkStartItem` for `CreateSessionRequest.workItemId`, linked in `begin()`'s transaction; `soleItemFor` for a session started from a pasted link in `ghlinks.ts`), Dismiss all (`closeAll`), the palette's lookup by link (`byLink`), and the sync (Sync, and `tick()` every minute against `[work_queue] sync_minutes`; each source only while `[work_queue] github` or `slack` is on, both off by default, Settings › Work queue): GitHub review requests (`reviewRequests()` in `github.ts`, Done on GitHub when gone) and Slack's To-dos (`slack.ts`: one `claude -p` with the user's own connectors but none of their settings beyond sign-in (`signInSettings`), no built-in tools but ToolSearch (which waits for the connector), the default permission mode, only `[work_queue] slack_tools` allowed and Slack's writes denied, read on the timer only while the last read worked, `work-slack-auto`), each source on its own, never re-adding a link any item has. |
| `src/server/sessionsearch.ts` | Finding a session by what it's about (`GET /api/sessions/search`): the words of the text, each session's name, PR, task, branch and design read from `state.db` (archived sessions included), and the ranking (`rankSessions()`). The palette's side is `findEntries()` in `src/web/palette.ts`. |
| `src/server/prdesign.ts` | A reviewed PR's design: fetched from Meko by the hash on the PR's `meko_design:` line (checked against it), and kept as the review session's design (a `designs` row marked with its `source`, never sent to Meko, and the file Claude reads). Fetched while the review starts, and again by the review's PR poll when the line's hash changes. |
| `src/server/projects.ts` | Projects (a closed one opens again when its dedicated datapack is picked; `open()` adds whether its dedicated datapack is empty, for the learn session offer), repo scan, datapacks (create with the repo remote in the description, attach, pin; an invite is accepted in Meko before its project is opened), project home and search, and What Meko doesn't know's routes (`mekoGaps`, `markMekoGap`, and `teachMeko`, which saves the user's answer to the dedicated datapack). |
| `src/server/prompts.ts` | Instructions sent to Claude at each stage (overridable per repo in `.agent-k/stages/`), the Meko recall lines added to them in code, the system prompt's saving rule (`mekoSaveSystemLine`), a learn session's `seed` prompt, task (`learnTask`) and saving rule (`SEED_RULE`), Run to merge's line on the coding prompts (`autoRunLine`, `AUTO_RUN_PROMPTS`), and the design lines added in code (the questions and AgentK's own decisions asked for in Design, naming the `design_questions` tool only to an agent with the mod; the "Key Design Decisions" section into the design at the approval, keeping it current after, and where a review's PR design is). |
| `src/server/review/` | The [local code review](../../docs/design/code-review.md) before a task's PR opens, ported from agent-k's `pkg/agenticreview`: `types.ts` (passes, findings, candidates, the diff), `strategies.ts` (Sagittarius 3.0's five mandates word for word, Sirius 1.0's one), `schemas.ts` (each report's JSON schema and the checks the review tools run: `checkReport`, with the dependents and claims ledgers, `checkScore`, `checkOutcomes`), `diff.ts` (the change from the merge-base to the working tree, untracked files included, with secret, deleted and generated files withheld, and per-file patches past 256 KiB), `history.ts` and `guides.ts` (the history of the rewritten lines; REVIEW.md and MEKO.md files that apply), `prompt.ts` (the base prompt, sweep context, prior rounds, the Meko datapacks section, pass and scorer prompts), `merge.ts` (`mergeSweep`, the refutation gate, `keepScored`, `validate`, counts), and `runner.ts` (`CodeReviews`, `Core.reviews`: one review per Open PR, or per move to Review & PR with work to push (`applies`, `Lifecycle.reviewBeforePr`), its code-review session, the steps' reports from the `review_*` tools, sweeps, scoring, re-review rounds, the PR prompt with the `me_ak_review:` line, Retry, Open anyway, cancel and recovery). |
| `src/server/learn.ts` | The learn step (and where a running one is, `progress()`, for `Session.learnProgress`): what a session learned about the product and repo, saved to its project's dedicated datapack at Merge & Close (before cleanup), at Discard (which waits for it: `sessions.discarding`), both unless the user checked **Don't save learnings** (`CloseSessionRequest.skipLearn`), and when asked (the `learn` action, `/agentk_learn`). Through the mod: the fork's facts (and which of the project's open questions on What Meko doesn't know each answers, the session's own first, `learnGaps`), the saved memories most like each, the small model's add/skip/update decisions, the writes, and marking those questions taught, or dismissed when Meko already had the answer; else a typed `learn` prompt (no questions). Records `meko_learns` and the model calls' usage. |
| `src/server/learnscope.ts` | A learn session's estimate for the New session dialog (`learnScope`, `GET /api/projects/:id/learn-scope`): the merged PRs in its window (first-parent commits since `learnSince()`) and the tracked files on `origin/<base>` or the local base, from local git only, in the paths its free-text Where names (`whereWords`, `wherePaths`, `globRegex`), else the whole repo. |
| `src/server/recall.ts` | Meko recall at session start: the search on a new session's task (and the issues it names), picking and formatting what it found (each item with its Meko id, for a design to cite), how poor Meko's answer was before picking (`startQuality`, for What Meko doesn't know), and holding it for the `SessionStart` context hook (`/context` on the hook socket). |
| `src/server/harness/` | The harnesses a session can run on (`docs/design/harnesses.md`): the `Harness` interface (`types.ts`: preparing its files, what a launch settles first, launch, hook payloads as AgentK's events, guard and context replies, edited paths, the Meko calls its hooks open and close for a CLI without the mod (`mekoTool`), its conversation and resume, the files a session's progress shows in, usage, the transcript for Meko, AgentK's mod, what it keeps for a session and drops when Meko changes (`forget`, `mekoChanged`), Ask AgentK, version and update), the registry and the pick for a new session (`index.ts`, `Harnesses`: the default, else the first available harness, else a 409 that says what to install; no harness is assumed installed; `statusOf` adds Meko's connection, `HarnessStatus.meko`, which keeps one `none`, `stale` or `elsewhere` from being available while there's a list to go by, `pick` reads Meko's list again before refusing one for it, and the 400 names the fix; `openCodeOwnMeko`), reading and comparing a CLI's version, the cached read and updater flag OpenCode's and Kiro's share (`cliState`) and the command a harness runs as (`harnessCommand`) (`version.ts`), and an adapter per CLI: `claude.ts` (Claude Code, over `claude.ts` and `claudecode.ts`: folder trust, the status line and mod variables), `opencode.ts` (OpenCode 2: its command line, always `--standalone`, its session's inline config and variables, the plugin's events as AgentK's, `normalizeOpenCode`, the files a patch names, AgentK's Meko server for it) and `kiro.ts` (Kiro CLI: the `agentk` agent's hooks, its command line, its conversation id, its usage from the session file, `normalizeKiro`). Code outside the adapters doesn't branch on a harness's id, apart from Kiro's plan reader (`Core.kiroPlan`), the agents' Meko status (`Core.claudeMekoStatus`, `Core.kiroMeko`, `Core.openCodeMeko`) and the usage report's per-day `kiro` counts and agent versions (`callhome.ts`). |
| `src/server/headtrust.ts` | Whether a session's PR head is trusted ([Code from public repos](../../docs/design/security.md#code-from-public-repos)): which sessions work on someone's PR head (`prHead`: a review, a task on a PR), the PR repo's visibility (kept 10 minutes; public or unreadable is untrusted), `repoConfigTrusted` (what `sessions.ts` checks before using the repo's status line and `.agent-k/stages` prompts, and the harnesses before loading its settings: Claude Code's `--setting-sources user`), the roles AgentK trusts (`TRUSTED_ASSOCIATIONS`), and the Kiro workspace config that stops an untrusted Kiro start (`kiroWorkspaceConfig`). `SessionManager.checkHead` reads it again before a launch's prompt is rendered (create, recover, resume), at every launch, and when `adoptPr` gives a session its PR, into `sessions.untrusted` (NULL with no PR head). |
| `src/server/launcher.ts` | The per-session launcher script every harness runs through (the login shell, the session's variables after the profile, every harness's markers cleared: `SESSION_MARKERS`, OpenCode's included), `shq()` and `scrubSessionMarkers()`, and the PATH the server and the session host take from the login shell at their start (`adoptLoginPath`: 5 s at most, with `~/.local/bin` and Homebrew's folders added, `withUsualBins` in `paths.ts`; it returns why the shell gave none, which `cli.ts` logs and `github.ts` puts in gh's error). |
| `src/server/opencode.ts` | OpenCode outside the adapter: the markers it sets, its command (the default also found in `~/.opencode/bin`, `openCodeCommand`), AgentK's plugin (its source and writer: the hooks of AgentK's OpenCode sessions, an OpenCode 2 plugin folder named by a hash of its files (`server.js`, `package.json`) and written only when missing, since OpenCode reloads a plugin whose files change, loaded only through their `OPENCODE_CONFIG_CONTENT`), a session's inline config, its CLI config (session tabs off, `OPENCODE_SESSION_CLI_CONFIG`) and its folder (`system.md`, the instructions; `messages.jsonl`, the usage and Meko calls the plugin logs, `parseOpenCodeMekoCalls`), whether OpenCode can still resume a session (`openCodeStoredSession`: its SQLite store's `session_v2`, read only, else the usage log), AgentK's Meko server for its sessions (an owner-only `meko.json` for `OPENCODE_CONFIG`, left out when OpenCode has a `meko` server of its own: any Meko reports, else one in its own config, `openCodeHasOwnMeko`, with a JSONC reader), the user's own config (`readOpenCodeConfig`), Ask AgentK's config and variables (`openCodeAskEnv`), what `[opencode] disable_tracking` adds to a run's environment (`OPENCODE_NO_TRACKING_ENV`) and one-shot output (`readOpenCodeRun`), and deleting a session (`--standalone`).
