# Phase 4k — `yb_light_local start` wedge on fresh init

## Resolution

Three landed changes — fresh `yb_light_local init + start` against an
empty `yb_storage` now comes up cleanly with no workaround.

1. `prepare_database_if_external` is hoisted out of
   `StorageController::start` and runs **synchronously** before the
   parallel-service JoinSet in `handle_start_all_impl`. This was
   the third (latent) wedge: pageserver / safekeeper /
   endpoint_storage all bind to `yb_storage` on start and crashed
   with `database "yb_storage" does not exist` whenever they raced
   storage_controller's own provisioning. The call is idempotent so
   the inner `StorageController::start` call still runs and is a
   no-op.
2. `ensure_yb_storage_schema` is wrapped in a per-attempt 120 s
   `tokio::time::timeout` + 3-attempt retry loop. Addresses the
   "sibling wedge" symptom where the tokio_postgres connection
   stalled silently between CREATE TABLE statements; reconnecting
   reliably makes forward progress because the schema-creation
   statements are idempotent.
3. `yb_light_local start --start-timeout` default bumped from 10 s to
   120 s. Storage_controller's diesel migrations take ~60 s on a
   fresh DB; the previous default fired before they finished and
   produced the original `relation "storage_controller.timelines"
   does not exist` symptom.

Also removed the per-test schema-bootstrap workaround from
`test/e2e/run.sh` — no longer needed.

(Below: original analysis at filing time.)

## Symptom

After a `yb_light_local init` + `start` against a freshly-created
`storage_controller` database, the very next API call from the
pageserver to storage_ctl fails with:

```
pageserver API: Conflict: 1 (localhost) 500 Internal Server Error:
500 Internal Server Error tenant is broken:
db error: ERROR: relation "storage_controller.timelines" does not exist
```

The default `--start-timeout 10s` triggers cleanup before
storage_controller's diesel migrations finish on a fresh DB. Bumping
to `--start-timeout 120s` (or higher) papers over it; sleeping ~30 s
after `start` before the first `tenant create` also works.

## Why it happens

`yb_light_local start` brings up storage_ctl's embedded Postgres, then storage_ctl
itself, then the pageserver. Pageserver registration with storage_ctl
appears to fire before storage_ctl's migrations have finished against a
just-created DB. The pageserver looks healthy by yb_light_local's standards
("port is open") but its first operation against storage_ctl hits a
schema that doesn't exist yet.

Storage_controller migrations against a freshly-dropped YB-style
database take ~60 s in practice; yb_light_local's health check doesn't
account for that.

## Sibling wedge (same area, hit twice on 2026-06-02)

`ensure_yb_storage_schema` (control_plane/src/storage_controller.rs)
itself can hang on a fresh YB database after the first few
`CREATE TABLE IF NOT EXISTS` statements complete. The tokio_postgres
connection ends up in a state where:

- yb_light_local's runtime sits in `do_epoll_wait` indefinitely (no syscall progress).
- pg_stat_activity shows zero active queries from the connection.
- Manually running the same `CREATE TABLE` via psql against YB
  succeeds in <1s, so YB itself is fine.

The hang reliably occurs *between* `pageserver.meta` and
`pageserver.timelines` creations. Killing yb_light_local and restarting
against the now-partial schema lets the idempotent path complete in
seconds because all CREATEs become no-ops.

Workaround: run init/start twice — or pre-create the schema
manually. Proper fix: investigate why the tokio_postgres connection
silently stalls; likely a connection-task cancellation race in the
external-DB bootstrap path.

## Repro

Clean slate:

```bash
export YB_LIGHT_REPO_DIR=$PWD/.e2e-tests
rm -rf "$YB_LIGHT_REPO_DIR"
target/release/yb_light_local init --config /tmp/neon-init.toml
target/release/yb_light_local start --start-timeout 30s     # default-ish
target/release/yb_light_local tenant create --tenant-id <fresh>   # ← fails
```

`start-timeout 240s` + `sleep 30` between `start` and `tenant create`
reliably unblocks; that's the current workaround.

## Fix shapes (pick one)

- **(a)** Bump `yb_light_local`'s default `--start-timeout` to ~120 s.
  Smallest change. Hides the underlying race but unblocks new-comers.
- **(b)** Drop the cross-service health-check coupling so
  `storage_controller` can finish migrating in parallel with
  pageserver registration retries.
- **(c)** Pre-create the storage_controller schema during
  `yb_light_local init` so first-`start` avoids the migration burst
  entirely.

(b) or (c) are the proper fixes; (a) is a sticky-plaster.
