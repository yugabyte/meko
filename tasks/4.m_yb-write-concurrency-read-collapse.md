# Phase 4m — YB write-side concurrency tuning + read-path collapse

## Write side

- Internal `PageStore` pool 1 → 4: `put_pages` already chunks at
  `PARALLELISM = 4` but was pipelining all chunks on a single YSQL
  conn (one YB backend) — independent conns give true 4-way
  concurrent INSERTs.
- Materialiser `MAX_INFLIGHT_INSERTS` 2 → 4 to match.
- `BATCH_DRAIN_LIMIT` 64 → 500 to amortise per-row PG protocol
  overhead.
- `MaterializeJob.chain` now captures the durable chain at
  write-side trigger time under the writer lock, so the materialiser
  skips both the cache fast path's `evicted_below` bailout AND the
  YB `read_chain_durable` round-trip on cache miss (~570 K trailing
  `read_chain` SQL hits observed pre-change on a 55 s TPC-C profile,
  expected to drop to near zero).

## Read side

- `read_chain` / `read_slru_chain` SQL collapsed from a two-query
  fast/slow path into one — anchor CTE + `LEFT JOIN ON TRUE` +
  `(p.lsn >= anchor.anchor_lsn OR anchor.anchor_lsn IS NULL)`, with
  client-side trim at first `will_init` row (covers the no-image
  case at full slow-path semantics in one round-trip).

## Cache eviction

- `UnifiedPages::evict_to_capacity` split-budget: real removals now
  run on a 2 ms wall-clock budget (~6 K entries / call) instead of
  the prior combined 64-iter cap that was leaking the cache by tens
  of MB per flush under sustained ingest; stale-skip stays bounded
  at 64.

## Tuning knobs

- `materialize_queue_capacity` 1000 → 2000 (burst absorption only —
  drain rate is the real lever).
- Compute-side `pageserver_response_disconnect_timeout` 150 s → 30 s.

New doc section "Compute ↔ pageserver timeouts" inventories the
full set of timers on that path.
