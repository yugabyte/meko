# PostgreSQL 17 → 18 merge

Notes from migrating yb-amp from PostgreSQL 17 to 18 (submodule
`compute/vendor/postgres-v18` at `REL_18_STABLE_amp` = `7b18ad1`, PG 18.2). This
doc records **what broke, why, and how it was fixed**, plus **patterns that
generalise to future PG merges**. Keep it updated as new issues surface.

## Approach

- **Gate, don't fork.** New-version deltas are wrapped in
  `#if PG_MAJORVERSION_NUM >= 18 … #else … #endif` (C) so future merges from
  neon upstream conflict minimally. The `#else` keeps the PG17 path compilable.
- **Label lag (temporary).** During bring-up the tree kept the `v17` *label*
  everywhere (`POSTGRES_VERSIONS=v17`, `pg_install/v17`, submodule dir
  `compute/vendor/postgres-v17`, `PgMajorVersion::PG17`) while the version *facts* said
  18 (`versionfile_string`→"18", parsers accept 18, `revisions.json`→18.2). The
  full `v17→v18` relabel is a separate mechanical pass done once the read/write
  paths validate — see "Version relabel" below.
- **Validate with the compute integration suite.** `test/integration/compute/run.sh all` is the
  gate. It accumulates diverse catalog/clog/rel/FSM churn across ~45 scenarios,
  which is what surfaces the *stateful* ingest/replay bugs a single scenario
  hides (see torn_wal_write below).

## Issues and fixes

### A. Compile-time (extensions: `compute/pgxn/yb_amp*`)

| Symptom | Cause | Fix |
|---|---|---|
| `INT64_MODIFIER` undefined | Removed in PG18 | Use `PRIx64` for `INT64_HEX_FORMAT`/`UINT64_HEX_FORMAT` (`yb_amp_pgversioncompat.h`) |
| `WaitEventSet` / `CreateWaitEventSet` unknown | WaitEventSet API split into `storage/waiteventset.h` | Add `#include "storage/waiteventset.h"` (+ `latch.h` where `ResetLatch` is used) |
| `pq_copymsgbytes` arg-type mismatch | PG18 `pqformat.h` signature changed `char *`→`void *` | Match the new signature under the PG18 gate |
| `ReplicationSlotAcquire` arity | PG18 added a parameter | PG18-gated call site |
| `ReorderBufferGetChange`/`GetTupleBuf` unknown | Renamed to `…AllocChange`/`…AllocTupleBuf` | Compat macros in `yb_amp_rmgr_decode.c` |
| smgr hooks gone | PG18 replaced `smgr_hook`/`smgr_init_hook` with a registration model (`smgrregister()` + `smgr_owns()`) | New `*_owns()` + `smgr_register_*()`; register in `_PG_init`/walredo instead of assigning hooks |

### B. smgr read path (AIO)

PG18 routes buffer reads through the AIO framework: an smgr must implement
`smgr_startreadv` / `smgr_maxcombine` / `smgr_fd` instead of a synchronous
`smgr_read`. yb_amp has no file to read (pagestore fetches over the network,
walredo reads an in-memory array), so it completes the read on the AIO
*synchronous* execution path rather than dispatching it:

- `yb_amp_startreadv` / `inmem_startreadv` fill the target buffers up front
  (`yb_amp_readv` / `inmem_readv`), set `op_data.read.fd = -1` as a sentinel,
  then `pgaio_io_stage()` the handle.
- A one-branch core patch in `compute/vendor/.../aio_io.c`
  `pgaio_io_perform_synchronously()` gates on `fd < 0`: skip the `preadv` and
  report the block count directly (no bytes→blocks callback is registered).
  A file-backed read always has `fd >= 0`, so the sentinel is unambiguous
  (yb-amp-postgres#1).
- That gate is reached by any read the buffer manager runs synchronously —
  every immediate `ReadBuffer`, and *all* reads under `io_method=sync`. So
  `_PG_init` forces `io_method=sync` (`PGC_S_OVERRIDE`): required for
  correctness (the async methods hand the read to a worker that reopens via
  `smgr_fd`, which errors for a network-backed smgr → reads would FAIL) and it
  keeps `read_stream`'s prefetch: the non-sync default (`worker`) disables it and
  regresses streaming reads (~7x bitmap, ~2x seqscan); with sync, reads are
  ~at parity with PG17.
- `smgr_maxcombine` returns `PG_IOV_MAX`; `smgr_fd` is an error stub.

True async getpage completion (a custom `IoMethodOps` that defers completion,
dropping the `io_method=sync` override) is tracked in #228.

### C. walredo "hand-rolled" startup (`compute/pgxn/yb_amp_walredo/walredoproc.c`)

walredo replicates a *curated subset* of Postgres per-process init instead of
calling `InitPostgres`. PG18 added new required init steps the standard path
picks up automatically but the hand-rolled copy missed — each surfaced as a
walredo crash:

- `InitPostmasterChildSlots()` + `InitializeFastPathLocks()` (after
  `InitializeMaxBackends`)
- `AioShmemInit()` (in the fake-shmem setup)
- `pgaio_init_backend()` + `InitLockManagerAccess()` (after
  `InitAuxiliaryProcess`; missing the latter → NULL `LockMethodLocalHash` →
  SIGSEGV in `lock.c`)
- PG18's `smgrinit()` re-registers an `on_proc_exit` callback *each call*, and
  walredo calls it per WAL record → "out of on_proc_exit slots". Fixed by
  re-initialising only the inmem smgr (`smgr_init_inmem()`) instead of full
  `smgrinit()`.

Also: shmem-init functions were renamed in PG18 (e.g. `→ BufferManagerShmemInit`).

### D. Data checksums default flipped

PG18 `initdb` enables data-page checksums **by default** (PG≤17 was off).
walredo's `GetPage` returns the redo-materialised page without recomputing
`pd_checksum`, so the compute rejected every materialised page ("page
verification failed, calculated X but expected Y"). Fix: pass
`--no-data-checksums` in `compute/libs/postgres_initdb/src/lib.rs` `do_run_initdb`.

### E. WAL commit-record decode — `xl_xact_stats_item` widened (12→16 B)

**Symptom:** safekeeper WAL sender panic
`cannot advance past 'remaining': 3276800 <= 616` (`bytes.rs`), which killed the
sender → pageserver walreceiver disconnected → pageserver stuck at
`last_record_lsn` → the next compute restart hung 180s in `Init`. Presented as
"`next-xid` times out" but the real failure was upstream in WAL decode.

**Cause:** PG18 widened `xl_xact_stats_item`: `PgStat_HashKey.objid` became
64-bit, stored as two `uint32` (`objid_lo`/`objid_hi`), so the struct grew from
12 bytes (`kind`,`dboid`,`objoid`) to 16. Our decoder
(`compute/libs/postgres_ffi/src/walrecord.rs`, `XlXactParsedRecord::decode`) still
skipped 12 bytes/item. Any commit record carrying *dropped-stats* items (e.g.
dropping an extension between scenarios) left the buffer misaligned by
4·nitems; the next field (invalidation-message count) read as garbage
(204800), and `buf.advance(3.2 MB)` panicked.

**Fix:** `sizeof_xl_xact_stats_item = 16` in `walrecord.rs` (with a comment).

### F. FSM/VM rel-size `MissingKey` wedge on ingest (regression of issue #36)

**Symptom:** in the `all` suite (needs accumulated churn — passes standalone),
`torn_wal_write` fails deterministically at iter 1 / mode A with pageserver
walreceiver panic `could not ingest record … could not find data for key
…01FFFFFFFF` (an **FSM-fork rel-size key**) during forward WAL replay after a
`kill -9`.

**Cause:** `torn_wal_write` is the regression guard for issue #36 — a
torn-recovery reldir can list an FSM/VM fork whose rel-size key is absent at the
replay LSN (the directory write landed but the first size write did not). The
#36 fix tolerated this in `Timeline::get_rel_size` (returns 0 for a missing
FSM/VM size), but **other ingest readers of the rel-size key were not guarded**:
`DatadirModification::put_rel_drop_v1` (dropping a rel reads each fork's size
for logical-size accounting) and `put_rel_extend`. `torn_wal_write` does
`DROP TABLE` every iteration, so the drop path hit the unguarded read →
`MissingKey` propagated → panic.

**Fix:** extend the #36 tolerance (missing FSM/VM size ⇒ 0; MAIN still errors)
to `put_rel_drop_v1` and `put_rel_extend` in
`compute/pageserver/src/pgdatadir_mapping.rs`. FSM/VM are advisory (rebuilt by VACUUM),
so treating a missing size as 0 is correct, not masking — and the scenario's
`count(*)==max(id)` MAIN-fork assertion still guards real corruption.
**Validated:** `torn_wal_write` PASSES in the full `all` suite after this fix.

### G. `bulk-mixed` — not a code bug (resource contention)

`bulk-mixed` (2M-row insert + index + 100k updates) once failed with
`psql exited status 2` (= connection to server lost). It turned out to be
**environmental**: that run had several other integration clusters up concurrently on
the shared box, and the heavy workload lost its connection under the
contention. On a clean, dedicated checkout it passes (764s). Lesson: an
`exit status 2` from a `psql` workload is a dropped connection (crash / OOM /
contention), *not* an output mismatch — check for competing clusters and
pageserver/walredo crash markers before assuming a PG18 regression.

### H. walproposer re-acquires its replication slot on reconnect (`--enable-cassert` abort)

**Symptom:** on the pg18 branch, `torn_wal_write` (mode D recycle) and
`restart_wal_replay` fail when the compute is restarted around a safekeeper
recycle: the compute's `WAL proposer` background worker aborts with `TRAP:
failed Assert("MyReplicationSlot == NULL")` (`replication/slot.c`). Because
compute runs `restart_after_crash=off`, that one abort takes the whole
postmaster down (exit 1); compute_ctl then retries with fresh basebackups,
which race on the not-yet-released ports and surface as a *misleading*
`Address already in use` / "endpoint start … exited status 1". The port
conflict is fallout — the root cause is the assert.

**Cause:** `StartProposerReplication` (`compute/pgxn/yb_amp/walproposer_pg.c`) acquires
the slot with `ReplicationSlotAcquire`, then enters `WalSndLoop`, which streams
until process exit and never reaches the matching `ReplicationSlotRelease` at
the end of the function. On a safekeeper reconnect the walproposer re-drives
streaming and re-enters `StartProposerReplication` while still holding the
slot, so it re-acquires a slot it already owns. `ReplicationSlotAcquire`
`Assert()`s `MyReplicationSlot == NULL` on entry. That assert is a no-op in the
PG17 build (configured without `--enable-cassert`) but live in the PG18 build
(`--enable-cassert`) — which is the sole reason this latent double-acquire
crashes only on pg18, even though the walproposer code is version-shared.

**Fix:** release any slot already held before re-acquiring, in
`StartProposerReplication`:
`if (MyReplicationSlot != NULL) ReplicationSlotRelease();`. No-op on the first
(non-reconnect) pass. **Validated:** `torn_wal_write` and `restart_wal_replay`
pass repeatedly on pg18 after the fix; both failed reliably before (`main`/PG17
always passed).

### Result

After fixes E + F, `test/integration/compute/run.sh all` is **green: 50 PASS / 0 FAIL**,
corruption-clean (validated on a dedicated checkout).

## Patterns for future merges

1. **A "timed out in Init" / "next-xid hangs" compute symptom is usually a
   *decode/ingest* failure upstream.** Trace it: compute Init hang → pageserver
   `last_record_lsn` stuck / walreceiver "disconnected" → safekeeper WAL-sender
   panic or pageserver ingest panic. Read the safekeeper log, not just the
   compute log.

2. **WAL struct-size drift is the classic decoder break.** Any PG struct that
   `compute/libs/postgres_ffi/src/walrecord.rs` hardcodes a `sizeof_*` for (stats
   items, invalidation messages, xl_xact_*) must be re-checked against the new
   `src/include/access/*.h`. A hardcoded size that drifts corrupts *everything
   after it* in the record (misalignment), so the panic often points at a
   *later* field than the one that actually changed. When you see
   `bytes.rs: cannot advance past 'remaining'`, suspect an earlier size
   constant.

3. **Stateful ingest/replay bugs need the full `all` suite.** Anything touching
   crash recovery, FSM/VM, clog, multixact, or rel-size only reproduces once
   diverse catalog/rel churn accumulates. A scenario that passes standalone can
   fail deterministically inside `all` at the *same* LSN/iteration — that's a
   real bug, not a flake. Don't trust standalone-green for these classes.

4. **`initdb`/GUC defaults flip silently across majors.** Checksums (PG18) are
   the example; audit `initdb` defaults and any GUC the walredo/basebackup path
   assumes. A default flip shows up as a data-integrity error
   ("verification failed"), not a build error.

5. **The hand-rolled walredo init lags every major.** `WalRedoMain` /
   `CreateFakeSharedMemoryAndSemaphores` curate a subset of `InitPostgres`.
   Every major that adds a per-process/shmem init step (AIO, fast-path locks,
   PM-child slots, lock-manager access) will crash walredo until the step is
   copied in. Diff the new `InitPostgres` / `AuxiliaryProcessMain` against the
   walredo copy on each merge.

6. **A `MissingKey` tolerance added for one read path must be applied to *all*
   readers of that key.** The #36 FSM/VM tolerance lived only in
   `get_rel_size`; the drop/extend readers regressed. When you add
   "tolerate missing X here", grep every reader of X.

7. **Errors that cross a typed-error boundary lose their backtrace.** The
   ingest `MissingKeyError` reaches the walreceiver as an anyhow `.context()`
   with only the wrapper frames — the originating ingest function is not in the
   trace (`backtrace: None` at construction). To pinpoint an ingest read, either
   temporarily populate that backtrace or reason from the key encoding (forknum
   byte + `0xFFFFFFFF` blockno ⇒ a rel-size key for that fork).

8. **Registration-model migrations (smgr).** PG18's shift from global hooks to
   `smgrregister()`/`smgr_owns()` is the template for future "hook → registry"
   changes: add an `_owns()` predicate and a `register_*()` called from init,
   keep the old hook assignment under the `#else`.

9. **A cassert-enabled new-major build turns latent invariant violations
   into hard aborts.** When a recovery/slow integration test fails *only* on the new
   branch with an `Assert(...)` `TRAP`, it is a real invariant break the old
   build silently tolerated (asserts compiled out), not a new-version
   behavior change. Fix the caller; never quiet the assert. (walproposer slot
   re-acquire on reconnect, §H, is the example.)

## Version relabel (v17 → v18)

_Status: **done**. Single-version PG18; `run.sh fast` integration green on macOS (41/0)._
It's a coupled, all-or-nothing change because the build derives everything from
`POSTGRES_VERSIONS`: `POSTGRES_VERSIONS=v18` ⟹ `compute/vendor/postgres-v18` (submodule
source, via `postgres.mk`'s `compute/vendor/postgres-$(pg_version)`) ⟹ `pg_install/v18`
⟹ `build.rs pg_version="v18"` ⟹ `bindings_v18.rs` ⟹ `postgres_ffi` `v18` module
⟹ `PgMajorVersion::PG18`.

**Recipe:**
- **Submodule dir:** `git mv compute/vendor/postgres-v17 compute/vendor/postgres-v18` (stage
  `.gitmodules` first, or `git mv` refuses); then fix the `[submodule "…"]`
  section *name* in `.gitmodules` by hand (`git mv` only rewrites `path =`).
- **`postgres_ffi`:** the macro token in `for_all_postgres_versions!` and the
  `dispatch_pgversion`/`enum_pgversion*` arms (`v17`→`v18`, `V17`→`V18`,
  `PG17 => v17`→`PG18 => v18`); `build.rs` `pg_version="v18"`; rename
  `pg_constants_v17.rs`→`pg_constants_v18.rs`.
- **`postgres_versioninfo`:** rename the enum variant **and fix the values** —
  `PG18 = 18` (discriminant), `major_version_num => 18`. The migration had left
  these at 17 (label lag) while only `versionfile_string` said 18.
- **Sweep** `PG17→PG18` / `v17→v18` across code/build/docs/Dockerfiles.
- **Build:** `rm -rf pg_install/v17`, then `make postgres-install` → `pg_install/v18`.

**Landmines the token sweep can't catch (do NOT blanket-sed):**
- SQL test-data uses `v17` as a column alias (`v17.c1833`) —
  `old_neon_test_runner/{performance/test_perf_olap.py,regress/test_compatibility.py}`.
- `.github/` has external **secret names** (`secrets.…_PG17`) + CI image maps.
- `old_neon_test_runner/fixtures/pg_version.py` has its own `PgVersion.V17`
  enum (legacy Python harness). All left as-is.

**Relabel-completion pass (bare numeric `17` the sweep missed):** the token
sweep only touches `PG17`/`v17`/`V17`; it cannot catch a bare `17`/`"17"`.
`cargo test --workspace --lib` (NOT integration — integration never runs unit tests) surfaced
the breakage. Fixed to `18`:
- Unit-test fixtures + a live assertion: `config.rs` (`pg_version = 17`,
  `major_version_num() == 17`), `page_store.rs`, `page_writer.rs`,
  `metadata.rs`; `pageserver_api/config.rs` doc.
- `compute_tools::parse_pg_version` test strings (`"PostgreSQL 17.x"`).
- **Hardcoded `--pg-version 17`** in the integration harness (`cluster.rs` + 8
  `fast/*.rs`) and `yb_amp_local` — this one is caught only by an integration run
  (branch-create fails: `yb_amp_local` now rejects `17`), *not* by cargo test.
- Control-plane **defaults**: `controller/local/config`
  (`DEFAULT_PG_VERSION` / `DEFAULT_PG_VERSION_NUM`), and the Go
  controller `deploy/kubernetes.go` + `api/handlers.go` `defaultPgVersion` — a
  PG18 product must not default new projects to a version it can't build.

The old `17 | 18 => PgMajorVersion::PG18` acceptance (a label-lag relic) was
then tightened to **`18`-only** across all parse/match sites now that nothing
emits `17`.

## Multi-version (17 + 18) — how to un-collapse, if ever needed

We are deliberately **single-version** (no PG17 users; product unreleased). The
neon multi-version machinery is preserved, so adding a version later is
*additive* (per the trim commit `94a6ca85c`). If a real need appears:
- Re-add `compute/vendor/postgres-v17` @ `REL_17_STABLE_amp` (the pre-migration branch,
  carries yb-amp's pre-AIO patches); `POSTGRES_VERSIONS = v17 v18`; loop
  `build.rs`; recreate `pg_constants_v17.rs`; re-add `PG17 = 17` to the enum
  with its arms; `for_all_postgres_versions!(v17, v18)`.

**Boundary-shift revert map (the delicate part).** The mechanical `PG17→PG18`
sweep turned every `< PG17`/`>= PG17` *comparison* into `< PG18`/`>= PG18`.
That is behavior-preserving for single-version (18 is on the same side of a
17-boundary), but for multi-version a `< PG18` gate wrongly puts PG17 on the
pre-17 side. Each comparison must be re-examined; the enum-definition arms
(`major_version_num`, `versionfile_string`, `v_str`, `ALL`, parsers,
`PG18 => v18`) are NOT boundaries — those just gain a parallel PG17 arm.

| Site | Now | For 17+18 | Why |
|---|---|---|---|
| `walrecord.rs:1107` `XlClogTruncate` pageno | `< PG18` | **`< PG17`** | 64-bit SLRU page numbers landed in PG17 |
| `wal_decoder/decoder.rs:387,479` pageno | `< PG18` | **`< PG17`** | same (multixact SLRU pagenos) |
| `basebackup.rs:726` twophase 8-/16-hex | `< PG18` | **`< PG17`** | 64-bit (16-hex) 2PC filenames landed in PG17 |
| `walingest.rs:774,879` `xid: u64` | `>= PG18` | **verify** (likely `>= PG17`) | 64-bit xid / FullTransactionId era is PG17 |
| `walingest.rs:1228` `oldest_active_xid` | `>= PG18` | **verify** | check neon origin |
| `pgdatadir_mapping.rs:1218,1580,1949,2514` | `>= PG18` | **verify** | check neon origin per site |
| `walrecord.rs:1058` `sizeof_xl_xact_stats_item` | hardcoded `16` | **re-gate** `>= PG18 ? 16 : 12` | genuine 18-vs-17 diff (pgstats objid 64-bit is PG18) — but plumb `pg_version` into `XlXactParsedRecord::decode`, which currently takes none |

Method to classify a **verify** site: check the neon-upstream original (`git
log`/blame the pre-relabel line) — a neon `>= PG17` boundary means 17 belongs on
the modern side (revert to `PG17`); a genuinely-new-in-18 behavior keeps `PG18`.
Getting one wrong silently corrupts PG17 data (the twophase case is proof).

Effort if pursued: mechanical parts (submodule/enum/build) are fast; the real
cost is the boundary audit above + building **two** Postgres trees + integration on
**both** versions. Estimate ~a few build/validate cycles, not minutes — the
wall-clock is Postgres compiles, not edits.
