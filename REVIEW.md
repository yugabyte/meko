# PR review guide

Use this when reviewing a pull request in this repo (human or agent). A good review
covers whatever the change actually touches — correctness, tests, docs, operational
impact, hygiene — so weight your attention by what's in the diff.

**This file carries the rules that apply to every review here.** What to actually look
for is project-specific and lives one level down:

| Reviewing changes under | Read, after this file |
|---|---|
| `amp/**` | [`amp/REVIEW.md`](amp/REVIEW.md) — compute/storage engine (pageserver, safekeeper, `compute_ctl`), control plane, deploy/Kubernetes, and the on-demand `/ci` suites |
| `meko/**` | [`meko/REVIEW.md`](meko/REVIEW.md) — `api_server`, database & migrations, `meko_ui`/`meko_admin`, `meko-provisioner`, `inference_gateway`, `cli_app` |
| `ycp/**` | **Not covered by either.** See below |

A PR spanning both trees needs both guides.

> **Report findings that matter.** Surface issues you're reasonably confident
> about and that carry real severity — don't report low-confidence guesses or
> low-severity nits. Tag each finding with its severity so the author can
> triage.
>
> **Keep the output reasonably sized.** Cover the findings, but write each one
> tersely — enough for the author to locate the issue and act on it (what's
> wrong, where, why it matters), and no more. Skip restating the diff, padding,
> and multi-paragraph explanations of one-line problems. Terse and actionable
> beats verbose.

> **Agents: pick the model by review complexity.** Run substantive reviews —
> anything touching correctness, concurrency, storage/schema/WAL, or cross-service
> seams — on an Opus-class model (e.g. Opus 4.8); review judgment is the
> priority there, not speed or cost. Simple reviews (docs, comments, config,
> small mechanical diffs) may downgrade to Sonnet. Never use Haiku, and don't
> use Fable unless explicitly requested.

## Before you start — gates

**Oversized PRs — ask before proceeding.** Check the size first. If any
threshold is exceeded, **stop and ask the user for permission to proceed** — the
point is to avoid accidentally burning tokens on a review that big:

- more than **20 commits**, or
- more than **100 files** changed, or
- more than **5000 lines** changed (additions + deletions).

If they decline, suggest the PR author run the review with their local AI agent
instead.

**Cap the review's own budget.** Stop and report progress rather than pushing
past either limit:

- **Wall-clock: 10 minutes.**
- **Tokens: 1M (~$25 on Opus).**

On hitting a cap, say how far you got and what's left. These are hard limits, not
targets — don't exceed them.

## Hygiene — both trees

- **No agent/assistant attribution** in commits or the PR body — no
  "🤖 Generated with Claude Code" / "Generated by Claude" line, no
  `https://claude.ai/code/…` session link or session id, and no
  `Co-Authored-By:` trailer. The PR and its commits are authored by the human.
- Body explains **what and why**, not just the diff, and follows the sections the
  `open-pr` skill specifies.
- Link related PRs and issues with **full URLs**, never a bare `#123` — AMP's issues
  were renumbered by the monorepo migration, so a bare number can resolve to an
  unrelated item.

Title conventions differ per tree (`[MEKO-<num>]` vs `[#<issue>]`) — see each guide.

## Reading paths in those guides

Paths quoted **inside** each guide are relative to that guide's own directory, not to
the repository root. So `api_server/` in `meko/REVIEW.md` means `meko/api_server/`, and
`compute/` in `amp/REVIEW.md` means `amp/compute/`. Paths in this file, like every
root-level file, are repo-root-relative and carry the prefix.

## `ycp/` has no review guide

`ycp/` sits at the root because it is shared between meko and amp, and **neither guide
mentions it**. Until one does, review it against `meko/REVIEW.md`'s Go and migration
sections — it is Go with its own `go.mod` — and note the coupling that has already
caused one CI break: its e2e (`ycp/test/e2e/run.sh`) builds **two** images, the agent
from `ycp/` and the control plane from `meko/api_server/`, so a change to either tree
can break it.
