# PR review guide

Use this when reviewing a pull request in this repo (human or agent). A good review
covers whatever the change actually touches — correctness, tests, docs, operational
impact, hygiene — so weight your attention by what's in the diff.

**This file carries the rules that apply to every review here.** What to actually look
for is project-specific and lives one level down:

| Reviewing changes under | Read, after this file |
|---|---|
| `amp/**` | [`amp/REVIEW.md`](amp/REVIEW.md) — compute/storage engine (pageserver, safekeeper, `compute_ctl`), control plane, deploy/Kubernetes, and the on-demand `/ci` suites |
| `meko/**` | [`meko/REVIEW.md`](meko/REVIEW.md) — `api_server`, database & migrations, `meko_ui`/`meko_admin`, `meko-provisioner`, `inference_gateway`, `cli_app` |
| `ycp/**` | this file — see [*`ycp/` — reviewing the shared tree*](#ycp--reviewing-the-shared-tree) below. It is shared, so its concerns live at the root |

A PR spanning more than one tree needs each of their guides.

> **Report findings that matter.** Surface issues you're reasonably confident
> about and that carry real severity — don't report low-confidence guesses or
> low-severity nits. Tag each finding with its severity so the author can
> triage.
>
> **Keep the output reasonably sized.** Cover the findings, but write each one
> tersely — enough for the author to locate the issue and act on it (what's
> wrong, where, why it matters), and no more. Skip restating the diff, padding,
> and multi-paragraph explanations of one-line problems. Terse and actionable
> beats verbose.

> **Agents: pick the model by review complexity.** Run substantive reviews —
> anything touching correctness, concurrency, storage/schema/WAL, or cross-service
> seams — on an Opus-class model (e.g. Opus 4.8); review judgment is the
> priority there, not speed or cost. Simple reviews (docs, comments, config,
> small mechanical diffs) may downgrade to Sonnet. Never use Haiku, and don't
> use Fable unless explicitly requested.

## Before you start — gates

**Oversized PRs — ask before proceeding.** Check the size first. If any
threshold is exceeded, **stop and ask the user for permission to proceed** — the
point is to avoid accidentally burning tokens on a review that big:

- more than **20 commits**, or
- more than **100 files** changed, or
- more than **5000 lines** changed (additions + deletions).

If they decline, suggest the PR author run the review with their local AI agent
instead.

**Cap the review's own budget.** Stop and report progress rather than pushing
past either limit:

- **Wall-clock: 10 minutes.**
- **Tokens: 1M (~$25 on Opus).**

On hitting a cap, say how far you got and what's left. These are hard limits, not
targets — don't exceed them.

## Hygiene — both trees

- **No agent/assistant attribution** in commits or the PR body — no
  "🤖 Generated with Claude Code" / "Generated by Claude" line, no
  `https://claude.ai/code/…` session link or session id, and no
  `Co-Authored-By:` trailer. The PR and its commits are authored by the human.
- Body explains **what and why**, not just the diff, and follows the sections the
  `open-pr` skill specifies.
- Link related PRs and issues with **full URLs**, never a bare `#123` — AMP's issues
  were renumbered by the monorepo migration, so a bare number can resolve to an
  unrelated item.

Title conventions differ per tree (`[MEKO-<num>]` vs `[#<issue>]`) — see each guide.

## Upgrade safety — every PR

**Every change must be upgrade safe.** The rule and its five cases are in
[`AGENTS.md`](AGENTS.md#every-change-must-be-upgrade-safe): old and new builds running
together, data the old build wrote, migrations that run while old pods serve, rollback,
and upgrade in place. CI runs a single build, so it can't catch a violation. That makes
this check the reviewer's job on every PR, whichever tree it touches.

For each persisted or cross-process surface the diff touches, ask:

- What happens when the previous release sends this, or receives it?
- Can the new build read what the previous release stored?
- Can the old pods still running keep serving once the new build has migrated?
- Does it stop the previous release from starting again? Every new migration file does,
  and so does a format the previous release can't read. Then it raises the downgrade
  floor, and the PR must name the new floor.

A change that breaks one of these with no stated plan (rollout order, a flag, or a
multi-release sequence) is a **high-severity** finding, even when every test passes.
When the diff touches such a surface, the PR body's **Upgrade safety** section must say
how a mixed-version pair behaves. A missing or hand-waved answer is also a finding. The
tree guides list the surfaces particular to each tree.

## Reading paths in those guides

Paths quoted **inside** each guide are relative to that guide's own directory, not to
the repository root. So `api_server/` in `meko/REVIEW.md` means `meko/api_server/`, and
`compute/` in `amp/REVIEW.md` means `amp/compute/`. Paths in this file, like every
root-level file, are repo-root-relative and carry the prefix.

## `ycp/` — reviewing the shared tree

`ycp/` sits at the root because it is shared, so its review concerns live here rather
than in either project's guide. It is small — one Go module, `module meko/ycp` — but it
spans a **trust boundary**, and that is what makes reviewing it non-obvious: the control
plane is ours, the `meko-agent` runs in the **customer's** cluster.

Start from [`ycp/ARCHITECTURE.md`](ycp/ARCHITECTURE.md), then weight these by the diff.

### `internal/api/types.go` is a wire contract, not internal types

It is JSON on the wire between our control plane and an agent the customer upgrades on
their own schedule, so **the two sides are always skewed in production**. It is the
sharpest case of [upgrade safety](#upgrade-safety--every-pr). Treat any change here as a
compatibility change:

- **JSON tags are the contract**, not the Go field names. Renaming a tag breaks agents in
  the field while the Go still compiles.
- `EnvState` is a **string** enum (`PENDING` … `DEREGISTERED`). A new value is safe only
  if the receiver tolerates unknown states; removing or renaming one is not.
- A new required field breaks older agents that never send it. Prefer additive and
  optional (`omitempty`), and have the PR say how a mismatched pair behaves.

### Direction is a security property

The agent reaches YCP over **outbound HTTPS only**; YCP never dials into a customer
cluster (`ARCHITECTURE.md:73`). Anything that introduces an inbound call, a callback URL,
or a port the customer must open inverts that model — a finding, not a design detail.

### The API key is the agent's only credential

Every agent call authenticates with the environment's YBM API key (bearer through
YBM's pass-through; `X-Meko-Admin-Secret` + `X-Meko-Api-Key-ID` direct against a
standalone control plane). One key drives one environment; the key id alone resolves
it, and enrollment is an idempotent check-in repeated at every startup. A change that
reintroduces a mintable agent-side credential, or makes enroll non-idempotent, brings
back the lockout class the token model had — check restarts and re-registration
deliberately.

### The e2e builds two images from two trees

`ycp/test/e2e/run.sh` builds the agent from `ycp/` **and** the control plane from
`meko/api_server/` (`run.sh:193`), so a change in either tree can break it — this has
already caused one CI break. It also asserts the whole surface is mounted under the
`/ycp` base path, with nothing at the domain root but the kubelet health alias: a route
added outside that base passes unit tests and fails deployment.

### Mechanics

`ycp/` has its own `go.mod`, so checks run from there (`cd ycp && go test ./...`) —
`gofmt`/`vet` aimed at the other trees' paths will miss it. The reconcile-agent image
publishes to Quay on merge to `main`
(`.github/workflows/ycp-reconciler-agent-image.yml`), so a Dockerfile change ships on
merge rather than at a release.

For anything not covered here — general Go style, migrations — use
[`meko/REVIEW.md`](meko/REVIEW.md).
