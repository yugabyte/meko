Platform Design · Draft

Meko BYOC Control Plane

Split Meko into a Meko-operated control plane and a customer-operated data plane, connected by a single outbound pull agent — so every byte of customer memory, RAG, and conversation data stays in the customer's own cloud. The control plane runs inside the YBM Aeon VPC and federates identity from Aeon over OIDC.

Owner: Platform Updated: 2026-07-16 Model: agent pull Auth: YBM Aeon OIDC Status: Draft

01 Summary

Today Meko runs as a single-tenant-per-row SaaS: one set of Meko-operated infrastructure (api_server + shared YugabyteDB universes + a shared MCP server) holds all customer data.

BYOC (Bring Your Own Cloud) splits that into two planes:

Control plane (MCCP) — Meko-operated, running inside the YBM Aeon VPC. Fleet registry + desired state; federates identity + entitlements from Aeon. Holds no customer data, no customer cloud credentials, and runs no billing of its own (billing is upstream in Aeon).
Data plane — customer-operated. Datapack workloads, the operator, and customer-owned YugabyteDB (a YBM Aeon cluster), in the customer's own Kubernetes cluster.

The planes are joined by a lightweight pull agent (meko-agent) running in the customer cluster. It only ever dials out to the control plane — there is no inbound network path into the customer's cloud. This mirrors the Amp BYOC control plane.

Why the pull model

02 Architecture

Key invariant. The only cross-plane channel is the agent's outbound connection. Customer memory/RAG data, YugabyteDB, and all data-plane secrets never leave the customer's cloud.

Functional split — MCCP vs Meko (data plane)

Meko (the data plane) keeps 100% of today's functionality. Every runtime feature the product ships now runs in the customer's cluster, unchanged. BYOC only lifts the control functions up to MCCP (identity, entitlements, fleet, desired state) and moves CR authoring into the agent. Nothing is removed from the data plane, and no MCCP dependency sits in the request path — datapacks keep serving even if MCCP is unreachable (§7, DEGRADED).

A customer's agents, CLI, and inference_gateway talk to Meko in the customer cloud exactly as they do today; only the management plane (onboarding, entitlements, fleet health, cross-customer dashboards) is what MCCP adds on top.

03 Data residency

This is the entire point of BYOC, so it is stated explicitly.

Stays in the customer cloud with Meko (never transmitted to MCCP): YugabyteDB and all its contents (datapacks.*, dist_rag.*); the customer's YugabyteDB credentials; OpenAI / Bedrock / AWS keys; Langfuse entirely — instance, Postgres, provisioning (agent-created org/project/keys), and traces; the meko-shared-credentials secret and all per-tenant secrets.
Held by MCCP: identity (users, accounts, Aeon OIDC subs, entitlements); fleet metadata (environments, health, versions, capacity); datapack metadata (id, name, owner, placement, desired versions, phase — but not its data); enrollment-token secrets and each environment's public identity. Never the customer's cloud credentials.

04 Authentication & identity

MCCP runs inside the YBM Aeon VPC and authenticates humans as an OIDC client (relying party) of YBM Aeon's identity provider. Aeon owns the login; MCCP federates the identity and layers its own session + entitlements on top. There is no bespoke Meko login for BYOC.

Because it is standard OIDC discovery, the same MCCP code serves both deployment topologies — only the issuer URL and client credentials differ:

TopologyWhere MCCP runsOIDC issuer
Cloud MCCPInside the YBM Aeon (cloud) VPCYBM Aeon cloud
On-prem MCCPAlongside a self-managed / on-prem AeonThat on-prem Aeon

Three distinct auth channels — do not conflate them:

ChannelPrincipalMechanism
Human → MCCPMeko operators, customer adminsOIDC relying party of YBM Aeon → MCCP session
Agent → MCCPmeko-agentmTLS environment identity (issued at enrollment)
Agent / inference → datapack MCPcustomer agents, inference_gatewayPAT mko_tkn_…
Cognito becomes legacy. The existing -cognito-* path is retired for MCCP; YBM Aeon OIDC is the default (and only) human IdP. New flags: -oidc-issuer-url, -oidc-client-id, -oidc-client-secret, -oidc-redirect-url. The Aeon sub claim replaces the Cognito sub as the account user_id, so downstream account plumbing is unchanged.

05 MCCP — the minimal layer & its API surface

MCCP is api_server run with -control-plane-mode, deployed inside the YBM Aeon VPC, plus its control DB. We build it minimally — it is only four things:

  1. Control DB — meko_system.* plus the new environments fleet registry (§8). Metadata only; no tenant data ever lands here.
  2. Identity — OIDC relying party of YBM Aeon (§4).
  3. Desired-state store — the authoritative set of environments, datapacks, and target versions that agents reconcile toward.
  4. HTTP API surface — below. MCCP is stateless and scales horizontally behind the Aeon VPC load balancer.

Nothing else from today's api_server is needed for the MVP: no per-datapack DB provisioning, no in-cluster k8s client (that moves to the agent), no direct MCP serving.

API surface — three groups

A · Human / console API — OIDC-authenticated (§4); called by the meko CLI and the cloud console:

Method + pathPurpose
POST /api/v1/datapacksCreate a datapack — writes metadata + placement, emits desired state; does not touch k8s.
GET /api/v1/datapacks · /{id}List / read datapack metadata.
DELETE /api/v1/datapacks/{id}Mark a datapack for teardown (agent reconciles).
POST /api/v1/environmentsRegister an environment — optionally with a new-cluster spec (provider / region / node size); mint a one-time enrollment token.
GET /api/v1/environments · /{id}Fleet view + health + state (§7).
entitlement (read-only)Plan/caps read from YBM Aeon upstream — no billing endpoints in MCCP. Observe is a deep-link to the in-cloud UI, not an MCCP-brokered session.

B · Agent API — mTLS environment identity (§4); called by meko-agent (detailed in §8). The pre-agent installer uses a token-authed bootstrap-progress endpoint for the same channel:

  • POST/api/v1/agent/bootstrap-progressPre-agent installer reports cluster-provisioning + install steps (§7.1).
  • POST/api/v1/agent/enrollExchange enrollment token → mTLS identity.
  • GET/api/v1/agent/desired-stateLong-poll the resources assigned to this environment.
  • POST/api/v1/agent/statusHeartbeat + component/datapack phases + metrics (§9).

C · Internal API — shared-secret (X-Meko-Internal-Secret); unchanged MCP→api_server PAT validation under /api/v1/internal/*.

Minimal build order. Stand up MCCP with the control DB + OIDC + the environments registry + the agent API behind -control-plane-mode, pointed at a Meko-owned test environment. That is the smallest thing that exercises the full pull loop end-to-end without a customer. The desired-state payload is the contract between MCCP and Meko — version it from day one.

06 The pull agent

A new lightweight Go binary in the monorepo — meko-agent — reusing the today-dormant k8s CR client from api_server/internal/k8s/client.go. It runs as a Deployment in the customer cluster and owns three outbound flows:

  1. Enroll. On first start it presents a one-time enrollment token, is attested by the control plane, and exchanges the token for a long-lived environment identity (mTLS client cert). It reports cluster facts (Kubernetes version, region, node capacity).
  2. Poll desired state. It long-polls for the resources assigned to this environment: which bootstrap components to run, which MekoUserAccount/datapack specs should exist, and target image versions.
  3. Report status. Heartbeats plus per-component and per-datapack phase and version, keeping the control-plane fleet view accurate.
The agent is the only writer of MekoUserAccount CRs. This relocates CR-authoring out of the control plane (where it is currently dead code) into the customer cluster, driven by desired state.

07 Bootstrapping state machine

The lifecycle of onboarding one customer environment, tracked as environment.status in the control-plane fleet registry.

StateMeaningDatapacks servable?New placements?
PENDINGEnv record exists; token issued, agent not yet seen.NoNo
CLUSTER_PROVISIONINGNew-cluster path: installer is standing up a fresh K8s cluster in the customer's cloud.NoNo
ENROLLINGInstaller running; agent starting.NoNo
ATTESTINGControl plane validating the enrollment token.NoNo
PROVISIONINGAgent installing CRD, operator, ingress, secret scaffold.NoNo
VALIDATINGSmoke checks: operator healthy, YugabyteDB reachable, canary datapack up + down.NoNo
READYHealthy and schedulable.YesYes
DEGRADEDHeartbeat missed or a component unhealthy. Existing datapacks keep serving.YesNo
SUSPENDEDAeon billing lapse or admin hold. Agent stops accepting new work.ReadNo

DEREGISTEREDEnvironment removed; agent identity revoked.NoNo

Transition guarantees

  • Every transition is triggered by an agent-reported fact or an admin action — never by MCCP reaching into the cluster.
  • PROVISIONING/VALIDATING are idempotent and retried with backoff; a partial install re-converges rather than requiring a manual reset.
  • Revocation (DEREGISTERED) invalidates the environment's mTLS identity so a leaked agent credential cannot resume pulling desired state.

7.1 Two onboarding modes — attach or provision

The customer chooses one when registering the environment. Both are driven by the meko bootstrap installer (a wizard / one-command CLI shipped in the meko-devops chart); both keep the customer's cloud credentials on the customer's side — MCCP never receives them.

ModeStarting pointWhat meko bootstrap does
Attach existing clusterCustomer already has a K8s cluster + kubeconfigInstalls the Helm chart (agent + CRD + operator); PENDING → ENROLLING.
Provision new clusterCustomer has a cloud account but no clusterProvisions a fresh cluster (YBM Aeon cluster API, or eksctl/gke/Terraform with local creds), then installs the chart; PENDING → CLUSTER_PROVISIONING → ENROLLING.

The installer holds a short-lived enrollment token and reports each step outbound to MCCP (POST /api/v1/agent/bootstrap-progress) so the fleet view shows live progress before the long-running agent exists. Once the agent is up and attested, it takes over all outbound reporting. The new-cluster path pairs naturally with a customer-owned YBM Aeon cluster — provision the Aeon data cluster and the Meko K8s cluster in the same wizard, same cloud/region.

08 Changes by component

api_server — becomes MCCP in control-plane mode

api_server run with -control-plane-mode is MCCP; the operator + workloads in the customer cluster are Meko.

New fleet domain. Add an environments registry table to meko_system:

New agent-facing API (mTLS + environment identity, separate from the human OIDC and PAT channels in §4):

  • POST/api/v1/agent/enrollExchange enrollment token → mTLS identity.
  • GET/api/v1/agent/desired-stateLong-poll; returns bootstrap components + datapack specs + target versions for the calling environment.
  • POST/api/v1/agent/statusHeartbeat + component/datapack phases.
  • Placement. AssignUniverse (internal/service/yba_service.go) generalizes to AssignEnvironment: a datapack is placed onto a customer environment whose registered YugabyteDB becomes its "universe". Free-tier accounts stay on a Meko-hosted default environment.
  • Stop shipping data-plane secrets. Today the CR spec carries YugabyteDBPassword from api_server. In BYOC the control plane emits a spec that references secret names; the agent injects real values from the customer secret store.
  • Entitlements from Aeon. MCCP does not run billing. The free-tier / plan / cap logic (today's FreeTierUsageRepo gate + Stripe) reads the customer's plan from YBM Aeon upstream — via OIDC claims or the Aeon billing API — and enforces caps against that. No money moves through MCCP.
  • New flags: -control-plane-mode, -agent-ca-cert, -agent-ca-key, -enrollment-token-key, plus the OIDC flags from §4. The -cognito-*, -stripe-*, and -crd-namespace flags are removed — human auth and billing move to Aeon, CR authoring moves to the agent.
  • Langfuse moves fully into the data plane. MCCP does not provision Langfuse and holds no admin key. Instance, Postgres, and provisioning (org/project/keys) all run in the customer cloud, created by the agent as ordinary desired state — it has local network access; MCCP does not. MCCP keeps only an optional project-id for console deep-links. Central Langfuse is a fallback only, for customers who explicitly accept traces leaving their cloud.

meko-provisioner — runs in the customer cluster

  • Reconcile logic is largely unchanged: it already creates per-tenant namespaces with mcp-server + rag-worker + config/secret + Service — exactly the data-plane unit.
  • Now installed by the agent in the customer cluster, not centrally.
  • The CR's YugabyteDBHost/Port/User/Password/Name already point at an arbitrary DB — in BYOC they point at the customer's own. Minimal change.
  • Add richer status conditions so the agent can relay accurate per-datapack phase back.
  • Add desired-version handling to drive rolling operator/image upgrades.

New: meko-agent binary + install chart

  • New Go binary in the monorepo; reuses the dynamic k8s client already written in api_server/internal/k8s/client.go.
  • Ships as a Helm chart in the meko-devops repo (where the existing deployment charts live), plus a single-command install script. The chart bundles the agent, the CRD, and the operator so a customer installs one thing.
  • Does: enroll, poll desired state, apply manifests (CRD, operator, ingress, secret scaffold), author MekoUserAccount CRs, report status, self-update.

Networking & secrets

  • All cross-plane traffic is customer→control-plane, outbound, over mTLS. The customer's egress allowlist needs only the control-plane FQDN.
  • MCP ingress stays in the customer cluster — the existing wildcard nginx proxy (meko-provisioner/config/proxy/) routes *.mcp.<customer-domain> to mcp-server.tenant-<id>. The control plane stores each environment's mcp_base_url.
  • Data-plane secrets are customer-owned. meko-shared-credentials and per-tenant secrets are populated from the customer's secret manager (installer prompts, External Secrets Operator, Vault, Sealed Secrets) — never shipped from the control plane.

09 Metrics & observability — Thanos

Observability flows outbound only, like everything else, and lands in Thanos on the cloud side. The split is clean:

PathHow it travelsWhere it lands
Time-series metrics In-cluster Prometheus scrapes MCP / RAG / operator / nodes → remote-write, outbound, mTLS Thanos Receive → object store → Thanos Query gives MCCP one global view. Customer's own Prometheus keeps a local copy.
Control signals POST /agent/status (§5) Fleet registry — heartbeat freshness, env state, reconcile lag, enrollment outcomes. Drives the §7 state machine.
Privacy line. Only counts, rates, latencies, and resource utilization leave the customer cloud — never memory text, embeddings, query contents, or PII. A metric label allowlist is enforced at the Prometheus remote-write egress (env id, datapack id, region, workload — nothing high-cardinality or user-derived).

What Thanos holds (per datapack / environment): MCP request rate, p50/p95 latency, error rate; RAG indexing throughput & queue depth; YugabyteDB connection health & slot utilization; workload CPU/mem vs. limits; token burn.

  • Reuse. meko_admin already serves a usage-metrics dashboard and a Token Burn efficiency tile through api_server. In BYOC it queries Thanos for the fleet aggregate instead of reading tenant databases directly (which now live in the customer cloud, unreachable from MCCP).

10 Executive dashboard — observability in the cloud

The metrics from §9 surface in MCCP as a true executive dashboard: one cloud view across the entire fleet, aimed at leadership and account owners rather than on-call engineers. It answers "how is Meko doing across every customer, right now and over time?" — without anyone touching a customer cluster.

  • Where it lives. Served by MCCP, rendered in meko_ui / meko_admin, behind Aeon OIDC (§4). Queries Thanos (§9) for the fleet aggregate and the fleet registry for state — never raw customer data.
  • Drill-down boundary. Trace-level detail (individual Langfuse traces, memory contents) stays in the customer cloud; the dashboard shows aggregates and links out to the in-cloud Observe UI.
  • Design. Summary tiles first, then trends; state encoded as color and label; every figure fleet-aggregated and privacy-safe.

12 Rollout phases

  1. Aeon OIDC auth — make the control plane an OIDC relying party of YBM Aeon; retire Cognito. Verify against both cloud and on-prem Aeon issuers.
  2. Fleet registry + agent API — add environments table and the three agent endpoints behind -control-plane-mode; no behavior change for SaaS.
  3. meko-agent MVP — enroll + poll + author CRs against a Meko-owned test cluster; package the install chart in meko-devops.
  4. Bootstrapping — attach mode — installer chart, attestation, smoke-check validation, health/heartbeat against an existing customer cluster.
  5. Bootstrapping — provision mode — meko bootstrap stands up a new K8s cluster (Aeon cluster API / eksctl / Terraform) then installs; live progress via bootstrap-progress.
  6. Observability + executive dashboard — in-cluster Prometheus remote-writes to a cloud Thanos; build the executive dashboard (§10) on Thanos Query; repoint meko_admin off tenant DBs.
  7. Customer secret custody — stop shipping YugabyteDBPassword in specs; agent injects from customer secret store.
  8. Langfuse in the data plane — agent provisions org/project/keys against the in-cloud Langfuse locally; MCCP drops all Langfuse admin access.
  9. GA — first external customer environment reaches READY.

13 Open questions

  • Upgrades: control-plane-driven (desired version) vs customer-approved maintenance windows? Enterprise customers usually want the latter.
  • Central-Langfuse fallback: is it worth supporting at all, or is in-cloud Langfuse a hard requirement for BYOC? The fallback reintroduces an MCCP→Langfuse path for those tenants and complicates the residency story (§3).
  • Break-glass: if an environment is DEGRADED and the customer needs help, what read-only diagnostic path exists without violating "no inbound access"? (Likely: agent-collected diagnostics pushed out on request.)
  • Multi-region / multi-cluster per account: one environment per cluster, or can one account span several READY environments with datapacks placed across them?
