# YCP PKI — one intermediate per data plane

**Status: CONSIDERED, NOT PURSUED (2026-09-21).** Kept as a decision record so the
proposal is not re-litigated from scratch; nothing here is built and nothing should be
built from it without revisiting the decision.

**What was chosen instead:** a self-signed root **per data plane** — which already
ships — with bring-your-own-CA for a customer who wants one anchor across their
environments. The reasoning is in
[`ac-compute-tls.md` § Why there is no shared root](../amp/controller/architecture/ac-compute-tls.md#why-there-is-no-shared-root-and-no-intermediate);
the short version is that a per-cluster root bounds the same blast radius by
construction rather than by `nameConstraints`, keeps root rotation on one customer's
schedule, and needs no control-plane PKI at all. The DNS zone is per data plane too,
so the per-environment trust anchor lines up with the per-environment address.

**What would reopen it:** environment *churn* making N roots a distribution chore
rather than one-time setup, or amp's own fleet tooling needing one trust anchor across
environments (cross-environment mTLS, fleet probes) — which bring-your-own-CA cannot
satisfy.

---

**Consumers, had it been built:** amp compute endpoint certificates
([`ac-compute-tls.md`](../amp/controller/architecture/ac-compute-tls.md)); meko later.
**Counter-case:** §[Why you might not want this](#why-you-might-not-want-this) — the
arguments the decision above rests on.

One self-signed root, held by the control plane. Each data plane holds an
intermediate signed by it, name-constrained to that environment's DNS zone, and
issues its own leaf certificates from it. Clients trust one root for the whole
fleet.

This replaces nothing: it is a *better-shaped issuer* for the `issue` mode that
already exists. A `ca` Issuer over the intermediate's Secret is what
`--deploy-compute-tls-issuer-name` already consumes, so no certificate consumer
changes.

## Why the key is generated in the data plane

The intermediate's private key is generated by the agent, in-cluster, and never
crosses the wire — the control plane sees a CSR and returns a certificate. The
alternative, minting the keypair centrally and shipping both halves, puts a CA
key in a request body, a log, and a TLS-terminating proxy's memory for no gain.

The consequence is the thing to be clear-eyed about: **that key then lives in a
Kubernetes Secret in a cluster the customer controls**, readable by anyone with
`get secret` in the namespace. `nameConstraints` is what stops it being useful
against another environment, so the constraint is a correctness requirement, not
a hardening nicety.

## The objects

```
control plane                          data plane (customer k8s)
─────────────                          ─────────────────────────
Root CA                                reconcile-agent
  self-signed, 10y                       owns the intermediate lifecycle
  key in KMS (or a Secret, for now)      │
  never leaves                           ├── Secret  amp-ica-tls
                                         │     tls.crt  the intermediate
POST /agent/pki/intermediate             │     tls.key  its key (generated here)
  signs, name-constrains, records        │     ca.crt   the root
                                         │
GET  /agent/pki/intermediate             ├── Issuer  amp-ca
  the current one, for a restart         │     ca: {secretName: amp-ica-tls}
                                         │
GET  /agent/pki/trust                    └── Certificate per endpoint
  the root bundle (two, mid-rotation)          → Secret yb-ep-<id>-compute-tls
```

The agent is already the sole YCP client for its environment and already holds a
YBM-minted key bound to one environment id, so a CSR on that channel is
authenticated by construction and needs no inbound reach
([`ARCHITECTURE.md`](ARCHITECTURE.md)).

## Bootstrap

```
agent                     YCP                      cert-manager        endpoint pod
  │                        │                            │                   │
  ├─ POST /agent/enroll ──►│  (existing, idempotent)     │                   │
  │◄──── environment id ───┤                             │                   │
  │                        │                             │                   │
  ├─ read Secret amp-ica-tls … absent                    │                   │
  ├─ generate ECDSA P-256 keypair (in memory)            │                   │
  ├─ build CSR  CN=env-<id>, self-signed                 │                   │
  │                        │                             │                   │
  ├─ POST /agent/pki/intermediate {csr} ─────────────────►│                   │
  │                        ├─ resolve env from key id     │                   │
  │                        ├─ verify CSR self-signature   │                   │
  │                        ├─ DISCARD requested extensions│                   │
  │                        ├─ sign: CA:TRUE pathlen:0,    │                   │
  │                        │        keyCertSign|cRLSign,  │                   │
  │                        │        nameConstraints(zone) │                   │
  │                        └─ record serial + SPKI + exp  │                   │
  │◄─ 200 {certificate, chain:[root], not_after, serial} ─┤                   │
  │                        │                             │                   │
  ├─ write Secret amp-ica-tls ──────────────────────────►│                   │
  ├─ ensure Issuer amp-ca ──────────────────────────────►│                   │
  │                        │                             ├─ issue leaf ──────►│
  │                        │                             │   Secret mounted   │
  │                        │                             │                    ├─ ssl = on
```

Five properties that are the design, not the implementation:

- **The CA decides the extensions, never the CSR.** A CSR's requested extensions
  are advisory; this one's are discarded outright and only the public key is
  taken. A data plane that asks for a wider constraint gets the same certificate
  it would have got anyway.
- **`pathlen:0`.** The intermediate cannot issue another CA. Without it a
  compromised data plane can mint a sub-CA and re-delegate.
- **`nameConstraints` are set from the environment's registered zone**, with
  excluded subtrees for the name forms this PKI never uses (IP, email, URI) —
  a permitted DNS subtree alone leaves the others unconstrained. Marked critical,
  so a verifier that does not understand the extension rejects the chain rather
  than ignoring it. This needs cert-manager ≥ 1.17 on the *consuming* side, where
  `NameConstraints` became beta and default-on.
- **Idempotent by public key.** A re-POST carrying the same SPKI returns the
  stored certificate and issues nothing; the agent re-posts on every startup and
  never accumulates intermediates. A *different* SPKI is a rotation — issued,
  recorded, and worth alerting on when unexpected.
- **Enrolment still mints nothing.** This is a separate call, so YCP's existing
  property ([`ARCHITECTURE.md`](ARCHITECTURE.md)) holds: a restart re-posts and
  gets the same answer.

### Ordering hazard

An endpoint with `computeTls.enabled` mounts a Secret cert-manager creates. If
the issuer is not Ready, that Secret does not exist and the pod sits in
`FailedMount` — it does not start without TLS, it does not start at all. So the
intermediate must converge **before** the first TLS endpoint is deployed. The
agent's PKI step therefore runs ahead of its endpoint reconcile, and the
controller should refuse a `computeTls` deploy while the issuer is not Ready
rather than producing a pod that cannot mount.

## Rotation

Three tiers, and they are not the same event. Only one of them can cause an
outage, and it is not the frequent one.

### Tier 1 — leaf, every 30–60 days, automatic

```
cert-manager ──renews──► Secret yb-ep-<id>-compute-tls
                              │  kubelet swaps ..data atomically
                              ▼
                        supervisor watcher (60s poll, compares contents)
                              │  SIGHUP
                              ▼
                        compute_ctl ──► pg_reload_conf()
                              │
                        open connections: untouched
                        next handshake:  new certificate
```

**No downtime.** No pod restart and no dropped connection — TLS material is read
at handshake, so a renewal cannot disturb a session in flight. This tier is
built and unit-tested today.

### Tier 2 — intermediate, yearly, automatic

The agent generates a new keypair, posts a new CSR, and rewrites
`amp-ica-tls`. cert-manager signs new leaves with the new intermediate.

**Existing leaves are not touched and do not break.** Their Secret still carries
the old chain, the old intermediate is still inside its own validity, and both
chain to the same root — so a client verifying to the root succeeds against
either. Leaves migrate as they renew. Forcing the migration is NOT an annotation —
cert-manager reissues on a spec change, `renewBefore`, or the `Issuing` condition
set by hand, and annotations trigger nothing (see
[`ac-compute-tls.md` §Not built](../amp/controller/architecture/ac-compute-tls.md#not-built)).
It would be `cmctl renew`, or the same controller-driven `Issuing` patch that
document defers.

**No downtime, under one constraint:** the old intermediate must outlive the last
leaf that chains to it.

```
   ICA-1  ├────────────────────────────────────────┤ notAfter
                      ICA-2  ├─────────────────────────────────────┤
   leaves ├──L1──┤├──L2──┤├──L3──┤├──L4──┤├──L5──┤
                          ▲                      ▲
                          rotate here            last leaf signed by ICA-1
                                                 expires — safely before
```

Rule: intermediate lifetime ≥ 2 × leaf lifetime, rotate at ≤ 50% of its life.
Violating it is the one way this tier bites: an intermediate that expires while
leaves still chain to it fails every `verify-full` client at once, and the
server looks healthy throughout.

### Tier 3 — root, rare, and the customer sets the pace

```
  a. generate root-2                            no client impact
  b. publish BOTH roots in the trust bundle     no client impact
  c. ── customers install the two-root bundle ──  UNBOUNDED, cannot be forced
  d. sign new intermediates from root-2         no client impact
  e. force leaf reissue → leaves chain to root-2
       │
       └─ any client that skipped (c) fails verify-full HERE
  f. retire root-1 from the bundle
```

**No server downtime at any step.** The risk is entirely client-side and it lands
at (e), silently, on whoever skipped (c). There is no server-side signal that (c)
is complete — which is why the root gets a 10-year life and why this tier is the
strongest argument against a fleet-wide root at all.

## Will there be downtime?

| Event | Pod restart | Connections dropped | Client must act |
|---|---|---|---|
| **Enabling `computeTls` the first time** | **Yes — one per endpoint** | **Yes, for that restart** | install the root |
| Leaf renewal (routine) | No | No | no |
| Intermediate rotation | No | No | no |
| Forced leaf reissue | No | No | no |
| Root rotation, steps a–d | No | No | **install the new bundle first** |
| Root rotation, step e | No | No | — (too late if they didn't) |
| Intermediate expires unrotated | No | No — but every `verify-full` client fails | no |

The first row is the only scheduled interruption, and it is unavoidable: a volume
mount is a pod spec change, and the endpoint Deployment is `Recreate` because an
endpoint is single-writer and a redeploy must not surge a second pod. Budget one
endpoint restart, once, at the deploy timeout. Everything after that is
hot-reloaded.

The last row is the one to alert on, because nothing else will tell you.

## Failure modes

| What happens | Effect | Recovery |
|---|---|---|
| Control plane unreachable at bootstrap | New TLS endpoints cannot become Ready; existing ones unaffected | Level-triggered — the next loop converges |
| Control plane unreachable at tier-2 renewal | Nothing, until the intermediate's `notAfter` | Alert at 25% remaining life |
| Agent's API key revoked | Cannot renew the intermediate | Re-register the environment with a fresh key |
| `amp-ica-tls` deleted | No new leaves; existing ones serve until their own renewal | Agent re-bootstraps with a *new* keypair on the next loop |
| Clock skew in the data plane | Leaves rejected as not-yet-valid | Outside this design's control; NTP |

## Revocation, honestly

There is none worth relying on. libpq checks no CRL unless the client passes
`sslcrl`/`sslcrldir`, and nothing here ships client configuration — so a CRL
would be published and unread. What actually bounds a compromised intermediate is
its own `notAfter` plus the `nameConstraints` that keep it inside one zone.

If revocation is later required it needs a distribution point clients can reach
*and* a documented client configuration, and it should be designed then rather
than half-built now.

## Why you might not want this

Recorded because the design was accepted over these, not in ignorance of them.

- **The key sits with the customer.** A Secret in their cluster, readable by
  their cluster-admins. It chains to a root every other customer's clients trust.
- **`nameConstraints` is the only thing making that safe**, and it is beta in
  cert-manager as of 1.17. A missed excluded subtree or a non-critical extension
  turns the mitigation decorative.
- **A per-cluster self-signed root — what exists today — has none of this
  coupling.** Compromise is one cluster and rotation is that customer's schedule.
- **Root compromise becomes a fleet event** requiring every client at every
  customer to install a new root, which you cannot force.
- **Central issuance reaches the same one-root property** with no signing key
  outside the control plane, at the cost of a CSR round trip per leaf. The
  offline-issuance advantage this design has over it is thin, because a data
  plane that cannot reach YCP is already not reconciling.
- **Bring-your-own-CA reaches it too**, for enterprises that already run an
  internal PKI — `TLS_ISSUER_NAME` / `TLS_CA_FILE` already exist and need nothing
  built.
