# Meko backend: web UI

A light UI for one person, on their own machine or, with remote access, from their other devices:
browse, edit and search a datapack (all sources or one), add memories and keep, promote or delete
several at once, upload and manage knowledge files, download artifacts, read conversations, see its
analytics, connect the agents on this computer (or copy the commands that connect any other), and manage the login. It calls the REST routes
and MCP tools in [api.md](api.md) and the sign-in routes below; the one data route it added is
`/usage`.

## Decisions

| Decision | Why |
|---|---|
| **Its own small app in `backend/web_ui`**, not Meko Cloud's web app: React, Vite, Tailwind and lucide-react, with Meko Cloud's colors | Cloud's web app is built for accounts, and most of it (billing, sharing, onboarding) has nothing to do on one machine. This one is about 100 KB gzipped, with four runtime dependencies; the fourth, `qrcode`, loads only when the account page draws a QR code. |
| **Served by the web listener (`[web] port`, 7777) from `web_ui/dist` on disk**, found as the memory engine is: `[web_ui] dir` (or `MEKO_WEB_UI_DIR`), else `<bin>/../web_ui/dist` | `go build` and `go test` don't need Node. Without a built UI, `/` says how to build one and the API is unchanged. The API listener (127.0.0.1:7778) doesn't serve the UI: it's for the CLI, MCP clients and AgentK, with their Bearer tokens, which the web listener never takes. |
| **Sign-in follows `[web] access`. `local`** (127.0.0.1, plain HTTP): **no login**, a request is let in when it's local by AgentK's loopback rule (a loopback peer, Host `localhost`, `127.0.0.1` or `[::1]`, no `Forwarded`, `X-Forwarded-*` or `X-Real-IP`, `Sec-Fetch-Site` `same-origin` or `none`, and its own Origin). **`remote`** (every address, HTTPS): **a password login, with optional two-step sign-in (TOTP)**, kept in the `meko_session` cookie (HttpOnly, SameSite=Strict, Secure). **`meko setup_link`** prints a link (`/setup?token=...`, one use, 7 days) that creates the login, or replaces it and turns TOTP off | On one's own computer a login only gets in the way, and the loopback rule keeps out another site's page and anything that came through a proxy. From other devices the page holds the user's memories and knowledge, so it takes a password, and the session lives in a cookie the page's script can't read, out of reach of injected script. The login is made and reset from the host's terminal, so only someone who can already run commands there can do either; there's no email reset. `meko ui` just opens the web URL. |
| **The page asks `/api/v1/auth/status` first**: the setup screen at `/setup?token=...` while remote access has no login (or a setup link waits; elsewhere, how to make one with `meko setup_link`), the sign-in screen at `/signin?next=<path>` while this browser isn't signed in (username and password, then a 6-digit code when the reply is `TOTP_REQUIRED`), else the app. A later 401 `UNAUTHORIZED` puts a remote browser back on sign-in and, with local access, says the request wasn't recognized as local | The UI's files load without a credential, so the page has to ask. A setup link's page keeps its address, since sending it to `/signin` would drop the token the form posts; while a reset link waits, the old login still signs in on every other page. After sign-in it goes to `next` only when that's a path on this site (it starts with `/`, not `//`), so a crafted link can't send a signed-in user elsewhere. With local access a 401 means something between the browser and Meko, such as a proxy, made the request look remote; the page says to use `meko ui` on the host, or set `[web] access = "remote"` in `config.toml` for a password. `RATE_LIMITED` replies show their message as it is. |
| **The web listener takes its own origin from a browser, and only it**, and sends no CORS headers | Another site's page can't call the API or read its replies, and its requests carry no session (SameSite=Strict). With local access the Host check also stops DNS rebinding. |
| **The UI's files need no credential**; catch-all `/api/*` and `/mcp/*` routes keep API paths off the UI's route | It's static and holds nothing secret. The credential check keys on the matched route alone, and an unknown API route stays a 401 without a credential and a 404 with one. |
| **Frames refused, `Content-Security-Policy` of `self`**, assets cached for good (their names are hashed) and `index.html` never | Another site can't frame the page to trick clicks on it, and a rebuilt UI loads at once. |
| **Search goes through `context_search` on `/mcp`** | There's no REST search route; the UI shows what an agent would get. Its calls are recorded as agent `meko_web_ui`, which the agent counts leave out. |
| **Search shows only memories at 0.40 cosine or above** (rounded to the two places shown), and every hit's cosine similarity | `context_search` applies no floor to memories, as Cloud's doesn't: an agent weighs them beside the other sources, and a floor costs recall on names and IDs. A person reading the list needs only the matches. With Meko's embedder, right answers measured 0.40 to 0.72 and unrelated memories 0.11 to 0.29; a 0.65 floor would drop most right answers. |
| **Overview leads with Cloud's three context tiles**: context size (tokens, KB · memory · conversations), context efficiency (% saved, ~sent vs ~baseline a search, a *live* badge once there are searches) and context quality (% of results that are relevant) | The numbers Meko Cloud's datapack page leads with. Efficiency and quality use Cloud's formulas; size counts with efficiency's weights (a chunk 1,000 tokens, a memory 200, a turn by its length), so the two tiles read against each other ([api.md](api.md#context-efficiency-and-quality)). `datapack_metrics` gives agents the same three. *Live* means measured from real searches, not polled. |
| **Metrics is Cloud's Analytics dashboard on the same `/metrics` payload and datapack counts**, plus a Usage section from `/usage` | The cards read what Cloud's read, so the two can't drift; Refresh reloads all three. Token counts are the context size tile's (`context_size` from `/metrics`). Usage (per-tool latency and errors, agents, the latest calls) is Meko's own: the call log already holds it. |
| **Metrics picks 7, 30 or 90 days** (`?days=` on `/metrics` and `/usage`); a recent call opens its steps' timings; **Status** reads `/api/v1/server` | Without `days`, `/metrics` keeps Cloud's windows for Cloud-shaped clients. `/api/v1/status` stays the CLI's (admin token); `/api/v1/server` gives the same reply to the web UI and the client token, since it describes nothing but the user's own install. |
| **Invite opens a banner pointing to Meko Cloud** (`cloud.mekodata.ai`) | Sharing needs the datapack in Cloud, so Meko has none; the button says where it lives instead of leaving the user to look for it. |
| **The sidebar's Extensions group**, under Status, starts collapsed on every load. Its label opens the Extensions page (`/extensions`); its chevron shows the installed extensions under it, each with a dot: a running one with a web UI is a plain link to it (`/ext/agentk/`, `/ext/presenter/`) that replaces the page, any other links to the Extensions page. AgentK and Presenter show their logos (`public/agentk-logo.png`, `public/presenter-logo.png`, bundled so they show while the extension is stopped), any other a puzzle piece; the Extensions page shows the same logo on each card | The web listener serves the extensions behind the same sign-in, so one login covers them all. Extensions refuse to be framed, so it's never shown inside Meko's page. The label and the chevron are two targets so that opening the page doesn't also open the group. |
| **While Meko Cloud is linked, the sidebar's datapacks are one list**: this Meko's first, each with a laptop instead of the database icon, then the linked Meko Cloud's (`/datapacks?location=cloud`; its 409 `CLOUD_NOT_LINKED` means unlinked, and so does a reply from a server older than the UI: a 404, or rows without `location: "cloud"`), newest first, each with a cloud, and a two-people icon at the end of one shared with the account. A Cloud row opens the datapack in Meko Cloud's web app in a new tab. After 50 Cloud rows a **Show all N** row shows the rest (and **Show fewer** hides them again, until the page reloads). The Cloud rows load beside the local ones, and a listing that failed is one note in their place, linking to Settings › Meko Cloud when the key was refused or the link has no API URL. They load again when Settings › Meko Cloud links or unlinks, and from the refresh beside **+**. While linked, **+** makes the datapack in Meko Cloud (`location: "cloud"`; Meko makes none on this computer then), says so in its dialog, and the new row shows among the Cloud rows; unlinked it makes one here (`location: "local"`). **A Find a datapack box** under the heading, linked or not, narrows both groups to the names that hold what's typed (ignoring case); while it holds a query, every matching Cloud row shows, with no Show all, and when nothing matches it says so (except while Meko Cloud's first listing loads, which may still bring matches, or in place of its failure note; a refresh matches against the rows it already has). × or Esc clears it | Once linked, AgentK and Presenter keep their new datapacks in Meko Cloud, so a list of only this Meko's would hide the user's current work. The UI browses only this Meko's datapacks, so a Cloud row never opens a local route; a Cloud datapack is browsed in Cloud's web app. The two-people icon is the one Meko Cloud's web app marks shared datapacks with. The cap keeps an account with hundreds of datapacks from making the sidebar endless; the route and the CLI still give every row. The box is Meko Cloud's sidebar's; it filters in the browser because both lists are already loaded, and a match is the row being looked for, so the cap doesn't hide it. |
| **The Extensions page** lists the installed extensions (registered with Meko, `extensions.json`) and the ones available to install, each with its description and state (and the release Meko installed, for Presenter), and **Install**, **Start**, **Stop** (asking first, since stopping AgentK ends its sessions), **Update** for an extension whose releases Meko installs (asking first: it restarts it; once done, the card shows the update's last line, such as "is running X" or "it runs at its next start"), shown only while its last check found a newer release that wasn't rolled back (`update_available`) or while an update runs, and **Open**. An action runs on the server as the extension's job ([web.md](web.md)), and a start or an install lasts until the extension answers; the page polls the list every 2 s while one runs, shows its output, and shows the error and output when it fails. An AgentK installed by its own installer shows as available: Install registers it, re-running its `install` with Meko's URL and token | "Installed" is the test the web listener serves an extension by, so the page never offers an Open that can't work. The sidebar and the page share the list (`lib/extensions.ts`) and reload each other when an action starts or ends. |
| **Works on a phone**: below `md` the sidebar is a drawer opened from a top bar (closed on every navigation, and hidden from the tab order while closed); the datapack header's actions go icon-only and its tabs, like segmented options, scroll sideways; dialogs fit the screen and scroll; inputs are 16px | Remote access means the UI is opened from a phone. iOS zooms the page into any input under 16px. The sidebar's dialogs render outside it, because its slide-in transform would otherwise trap them inside it. |
| **Status is the sidebar's first link**, with a dot for the memory engine's state (polled every 30 s); pages render inside an error boundary | It's where someone looks when something seems off. A page that throws (as against a server older than the UI, between a rebuild and a restart) says so and suggests `meko restart` instead of going blank. |
| **Status has an Updates card**: the running version, the newest release the server found (with its release notes), when it last checked and why a check failed, **Check now** and **Update to X**. While it installs, the card polls `/api/v1/update`; once Meko stops to restart (the job's restarting step, or a poll that fails while it installs a version, since Meko stops at once), it polls `/healthz` and reloads the page when the version changed, or when Meko answers again after it stopped answering (a rollback brings back the old version); after 3 minutes it says Meko hasn't come back. The version it asked for is kept in `sessionStorage`, so after the reload it says whether the update worked, was rolled back (`rolled_back`, from `bad-versions`) or didn't start. A build from source says it doesn't update itself. **The sidebar's version gets an Update chip** to Status while a newer release is out (read every 30 minutes) | Without it, a server the service doesn't run with `[update] auto` only reports updates, and installing one needs `meko update` in a terminal. The new web UI comes with the new binary, so the page must reload into it. The Status page keeps showing while a refresh fails, so the card can wait out the restart. |
| **Settings is a page (`/settings`), linked under Status and Extensions in the sidebar**: switches for **Memory extraction** and **Search answers** under "Uses your Claude Code" (each turned on after the server's test call, with a note while it runs and the error when it fails; extraction's line shows the model, interval, waiting turns and last run), **Usage stats** (`/settings/usage-stats`), and links to the Meko Cloud link and the account settings. Every switch saves as soon as it's flipped | The two features spend the user's Claude quota, so they're opt-in, and a switch is easier to find than a command; the server finds Claude Code itself, as it does for the Agents card, so the browser never names a program. When `config.toml` or the environment turned [usage stats](callhome.md) off, its switch is off and disabled and says which. |
| **The Meko Cloud link at `/settings/meko-cloud`** (from Settings, and AgentK's Settings › General): its state, the API key (never shown; its last four characters), Sign up and Log in links to the web app that goes with the MCP URL as it's typed (`lib/mekourls.ts`, worked out as the server does) with Meko Cloud's Settings URL to copy, and under *Your own Meko server* the MCP, web app and API URLs; **Check and link** (or save), with a second press to confirm a switch to another host, and **Unlink** after a confirmation | The link is Meko's, for every extension ([cloud.md](cloud.md)). Switching hosts leaves existing projects' datapacks on the old one, so it's confirmed. The server checks and refuses; the page shows its message. After a link or unlink, one line says which agents it moved (to Meko Cloud, or back to this Meko) and which it couldn't, with why (the reply's `agents`); nothing when it moved none, or from an older server. |
| **The Connect page's Agents card**: the agents installed on this computer (`GET /agents`), that they connect to Meko on this computer, which sends their calls to Meko Cloud while it's linked, and each one's state: Connected, Needs reconnecting (a meko server on this computer that isn't exactly the target), Connected elsewhere with its URL, or Not connected; with **Connect** for any not connected and **Disconnect** for a connected or stale one, then the list read again. Under the agent go its notes, the reply's, a reminder that running sessions need a restart, or Meko's error. With none installed it names the agents Meko works with; a server without the route (a 404) shows no card | Meko owns the agent connections ([api.md](api.md)), so one press does what `meko agent connect` does, without a terminal. Connect replaces a meko server that points elsewhere and the reply says so; Disconnect is offered only for Meko's own. Nothing polls: the list is read when the page opens and after each press. |
| **Account settings at `/account`** (from Settings, and AgentK's Settings): change the password (current, new and confirmed, 12 characters or more); two-step sign-in, turned on by scanning a QR code of the `otpauth://` URL (its key also shown as text) and typing a code, and off with a code; and Sign out (`/auth/logout`, then `/signin`). Shown when access is remote or a login exists | One place for the login, which both Meko's and AgentK's pages sit behind. The QR code is drawn in the browser, so the secret goes nowhere but this page. With local access and no login it says none is needed on this computer, and that `[web] access = "remote"` in `config.toml` turns on the login `meko setup_link` creates. |
| **Each conversation turn has a decision trace**: what the agent looked up, its reasoning and plan, and what it saved, each call opening its step timings | The call log already records every call's conversation, result counts and steps, and the turn stores the reasoning and plan the agent sent, so no new data is collected. Lookups and actions are grouped by each tool's own read-only flag. The reasoning and plan are only as good as what the agent sends. The calls go back to the conversation's start (an earlier conversation under the same id doesn't leak in) and include calls that failed before their datapack was known; the call log keeps 90 days, so an older turn says its calls may be gone. |
| **Overview leads with the collective-learning ribbon** (conversations → memories → learnings → collective memory, each opening its tab); **Knowledge** ends with its activity log (uploads with their chunks, promotions); collective memories can be deleted | As Cloud's datapack page shows them, from routes Meko already serves (the datapack's counts, `activity-log`, `DELETE /promoted-memories/:id`). |
| **A new datapack's Overview starts with "Get started"** (connect an agent, add a memory, upload a file, run a search), each ticked from the datapack's counts and gone for good once all are done; **`/` jumps to Search** from anywhere outside a field or a dialog (from Status, to the first datapack's), and Esc closes dialogs | Meko Cloud's datapack page shows the same first steps. The agent and search steps come from the call log, which forgets after 90 days, so the browser remembers a datapack that got started rather than showing the card again. |
| **Memories are just memories for now** (`SHOW_COLLECTIVE` in `lib/features.ts`): no Learnings or Collective scope, no Keep or Promote, no learnings or collective counts on Overview, no collective-learning ribbon or memory breakdown on Metrics, no promotions in the knowledge activity log, no "promoted memory" badge in Search, one color on the map, and a turn's trace tags what it saw just "memory" | A new memory is a learning until it's kept (reviewed) or promoted to the collective memory every agent finds through the knowledge base. Meko local has one user on one laptop, so neither step has a benefit there. The server still serves and exports all of it, so one line brings the UI back. |
| **The Memories tab's Graph view draws its scope's memories by meaning, and Search's Graph view shows where a question lands among everything it searched** (`/memory-map`, `/search-map`; List or Graph, remembered in the browser per page, on every Search source): the Memories map is one dot per memory, alike ones close and linked; Search's is the 100 memories, knowledge-base chunks and conversation turns nearest the question, colored by source (the legend hides or shows each), with the question as a star and lines to what the search returned, listed beside with their scores. A dot hovered or focused shows its score above it. A click only picks a dot: the map can't be selected or take a focus outline, which browsers paint over it. **2D or 3D** (remembered in the browser): 3D adds the third main direction as depth, nearer dots larger and bolder, drawn far to near; it turns slowly until touched (not at all with reduced motion) and a drag turns it | Plain SVG, no chart library, 3D included: a few hundred dots rotate cheaply in JavaScript, where a WebGL library would add its weight and replace the click, hover and legend code. Depth is stretched to the map's spread, since the third direction varies less and would draw nearly flat; 2D stays the default, as 3D is harder to read when still. The projection runs on the server, which holds the vectors; all three sources share one embedding model, so one map places them. 100 nearest, not the whole datapack, keeps Search's map readable however large the datapack, and drawing a turn once (at its nearest chunk) keeps a long turn from being several dots. Search lights what its own results list, so List and Graph show the same matches; the question lives in one place, Search, rather than a second box on Memories. A turn's decision trace draws the same map small, lighting the memories its searches returned (the ids the call log records for each memory search). |
| **Overview's counts open their tabs** (memories, knowledge files, conversations, artifacts; searches and agents open Metrics), as real links; **a memory's "where it came from" opens its conversation at the turn it came from**, scrolled to, ringed with a brief pulse and labeled | A count invites a click, and a conversation can be long: the link carries the turn as the address's `#fragment`, so the page can point at it and the link still works pasted elsewhere. |
| **Search writes an answer above its results when answers are on** (`meko answers use claude`): the user's own Claude Code reads up to 10 of them, taken in turn from each source, and answers citing them as [n], each listed below with its source; off, a line links to Settings and names the command | An answer from what the search found, without a model to download: the same reasoning as memory extraction ([memory-extraction.md](memory-extraction.md#search-answers)). |
| **Overview warns while memory extraction is off** (a reusable `Banner`, which the Invite notice uses too), linking to Settings, with `meko memory-extractor use claude` to copy; closing it lasts until the datapack has more conversations, and it's hidden for a datapack that opted out. **Status** has a Memory extraction card (the tool, the interval, what waits, the last run and error, or a link to Settings while off); an extracted memory is tagged **extracted** | Extraction runs through the user's own AI tool ([memory-extraction.md](memory-extraction.md)), turned on in Settings or the CLI. |
| **Each memory has an Origin**: who saved it and during which conversation turn (or directly, with `memory_add`), each update with its old and new text, and, where the page knows it (the Learnings scope and the graph), whether it's a learning, kept or collective, a step hidden while `SHOW_COLLECTIVE` is off | Its conversation comes from the memory's `conversation_id`. An extracted memory names its turn (`message_id`), and the dialog says Meko extracted it from that turn; any other memory's turn is the first one stored at or after it, since an agent saves memories before the turn they belong to; with none (not stored yet, or past the 100 turns loaded), no turn is quoted. mem0 already records every change in `memory_history`; `GET /memories/:id/history` reads it, so an agent's edits (`memory_update`) can be seen and checked. A collective memory shows no history, because the route doesn't serve a promoted one. It takes the same ownership check as reading the memory: history rows don't say whose a memory was, so a deleted one's history isn't served. |
| **Export downloads the datapack as a zip** (the header's Export), the same file as `meko-cli export` | Everything in it, ids and dates kept, with embeddings, knowledge-file and artifact contents, and the call log; groundwork for moving a datapack to Meko Cloud. The page fetches it with its own credential (the session cookie, or none with local access), then saves it. |
| **Uploads use Cloud's presigned flow** (`upload-url`, then the multipart POST), hashing the file in the browser | The same path AgentK and Cloud's web app take, so nothing new is trusted. |

## Develop

```sh
cd backend
make web_ui                      # npm ci when the lockfile changes, then web_ui/dist
./bin/meko start && ./bin/meko ui
cd web_ui && npm run dev         # Vite on :5178, proxying the API to MEKO_URL (default http://127.0.0.1:7777)
```

With `npm run dev`, open `http://localhost:5178/`. The proxy sends Meko's web listener its own Host
and origin, so with local access the page needs no token and no login.
