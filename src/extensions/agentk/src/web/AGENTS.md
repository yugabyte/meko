## Every UI change works on a phone

People drive sessions from their phones, so a change isn't done until it works at 390 px wide
with a finger. Before you finish a UI change:

- **Check it at phone width.** Open it in device emulation (a 390×844 phone, with touch on) as
  well as on the desktop, in both light and dark themes. Nothing may scroll sideways except code,
  diffs and wide tables inside their own `overflow-x: auto` box.
- **Use the existing breakpoints.** The phone layout is `@media (max-width: 760px)`; in code,
  `useIsMobile()` from `hooks/useMedia.ts` (`MOBILE_QUERY`). Touch sizing is `(pointer: coarse)` /
  `useTouch()`, and hover-only affordances need a `(hover: none)` fallback. Don't add new
  breakpoints; if you really need one, add it to `hooks/useMedia.ts` so CSS and code agree.
- **Prefer CSS over separate markup.** Restyle in the phone section at the end of `styles.css`.
  Render different markup only where the structure really differs (the app bar, the ⋯ sheet, the
  terminal key bar), and gate it on `useIsMobile()` / `useTouch()`.
- **Where do new controls go on a phone?** A new session action goes in `sessionActions()`
  (`src/web/sessionactions.ts`), tagged with where it shows: the desktop ⋯ menu, the phone's ⋯ sheet
  and the palette all read that list. Only what needs the user stays in view in the desktop stage
  bar, and anything there also needs to reach the phone, which renders the stage bar only inside the
  sheet and shortens the footer. A new project-level action belongs in the drawer (`Rail.tsx`).
- **Touch targets** are at least 36 px tall (40 px for icon buttons), except the rail's code
  review box (`.rail-review`), kept 13 px tall so a task's row stays short. Don't rely on hover,
  right-click, Shift/⌘-click, drag and drop, or keyboard shortcuts alone; give each one a tap
  equivalent. Tooltips (`title`) aren't seen on touch, so don't hide needed information in them.
- **Text inputs are 16 px or larger on phones**, or iOS zooms in on focus. The phone section
  already covers `.input`, `textarea` and `select`; add any new input class there. `html` sets
  `text-size-adjust: 100%`, so iOS never enlarges small text on its own (it did to a diff's rows as
  files scrolled back into view); text is the size the CSS gives it.
- **The keyboard comes up only when a field is tapped.** On touch (`useTouch()`), opening a dialog,
  menu or picker doesn't focus a text field: write `autoFocus={!touch}`. `Dialog` focuses only an
  enabled `button.primary` there, or else the dialog itself, so focus never stays on the terminal
  behind it. The exception is a view opened in order to type, which still focuses its field: the
  command palette, the sign-in screens, the Changes panel's comment editor, and the Other / custom
  answer boxes in `AskSheet.tsx` and `DesignQuestions.tsx`.
- **Heights follow the keyboard.** Size full-height views with `var(--app-h, 100dvh)` in the phone
  section, never a bare `100vh`, so the on-screen keyboard shrinks the view instead of covering it.
  A fixed layer over the whole screen takes `top: var(--app-top, 0px)` and `height: var(--app-h, 100dvh)`
  there, not `inset: 0`: iOS doesn't shrink the layout viewport, so its bottom is behind the keyboard.
  Things pinned to the top or bottom edge pad themselves with `env(safe-area-inset-*)`.
- **Dialogs** use `Dialog` from `common.tsx`, which is already a bottom sheet on phones, and whose
  Ctrl+Enter presses the main button (`submitButton()`): make it the `btn primary` in the footer or
  its form's submit, or, outside a form and footer, a `btn primary` marked `data-submit`. A field that
  takes Enter itself prevents its default, and the dialog leaves it alone. New bottom menus use
  `Sheet` from `SessionSheet.tsx`, which brings a × at its top right, as `Dialog` does.
- **The terminal** takes touch input through `terminals.ts` (`sendKey`, `submit`, swipe scrolling)
  and the pure helpers in `keys.ts`, which have unit tests. Don't focus the terminal on touch
  screens unless typing mode is on (`term.typing`), or the keyboard pops up on every tap.

## In-progress labels

A label for something still running ("Starting", "Opening", "Loading") is `<Busy label="Starting" />`
from `common.tsx`, never a static "Starting…", which looks stuck. Its dots (`Dots`) are three
keycaps that play a tune (`TUNE` in `typing.ts`, as `[key, beats]` pairs) with the Web Animations
API, from its first note whenever a label appears (`transform` and `box-shadow` only, so the width
never changes), and stay still with reduced motion.
`test/unit/busy-labels.test.ts` flags a static label like "Saving…" in a component.

## Keys: checkboxes and buttons

Checkboxes and buttons are drawn as keycaps, like the busy dots' keys: a key stands on an edge
(a `box-shadow`), sinks when pressed (a `transform`), and stays down while it's on. A press goes
straight to the on depth, so a press that checks a box or turns a toggle on is one move, and while
a key is down a transparent `::before` covers the 2 px above it, the spot it left, so a press near
its top edge doesn't slide it out from under the pointer (the hover flickered, and the click was
lost). Each key's state reads by shape as well as color.

- **Checkboxes:** every `<input type="checkbox">`, standing up when off, down and lit with a tick
  when checked. It's the native input restyled in `styles.css`
  (`:where(input[type='checkbox']:not(.prose *))`), so a new checkbox needs no class or component,
  and labels, Space and screen readers work as they always did. The base rule is wrapped in
  `:where()`, so it has no specificity and a context's own rule (`.check input`) places the key;
  the state rules (`:checked`, and `:hover` and `:active` on an unchecked key only) weigh their
  pseudo-classes, more than `.check input`, so a context rule mustn't set the key's border, fill,
  edge or transform. Task lists in rendered markdown (`.prose`) keep the browser's box. Radio
  buttons aren't restyled.
- **Buttons:** `.btn` (every variant but `.ghost`, which stays flat) and the stage bar's `.gate`.
  Each variant sets only `--key-edge`, the edge's color; a toggle that's on (`.btn.on`, or
  `aria-pressed="true"`) stays down, unless it's a ghost, which takes the on colors but stays flat. `.btn` and `.gate` are `position: relative` for the hit area,
  so a context rule mustn't set their `box-shadow`, `transform` or `position`. Icon buttons, link
  buttons, `.seg` segments, tabs and the rail's rows stay flat. The edge is outside the button's
  box, so a box that clips (a scroll box) needs 2 px of room under a button at its bottom, as
  `.stages` has for the gate.

Forced-colors mode brings the checkbox's native box back and holds every key still: it resets each
rule that moves one with that rule's own selector. Transitions run only without reduced motion.
`test/unit/keycap-style.test.ts` checks that keys are shaped by state, move once to the on depth,
keep their hit area while down, and are still under reduced motion and forced colors.

## Reloads after an update

An open page reloads itself when the server comes back on another version (`reload.ts`), unless
the user is busy: a `role="dialog"` element is open, a text field has focus, a `textarea` holds
text, or a session's terminal holds images for Claude (`hasHeldImages()`, checked in
`useReload.ts`, since terminals outlast their pane). A field whose text survives a reload (kept in `sessionStorage`, like the terminal compose box)
gets `data-reload-safe` so it doesn't hold the reload up. Text kept anywhere else in a field that
isn't a focused input or a textarea is lost on the reload, so keep drafts that matter in a
textarea, a dialog, or storage.

## Checking it

`npm run dev` serves the UI on :5173, at `/`, and passes `/api/`, `/healthz` and `/ws/` to the dev
server's unix socket (`vite.config.ts`; `AK_DEV_SOCK` names another). Use your browser's device
toolbar with touch emulation. Behind Meko the UI is at `/ext/agentk/`, so a URL that skips `appUrl()`
or `routePath()` breaks only there. For a real phone, open the installed Meko's HTTPS address.
