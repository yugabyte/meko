# AGENTS.md: the server

The modules under `src/server/`: the server, the session host (`host/`) and the CLI. Kode's
guide, with the invariants every change here keeps, is [../../AGENTS.md](../../AGENTS.md).

## Map

| Path | What it is |
|---|---|
| `src/server/cli.ts` | Entry point: `serve` (which first lets a move of the home under way finish, or does one itself without services: `moveFirst`), `stop`, `start`, `restart` (the server's service only, which Meko runs after an update: `restartServer` in `health.ts`), `host` (`host stop`, `host restart`), `attach`, `install`, `uninstall`, `status`, `ui` (through Meko), `logs`, `selftest`, `version` (`--json`, which Meko checks a release with), the hidden `_move-home` the move's job runs and `_handoff` Meko runs (`handoff.ts`), and `mcp` (unlisted: the session tools' MCP server, which sessions start as `mcpmain.js`). Run by `meko start` and `meko stop` (`MEKO_SUMMARY=1`), `start` and `stop` print one row of Meko's summary, and run by `meko status` so, `status` prints only its headline. |
| `src/server/statusview.ts` | `status`'s output (`formatStatus`), from what `cli.ts` found, laid out as `meko status` (Meko's `report.go`): a row each for the server, the session host and the services, a `●` headline, the links as plain rows, and `Next:`, colored by Meko's roles (`Paint`); and `headline`, the one line always marked ✓, ! or ✗ that `status` prints alone under `MEKO_SUMMARY=1`, which `meko status` shows in its own row without the mark and the title, and first off a terminal (a Meko from before `MEKO_SUMMARY` on status reads the first line, and would take a row's mark for Kode's). The uptime from `/healthz`'s `startedAt`, as Go writes a duration (`upFor`). |
| `src/server/summary.ts` | That row: Meko's format (`  ✓ Kode            started`), colored (bold yellow for `!`) only on a terminal without `NO_COLOR` and with `TERM` not `dumb` (Meko's `docs/install.md`, "The summary rows"), and what the stop row says (`stopRowText`: where the sessions resume, `meko start`, or `meko kode serve` without services). |
| `src/server/core.ts` | Wires config, db, the session host, Meko and the services (refusing to start while a tmux-era version's service is installed, unless the host service is too and none of this home's sessions is in tmux); timers; `state()` snapshot for the UI; the terminal colors sessions start with (`termTheme`, kv `term-theme`). |
| `src/server/server.ts` | Fastify routes, origin checks (no login: Meko decides who gets in), WebSockets (`/ws/events`, `/ws/term/:id`), static files, and the page stamped with its `<base href>` and version (`stampPage`): the base is the path Meko served the page under, from `X-Meko-Prefix` (`/ext/kode/`), else `/ext/agentk/`, where a Meko from before Kode was called Kode serves it (`pageBase`). The server listens only on `Paths.webSock` (`cli.ts`, with `listenPrivate` from `hooks.ts`). |
| `src/server/sessions.ts` | Session lifecycle in the session host: create (`begin` answers once the row is in; the worktree and launch follow, and a worktree that can't be made is a failed start; a task on an existing branch or an open PR, a fork's included, works on that branch as it is; a learn session, `CreateSessionRequest.learn`, is a task at Explore marked `purpose = 'learn'` on the `seed` prompt; a workshop's host, `begin`'s `own.purpose`, one marked `guide` on its bundled script), launch (through the session's harness adapter, `src/server/harness/`; hook payloads normalized by it), hook-driven status (a turn's end: `Stop`, or one the mod reports interrupted, `endTurn`; what it left running in the background, `background_tasks`, for `Session.background`), submitting prompts (through Kode's mod while it's live, else typed into the terminal; one Claude exits before starting is reported to its sender) and the agent's own commands that start no turn (`command`: Kiro's `/clear` and `/model` in a code review), recovery and auto-continue, stopping agents idle past `[sessions] idle_stop_hours` and starting them again when something needs them (`stopIdle`, `awake`, `wakeSoon`; [recovery.md](../../docs/design/recovery.md#stopping-idle-agents)), archive. |
| `src/server/lifecycle.ts` | Stages and gates, moves by hand between stages, the user's instructions sent with a move or Open PR (`checkInstructions`), GitHub polling, the review watchers (by reviewer mode: straight to Claude, or held for the user, and the user's send or dismiss, `decideHeldReviews`), the merge-conflict watcher (`[pr] resolve_conflicts`, also in Settings → General) and CI-fix watcher with their prompt queue (which also carries the fix and push prompts of a code review the user ran, `local-review`, in Pull Request and in Code, sent again when Claude lost one), a PR prompt Claude exited before taking, sent again once it's back (`prLost`, `claudeBack`), queued gates (Open PR after this turn, with its instructions, Merge when ready: `sessions.queued_gate`, `queued_instructions`), Run to merge (`sessions.auto_run`: `setAutoRun`, Open PR queued at each Code turn's start, `onTurnStart`, and a merge that stays queued through any blocker, `armMerge`, `autoRunWaits`, stopped by an uncheck, a Cancel, an interrupt or a move, `stopAutoRun`), Merge & Close (merge, then cleanup), no PR in a workshop's project (`checkOpensPr`: Open PR, Run to merge and a move to Pull Request refused), closing a learn session once Claude wrote its summary (`learnDone`), and a Review a PR session's watch on its PR (new commits, merged or closed) and Update to latest. |
| `src/server/heldreviews.ts` | Reviews held for the user (`held_reviews`): where a review goes in each reviewer mode (`reviewRoute`, the one place that decides), keeping a held review with its inline comments, the list and count the UI shows, marking reviews sent or dismissed, the merge blocker while any are held, and the `review-held` prompt's lines. Polling and sending are in `lifecycle.ts`; the details come from `github.reviewDetails`. |
| `src/server/prreview.ts` | Review a PR and sharing with reviewers: the PRs a review can start on (found on GitHub by the project's datapack ids, in any repo, each matched to a local clone, a fork first), cloning a PR's repo, and who reviews the project's open PRs (with emails remembered per GitHub login). A review's create path (fetching `refs/pull/<n>/head`, a review branch with no upstream) is in `sessions.ts`, its git helpers in `git.ts`. |
| `src/server/ghlinks.ts` | Starting from a GitHub PR or issue pasted into Ask Kode (`GET /api/github-link`, `POST /api/github-link/start`): reading it (`issueOrPr()` in `github.ts`, one call for both), the project it belongs to (a datapack its description's Meko line names, else the one on screen if it's on its repo, else the first on it; the repo's other projects are offered too) or the one to open (its datapack: the named one, reopening a closed project with it, else none for a PR and a new one for an issue), the clone to work in, and the session (a review, or a task from the issue's prompt). The palette's side is `linkEntries()` in `src/web/palette.ts`; the ref parser is `src/shared/github-refs.ts`. |
| `src/server/askagentk.ts` | Ask Kode (`POST /api/ask-kode`): an instruction in plain words from the command palette, answered by one call to the default agent with no tools, MCP servers or hooks, as its adapter's `Asker` says (`claudeAsker`: `claude -p`, `askArgs()`; `kiroAsker`: `kiroAskArgs()`, the `kode-ask` workspace agent and `readKiroAnswer()`; `openCodeAsker`: `openCodeAskArgs()`, the `kode-ask` agent in a global config of the ask's own in place of the user's, `XDG_CONFIG_HOME`, so their plugins and MCP servers don't run, and `readOpenCodeAnswer()`; an ask's Kiro or OpenCode session is deleted whether or not it answered), the message (projects, running sessions, what's on screen, the exchange so far) on stdin; reading its JSON answer and errors (`readAnswer()`), checking the proposed actions against the state (`checkActions()` in `actions.ts`) and whether they're the steps of one instruction (`together`, for Do all), each project's GitHub repo in the message (`withGithub`), two asks at a time, and counting asks for the usage report (`agentk_asks`). The palette's side is `askEntries()` in `src/web/palette.ts` and `CommandPalette.tsx`, which runs the picked action through the routes the UI already uses. |
| `src/server/actions.ts` | The actions Ask Kode proposes and Kode's session tools take (`start`, `link`, `go`, `move`, `openPr`, `openProject`): checking them against the state (`checkActions()`, at most `ACTIONS_MAX`), running them in order through the core calls the UI's routes make (`runActions()`: Do all's `POST /api/actions/run` and the tools; a `tools` event on the calling session and the one it changed), opening a project for one, and the session tools' side of a call (`SessionTools.call`, the hook socket's `/tools`: refused while `[tools] enabled` is off or from a PR head `repoConfigTrusted()` doesn't trust; no Open PR on the caller; the caller's own move held for its turn's end, `turnEnded`; calls still running answered when the hook socket closes, `pause`). See [docs/design/tools.md](../../docs/design/tools.md). |
| `src/server/tools.ts`, `tooldefs.ts` | The session tools' files each harness launches with (`writeToolFiles` into `run/tools/`: Claude Code's `--mcp-config` file and the hook-less skill plugin, the skill's copy Kiro and OpenCode read; `toolsReady`), how a session's CLI starts the MCP server (`toolsCommand`: `app/current`'s Node on `mcpmain.js`, or a dev server's Node with its loader flags), Kiro's `mcpServers` entry and OpenCode's part of a session's config (`openCodeTools`); and in `tooldefs.ts` (no imports, so the MCP server loads nothing else) the tools' names, descriptions and input schemas, and the read-only ones each harness allows. |
| `src/server/mcp.ts`, `mcpmain.ts` | `me_kode mcp`: the session tools as a stdio MCP server, MCP's few messages spoken directly (no SDK: its schemas cost about 30 MB per session), each call forwarded to the hook socket's `/tools` with `KODE_HOOK_SOCK` and `KODE_HOOK_TOKEN` from the session's environment. `mcpmain.ts` is the entry sessions start, without the CLI's imports. |
| `src/server/workqueue.ts`, `slack.ts` | The work queue (`work_items`, `work_item_links`; [docs/design/work-queue.md](../../docs/design/work-queue.md)): items, their links by `parseWorkLink` key (`src/shared/worklinks.ts`), order, one session per item (`setItemSession`, the only writer; `checkStartItem` for `CreateSessionRequest.workItemId`, linked in `begin()`'s transaction; `soleItemFor` for a session started from a pasted link in `ghlinks.ts`), Dismiss all (`closeAll`), the palette's lookup by link (`byLink`), and the sync (Sync, and `tick()` every minute against `[work_queue] sync_minutes`; each source only while `[work_queue] github` or `slack` is on, both off by default, Settings › Work queue): GitHub review requests (`reviewRequests()` in `github.ts`, Done on GitHub when gone) and the user's Slack list (`slack.ts`: `[work_queue] slack_list`, read with the connector's `slack_read_file`; one `claude -p` with the user's own connectors but none of their settings beyond sign-in (`signInSettings`), no built-in tools but ToolSearch (which waits for the connector), the default permission mode, only `[work_queue] slack_tools` allowed and Slack's writes denied, read on the timer only while the last read worked, `work-slack-auto`), each source on its own, never re-adding a link any item has. |
| `src/server/sessionsearch.ts` | Finding a session by what it's about (`GET /api/sessions/search`): the words of the text, each session's name, PR, task, branch and design read from `state.db` (archived sessions included), and the ranking (`rankSessions()`).
