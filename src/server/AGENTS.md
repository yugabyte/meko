# AGENTS.md: the server

The modules under `src/server/`: the server, the session host (`host/`) and the CLI. The repo-wide
guide, with the invariants every change here keeps, is [../../AGENTS.md](../../AGENTS.md).

## Map

| Path | What it is |
|---|---|
| `src/server/cli.ts` | Entry point: `serve`, `host` (`host stop`, `host restart`, and `host retire` for the launcher's rollback), `attach`, `install`, `uninstall`, `setup-link`, `status`, `logs`, `selftest`, `version`. |
| `src/server/core.ts` | Wires config, db, the session host, Meko and the services (adding the host service for a server that updated itself); timers; `state()` snapshot for the UI. |
| `src/server/server.ts` | Fastify routes, auth hook, origin checks, WebSockets (`/ws/events`, `/ws/term/:id`), static files. |
| `src/server/sessions.ts` | Session lifecycle in the session host: create (`begin` answers once the row is in; the worktree and launch follow, and a worktree that can't be made is a failed start; a task on an existing branch or an open PR, a fork's included, works on that branch as it is), launch (through the session's harness adapter, `src/server/harness/`; hook payloads normalized by it), hook-driven status (a turn's end: `Stop`, or one the mod reports interrupted, `endTurn`), submitting prompts (through AgentK's mod while it's live, else typed into the terminal), recovery and auto-continue, archive. |
| `src/server/lifecycle.ts` | Stages and gates, moves by hand between stages, the user's instructions sent with a move or Open PR (`checkInstructions`), GitHub polling, the review watchers (by reviewer mode: straight to Claude, or held for the user, and the user's send or dismiss, `decideHeldReviews`), the merge-conflict watcher (`[pr] resolve_conflicts`, also in Settings → General) and CI-fix watcher with their prompt queue, queued gates (Open PR after this turn, with its instructions, Merge when ready: `sessions.queued_gate`, `queued_instructions`), Merge & Close (merge, then cleanup), and a Review a PR session's watch on its PR (new commits, merged or closed) and Update to latest. |
| `src/server/heldreviews.ts` | Reviews held for the user (`held_reviews`): where a review goes in each reviewer mode (`reviewRoute`, the one place that decides), keeping a held review with its inline comments, the list and count the UI shows, marking reviews sent or dismissed, the merge blocker while any are held, and the `review-held` prompt's lines. Polling and sending are in `lifecycle.ts`; the details come from `github.reviewDetails`. |
| `src/server/prreview.ts` | Review a PR and sharing with reviewers: the PRs a review can start on (found on GitHub by the project's datapack ids, in any repo, each matched to a local clone, a fork first), cloning a PR's repo, and who reviews the project's open PRs (with emails remembered per GitHub login). A review's create path (fetching `refs/pull/<n>/head`, a review branch with no upstream) is in `sessions.ts`, its git helpers in `git.ts`. |
| `src/server/ghlinks.ts` | Starting from a GitHub PR or issue pasted into Ask AgentK (`GET /api/github-link`, `POST /api/github-link/start`): reading it (`issueOrPr()` in `github.ts`, one call for both), the project it belongs to (a datapack its description's Meko line names, else the one on screen if it's on its repo, else the first on it; the repo's other projects are offered too) or the one to open (its datapack: the named one, reopening a closed project with it, else none for a PR and a new one for an issue), the clone to work in, and the session (a review, or a task from the issue's prompt). The palette's side is `linkEntries()` in `src/web/palette.ts`; the ref parser is `src/shared/github-refs.ts`. |
| `src/server/askagentk.ts` | Ask AgentK (`POST /api/ask-agentk`): an instruction in plain words from the command palette, answered by one call to the default agent with no tools, MCP servers or hooks (`claude -p`, `askArgs()`; on Kiro `kiroAskArgs()`, the `agentk-ask` workspace agent and `readKiroAnswer()`), the message (projects, running sessions, what's on screen, the exchange so far) on stdin; reading its JSON answer and errors (`readAnswer()`), checking the proposed actions against the state (`checkActions()`), two asks at a time, and counting asks for the usage report (`agentk_asks`). The palette's side is `askEntries()` in `src/web/palette.ts` and `CommandPalette.tsx`, which runs the picked action through the routes the UI already uses. |
| `src/server/sessionsearch.ts` | Finding a session by what it's about (`GET /api/sessions/search`): the words of the text, each session's name, PR, task, branch and design read from `state.db` (archived sessions included), and the ranking (`rankSessions()`). The palette's side is `findEntries()` in `src/web/palette.ts`. |
| `src/server/prdesign.ts` | A reviewed PR's design: fetched from Meko by the hash on the PR's `meko_design:` line (checked against it), and kept as the review session's design (a `designs` row marked with its `source`, never sent to Meko, and the file Claude reads). Fetched while the review starts, and again by the review's PR poll when the line's hash changes. |
| `src/server/projects.ts` | Projects (a closed one opens again when its dedicated datapack is picked), repo scan, datapacks (create with the repo remote in the description, attach, pin; an invite is accepted in Meko before its project is opened), project home and search, and What Meko doesn't know's routes (`mekoGaps`, `markMekoGap`, and `teachMeko`, which saves the user's answer to the dedicated datapack). |
| `src/server/prompts.ts` | Instructions sent to Claude at each stage (overridable per repo in `.agent-k/stages/`), the Meko recall lines added to them in code, the system prompt's saving rule (`mekoSaveSystemLine`), and the design lines added in code (questions and decisions into the design at the approval, keeping it current after, and where a review's PR design is). |
| `src/server/learn.ts` | The learn step: what a session learned about the product and repo, saved to its project's dedicated datapack at Merge & Close (before cleanup), at Discard (which waits for it: `sessions.discarding`), both unless the user checked **Don't save learnings** (`CloseSessionRequest.skipLearn`), and when asked (the `learn` action, `/agentk_learn`). Through the mod: the fork's facts (and which of the project's open questions on What Meko doesn't know each answers, the session's own first, `learnGaps`), the saved memories most like each, the small model's add/skip/update decisions, the writes, and marking those questions taught, or dismissed when Meko already had the answer; else a typed `learn` prompt (no questions). Records `meko_learns` and the model calls' usage. |
| `src/server/recall.ts` | Meko recall at session start: the search on a new session's task (and the issues it names), picking and formatting what it found, how poor Meko's answer was before picking (`startQuality`, for What Meko doesn't know), and holding it for the `SessionStart` context hook (`/context` on the hook socket). |
| `src/server/harness/` | The harnesses a session can run on (`docs/design/harnesses.md`): the `Harness` interface (`types.ts`: launch, hook payloads as AgentK's events, guard and context replies, edited paths, resume, version and update), the registry and the pick for a new session (`index.ts`, `Harnesses`), and an adapter per CLI: `claude.ts` (Claude Code, over `claude.ts` and `claudecode.ts`) and `kiro.ts` (Kiro CLI: the `agentk` agent's hooks, its command line, its conversation id, `normalizeKiro`). |
| `src/server/headtrust.ts` | Whether a session's PR head is trusted ([Code from public repos](../../docs/design/security.md#code-from-public-repos)): which sessions work on someone's PR head (`prHead`: a review, a task on a PR), the PR repo's visibility (kept 10 minutes; public or unreadable is untrusted), `repoConfigTrusted` (what `sessions.ts` checks before using the repo's status line and `.agent-k/stages` prompts, and the harnesses before loading its settings: Claude Code's `--setting-sources user`), the roles AgentK trusts (`TRUSTED_ASSOCIATIONS`), and the Kiro workspace config that stops an untrusted Kiro start (`kiroWorkspaceConfig`). `SessionManager.checkHead` reads it again before the first prompt and at every launch, into `sessions.untrusted`. |
| `src/server/launcher.ts` | The per-session launcher script every harness runs through (the login shell, the session's variables after the profile, every harness's markers cleared: `SESSION_MARKERS`), `shq()` and `scrubSessionMarkers()`. |
| `src/server/kiro.ts` | Kiro CLI outside the adapter: its home (`KIRO_HOME`), the markers it sets, the agent files AgentK writes (`agentk`, built from the user's default agent; `agentk-ask` for Ask AgentK), Kiro's built-in agent exported once, the guard script (exit 2), its session store (finding a worktree's session, each turn's credits and context fill), its one-shot output, and deleting a session. |
| `src/server/mekokiro.ts` | Whether Kiro's sessions reach AgentK's Meko (`MekoStatus.kiro`): the Meko servers in Kiro's MCP config, and what's missing for Meko's setup for Kiro to fix. Reads files only. |
| `src/server/claude.ts` | Claude Code's launch arguments (`claudeLauncher`: every path Claude is started with in its local spelling, `claudePath()` in `paths.ts`, for a home under `/net`), the hooks settings file, the hook forwarder script, the SessionStart context hook, the status line relay (reports plan limits, then runs the user's own status line, minus Meko's datapack suffix), and AgentK's mod: copying it to `run/mod/agentk` and the Claude Code version it needs. |
| `src/server/claudecode.ts` | The Claude Code sessions launch with: its version (read with `--version`, at most every 10 minutes), whether it runs AgentK's mod, and updating it with `claude update` (`AppState.claudeCode`, the banner in `Banners.tsx`). |
| `src/server/modlink.ts` | Each session's link to the mod: live while it polls (changes reported for `Session.modLive`), the long-polls the server holds (answered before the hook socket closes), prompts handed over and acked (a late ack is told not to run it, so a prompt never runs twice), refused prompts named by their text, Claude's questions (`AskUserQuestion`) while its call waits, Claude's Meko calls in flight (`mekoCall`, cleared at the turn's end; their content goes to the Meko call log from `sessions.ts`), the protocol the mod speaks (from `/mod/hello` and every poll: `learnReady`), the parts of a learn step and the line to show handed over on its next poll (`queueLearn`, `queueToast`), and resets on relaunch or exit. |
| `src/server/asks.ts` | Claude's `AskUserQuestion` questions as the mod forwards them (checked and capped for the browser; only choice questions), and the user's answers to them (`POST /api/sessions/:id/ask/:askId`). |
| `src/server/limits.ts` | Plan usage limits (5-hour and weekly) from status line reports and AgentK's mod's `session.measure` readings: parsing, merging (each session's last reading tells new data from a repeat), expiry, and the latest reading and each session's last one kept in `kv`. |
| `src/server/hooks.ts` | Unix-socket receiver for every session's hook events (Claude Code's, and Kiro's from the `agentk` agent), the edit guard's decisions (JSON, or plain text for Kiro's guard script), the SessionStart context and AgentK's mod (`/mod/*`). It binds under a temporary name and renames into place, so closing never removes another server's socket; `socketId()` tells its file from one put there since (the server binds again when it changes). |
| `src/server/instance.ts` | One server per AgentK home, even across hosts sharing it over NFS: the `server.lock` lease (heartbeat, stale after 45 s), taken before `serve` opens anything; on this host it waits for the old lease to be released or go stale, and a refused start exits 75. |
| `src/server/host/host.ts`, `host/protocol.ts` | The session host (`agent-k-local host`): every Claude in a node-pty pty, a headless xterm per pane for the screen a new viewer gets and for answering terminal queries, panes kept with their exit status, pastes, captures, attach streams with the active viewer's size and a fresh screen for a viewer that fell behind, `run/host.json`, and the home's host lease (`host.lock`, as `instance.ts` guards the server). Its protocol on `host.sock` (one JSON request per connection; `attach` then frames) and `PROTOCOL`/`MIN_PROTOCOL`. |
| `src/server/hostclient.ts` | The server's side of the host (`SessionHost`): requests, telling "no host" from other failures, starting a host (through its service when installed, never one of our own then; else detached), attach streams, `paneName()`. |
| `src/server/terminal.ts` | A browser terminal's socket (`/ws/term/:id`) bridged to its pane's attach stream while its screen has the session: input, resizes and focus claims in; output coalesced into ~16 ms frames out, with the host stream paused while the browser has a backlog; show, hide and Move to this screen passed to the session's `ScreenBoard`; and each socket's attach and close, and each move, in the server log. |
| `src/server/screens.ts` | One screen per session: `ScreenBoard`, the rules for which screen (page load) has a session, who waits for it and when it moves (closed, not showing, idle `SCREEN_IDLE_MS`, Move to this screen), and `screenName()` (browser and system from a user agent). No sockets or host calls; `terminal.ts` acts on what each screen is told. |
| `src/server/attachcli.ts` | `agent-k-local attach [name]`: a session's terminal in your own (`Ctrl+\` detaches). |
| `src/server/legacytmux.ts` | Moving an install off tmux (versions before the session host): ending this home's sessions still in tmux at startup, so recovery resumes them in the host, and removing the tmux service once the update is final. Remove after 2026-10-14. |
| `src/server/git.ts`, `github.ts` | Thin wrappers over the git and gh CLIs. |
| `src/server/worktrees.ts` | The worktree pool: which session owns each worktree, idle ones shared by every project on a repo (keyed by its real path) so build outputs carry over, claiming, releasing, trimming to `[worktrees] idle_per_repo`, removing ones unused for `idle_days`, and the startup sweep. |
| `src/server/design.ts` | Reading a session's design: the markdown design file, or the page and claude.ai link of a published Artifact; its open questions (`questions.json` beside it, or a markdown design's "Open questions" list) and the answers formatted for Claude; and the PR description's `meko_design:<name>;<hash>` line (formatting, reading, and setting it in a body). Sending versions to Meko, capturing the design after the approval and keeping the PR's line current are in `lifecycle.ts`. The Design-stage edit guard is `SessionManager.guard()` (hook `guard.sh`, route `/guard` on the hook socket). |
| `src/server/pastes.ts` | Images pasted into a terminal (`POST /api/sessions/:id/images`): checked by their bytes (PNG, JPEG, GIF, WebP; 20 MB), saved owner-only under `pastes/<session>/` for Claude Code to read by path, and removed when the session is archived. Images added in the New session dialog (`POST /api/projects/:id/images`) are staged under `pastes/.new/<project>/`, named by id in `CreateSessionRequest.images` (never a path), moved into the session's folder when it's created, and swept after a day. The routes' `image/*` body parser exists only in their own Fastify scope. Files of any other type pasted or dropped on a terminal (`POST /api/sessions/:id/files`, `savePastedFile`) go to the same session folder under a name the server picks, ending in the safe part of their own (`safeFileName`), 20 MB at most, through the `application/octet-stream` scope the knowledge route shares. |
| `src/server/changes.ts` | What a session changed vs. its base (committed, uncommitted, untracked): footer diff size (files and lines) and the Changes panel's per-file patches, with size caps, both sides of changed images for previews, and a closer base to suggest when the branch was moved onto another branch (`suggestBase`). Changing a session's base is `setBase()` in `sessions.ts`. |
| `src/server/comments.ts` | Review comments on a session's diff: drafts, validation, formatting them for Claude, and delivery (now if Claude is at its prompt, else at the next turn end). |
| `src/server/answers.ts` | A design's open questions, kept in memory (`DesignQuestionStore`: read from the questions file, or a markdown design's "Open questions" list, at first use, at startup for sessions in Design, and at each Design turn end; replaced mid-turn by the mod's `design_questions` tool, which writes the file too), and checking the answers a browser sends (with an approval or a request to revise) against them. Answers aren't kept on the server; once they've gone to Claude, `record` writes them into the questions file, each answered question resolved with the answer as its decision (an approval leaves the rest to AgentK, noted in `questions-approval.json` so `reopen` can undo it on a move back to Design). Reading and normalizing the questions and formatting answers are in `design.ts`. |
| `src/server/meko.ts` | Meko MCP client; every call AgentK makes is reported to `onCall` (tool, sizes, outcome, time, and the learn step's `mekoTag`), which Core records in `meko_agentk_calls`, and to `onTrace` with what was sent and what came back and the session it was for (`withMekoScope`), for the session's Meko call log (`mekolog.ts`). |
| `src/server/mekolog.ts` | A session's Meko call log (Log Meko calls, a project setting): every call AgentK makes for the session and every one Claude makes in it, with what was sent and what came back, as JSON lines in `designs/<session>/meko-calls.jsonl`, deleted on archive. AgentK's call sites mark their calls as the session's with `withMekoScope()` (`meko.ts`), which `MekoClient.onTrace` reports; Claude's come from the mod's `/mod/meko` end (`recordClaude`), a reply too large for Claude read from the file Claude Code saved it to (`claudeReply`, through `savedreply.ts`). Read backwards from the end a page at a time, and one call by its byte offset. |
| `src/server/savedreply.ts` | Claude Code's notice for a tool result too large for Claude's context (`TOO_LARGE`), and the file it saved the result to, only from the transcript's own session's `tool-results` folder (`savedReplyFile`, `readSavedReplySync`). Used by the Meko call log and the transcript reader. |
| `src/server/mekogaps.ts` | What Meko doesn't know: the project's Meko searches that found nothing or nothing relevant (`meko_calls.quality`, and `meko_preloads.quality` for searches at start, by what Meko returned before picking), grouped by question (`query_key`), a question left out once a later ask found something, the marks (`meko_gap_marks`: dismissed, taught, restored, each with its latest time, and the session whose learn step made one) that hold until it's asked again, the pages (after the last question's time and key) and open counts, the project's open questions for a session's learn step, its own first (`learnGaps`), and people's marks for the usage report. The routes and Teach Meko (`memory_add` into the dedicated datapack) are in `projects.ts`. |
| `src/server/mekoapi.ts` | Meko REST client for sharing (share, members, invites, accept or decline) and knowledge-base uploads (multipart `uploadKnowledge`, `documentStatus`). Sharing needs Meko's API URL (`resolveMekoApiUrl()` in `config.ts`), checked by `InviteService.requireSharing()`. |
| `src/server/knowledge.ts` | Files added to a session's knowledge base (`POST /api/sessions/:id/knowledge`): the checks (Meko on, the project's dedicated datapack, a base name with a type Meko takes, size), the upload through `MekoApi`, Meko's refusals in words (`uploadError`, never a 401 to the browser), the session's Meko call log line, and following each upload's indexing in memory until Meko is done (a `knowledge` event). The route's `application/octet-stream` parser exists only in its own Fastify scope. |
| `src/server/contacts.ts` | The people the Share dialog has invited (`share_contacts`), every project's: counted when an invite goes through, named from Meko's member lists, ranked (often and lately first), kept to 200, and forgotten one at a time. |
| `src/server/invites.ts` | Project datapacks shared with us: synced from Meko into `datapack_invites`, the first-sync baseline, accept, decline, later. |
| `src/server/mekosettings.ts` | The Meko tab in Settings: what it shows (never the key), checking a change against Meko before it's saved, and running Meko's setup for Claude Code and for Kiro (`setUpKiroMeko`). |
| `src/server/mekoclaude.ts` | Whether Claude Code's sessions reach AgentK's Meko (`MekoStatus.claude`, shown as a banner and on the Meko tab): the same server in Claude Code's settings and on its `meko` MCP server, and each of its tokens that isn't AgentK's tried on AgentK's server (accepted, and seeing the project datapacks AgentK's own token sees), with results reused for 10 minutes. Refreshed at startup, on a config change, on Settings open, at session launch, and after Claude Code's setup. It never changes Claude Code's setup. |
| `src/server/usage.ts` | Token usage: incremental transcript reader (main + subagents), Kiro's turns with their credits (`recordKiroTurns`, never priced), which also finds pushes to the base branch and Meko calls, and per session/project/model/day totals and costs plus the all-projects overview (`GET /api/usage`). |
| `src/server/callhome.ts`, `filetypes.ts` | Anonymous usage stats: the report (`buildReport`, counts only, Meko use included; its contract is `CallHomeReport` and `docs/call-home-report.schema.json`), sending it to the collector (hourly in an install's first day, then daily; `[call_home]`, or the `CALL_HOME_URL` a release carries), and file types (paths reduced to extensions right away). |
| `src/server/mekousage.ts`, `mekosavings.ts` | Meko calls in transcripts: finding them and their results (found, empty, failed), what a search asked and how poor its answer was (`searchQuality`: found nothing, or only memories below `MIN_MEMORY_SCORE`, which recall at start shares; a reply too large for Claude read from its saved file), the counts per session and project, a `seed` row for what AgentK's search at start passed to Claude, and the tokens Meko brought into first turns, and for the usage stats calls by tool (`toolCounts`, naming only the lookups and saves) and the searches at start (`mekoStarts`), the tokens calls sent (`toolSent`), learn steps (`learnRuns`), AgentK's own calls and transcript captures; the fixed formula, with its constants, for what a search that found something (or a seed) saved. |
| `src/server/db.ts`, `store.ts` | SQLite (`node:sqlite`), migrations, row ↔ API type mapping (`sessions.kind`, and `Session.kind`, keep the old type names for tasks; `kindOf()` in `stages.ts` reads them as `task`). |
| `src/server/auth.ts`, `tls.ts`, `trust.ts` | Login, TOTP, rate limiting; TLS certs; Claude Code folder trust. |
| `src/server/updater.ts`, `install.ts` | Self-update with rollback (tarball per platform and CPU); host install. |
| `src/server/mekosetup.ts` | Meko set up for Claude Code (plugin, MCP server, key): reading it from Claude Code's settings and `~/.claude.json` (the user-scope `meko` server), what keeps it off AgentK's Meko, and running Meko's own setup package from npm (integrity-checked) with the bundled Node. |
| `src/server/service.ts` | The two background services (server, session host) behind one `ServiceManager`, and removing the tmux service of older versions; `servicesFor(home)` uses them only when they run this home: systemd user units on Linux (run only on the install host, `ConditionHost=`), LaunchAgents on macOS. Install, start, state, remove, boot check. |
| `src/server/tty.ts`, `health.ts` | CLI output helpers (sections, marks, color only on a TTY); local `/healthz` probe used by `install` and `status`. |
