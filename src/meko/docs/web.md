# Meko backend: one port for browsers and agents

Meko listens on one port, `[server] port` (7777), for everyone. Agents (MCP clients, AgentK,
Presenter) and the CLI call `/mcp` and `/api/v1` there with their Bearer tokens
([api.md](api.md#auth)). Browsers get the web UI ([web-ui.md](web-ui.md)) at `/`, the data routes
and `/mcp` the UI calls, `/api/v1/auth/status`, and each extension's own web UI at `/ext/<name>/`:
AgentK's at `/ext/agentk/`, Presenter's at `/ext/presenter/`. This page is about the browsers' side:
how they get in, remote access, turning the web UI off, and the extensions.

```mermaid
flowchart LR
  b["browser on another device"] -->|"TLS, remote access"| port["Meko's port, 7777"]
  bh["browser on this computer"] -->|"plain HTTP"| port
  agents["MCP clients, AgentK, meko CLI"] -->|"127.0.0.1, plain HTTP, Bearer"| port
  port --> ui["/ : web UI"]
  port --> data["/api/v1, /mcp"]
  port -->|"/ext/agentk/*, prefix stripped"| sock["AgentK's unix socket"]
  port -->|"/ext/presenter/*, prefix stripped"| psock["Presenter's unix socket"]
```

## Decisions

| Decision | Why |
|---|---|
| **One port for agents, the CLI and browsers** (`[server] port`, `MEKO_PORT`, `--port`; 7777, the port AgentK listened on before Meko served it). It's taken when `serve` starts, before anything else: one another program holds stops `serve` with what to do (an AgentK from before Meko served it is the usual one), and `meko install` checks it first | One address to remember and open in a firewall, with nothing to keep in step. Before, agents had an API listener of their own on 127.0.0.1:7778, because remote access is HTTPS with a self-signed certificate, which MCP clients can't use; reading each connection's first byte (below) answers that on one port. Agents Meko had connected to 7778 are connected to the one port at its first start (`moveToOnePortOnce` in `internal/cli/serve.go`), once, and only those at exactly `http://127.0.0.1:7778/mcp` (an `Exact` move), so one pointed by hand at another Meko on this computer is left as it is; one pointed at 7778 later shows "needs reconnecting". `[web] port` and `MEKO_WEB_PORT` are refused, naming `[server] port`, so a port someone chose for browsers never quietly moves; one an older Meko wrote into `web.toml` itself (`meko install`, the handoff) is ignored there and dropped at the next write |
| **The credential depends on the request, never on how it came in** (`authorize` in `internal/server/server.go`): a Bearer token is held to the token rules and never falls back to a browser's; a request without one is a browser's when it passes their rules (below); the owner's routes (the Extensions and Status pages', the Meko Cloud link's) refuse the client token; the admin-only ones (`status`, `version`, `web/reload`) take only the admin token. Tokens are taken only from this computer | Each credential keeps its meaning: what a browser holds never opens an admin route, and an agent's token never installs software or moves the Meko Cloud link. A token from another computer is refused, as it was when agents had a listener on 127.0.0.1 only. |
| **With remote access the port speaks TLS and plain HTTP** (`server.Sniff`): each connection's first byte says which. A TLS handshake (`0x16`) is served over TLS, with the remote access rules; anything else is plain HTTP, served only to a loopback peer, with the local rules (the Host list), and answered `400` from anywhere else. The first byte is read off the accepting goroutine, within 10 s | Agents and the CLI on this computer keep `http://127.0.0.1:7777`, while browsers anywhere get HTTPS on the same port. Rejected: HTTPS only (MCP clients refuse a self-signed certificate), and two sockets on the same port number (Linux refuses `127.0.0.1:7777` beside `0.0.0.0:7777`). |
| **`[web] access`: `local`** (the default) **or `remote`** | Local listens on 127.0.0.1 over plain HTTP and takes only requests from this computer (below). Remote listens on every address, browsers over HTTPS, and takes any browser's. Neither has a login. An unknown value is refused at start, so a typo never opens the port to the network. |
| **Local access: no login, by the loopback rule AgentK had** (`LocalAccess` in `internal/server/local.go`): a loopback peer; Host `localhost`, `127.0.0.1` or `[::1]`; no `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host` or `X-Real-IP`; `Sec-Fetch-Site` `same-origin` or `none`; an Origin, when sent, that's this one | The owner chose it for this computer. The Host check keeps a DNS-rebound page out, the proxy headers keep out what a proxy forwarded, and the site checks do a SameSite cookie's job: an `<img>` on another site gets a 401, not an answer it could time. |
| **No login, with either access.** Remote access lets in every request another site's page didn't send (`SameSite` in `internal/server/local.go`): `Sec-Fetch-Site` `same-origin` or `none`, and an Origin, when sent, that's `https://<Host>`. `GET /api/v1/auth/status` stays, always saying signed in; no other `/api/v1/auth/*` route exists. The `owner` and `auth_sessions` tables stay in the database, unused | The owner opens the URL and gets the page, from any device. What that exposes is the owner's call: with remote access, anyone who can reach the port has the memories, the knowledge and, through AgentK's terminals, a shell on the host as the user Meko runs as. `meko ui stop` closes the port when the web UI isn't needed (below). The site check keeps another site's page from driving the API through a browser that can reach the host, when the browser sends Fetch Metadata. One that doesn't (Safari before 16.4, older Firefox) sends neither header on a cross-site `<img>` or `<script>` GET, so with remote access such a GET is let in, where the session cookie refused it; it can't read the reply (no CORS), and a POST still carries an Origin, which must be this one. The status route stays for pages that read it, AgentK's among them, which go to a sign-in screen only when it says remote and not signed in. The tables stay so a rollback finds an older release's login as it left it. |
| **`[web] enabled`** (default true): **`meko ui stop` turns the web UI off, `meko ui start` on, and `meko install --no-ui` installs with it off**. Meko writes it to `web.toml` (`config.SetWebEnabled`), keeping the file's other keys; `config.toml`'s own `enabled` wins, and then the commands refuse and say to change it there. The CLI writes the file, then has a running `serve` read it (`POST /api/v1/web/reload`, admin token only); a stopped one reads it at its start. Off, no browser gets in: `/` and `/ext/<name>/` answer 404 saying so, and only tokens (and tickets, and nothing with `auth = "none"`) open the rest. With remote access the port is taken again on 127.0.0.1 only. Turning it off closes the WebSockets the proxy upgraded (`extproxy.Proxy.CloseAll`) | The owner turns off what nobody uses: with remote access, an open port with no login. Agents keep the port, so stopping the UI never cuts off MCP. It stays off through restarts, reboots and updates, until `meko ui start`, so a reboot doesn't quietly reopen it. `web.toml` is where Meko keeps what it chooses for browsers; releases that read it ignore a key they don't know there, so a rollback serves the UI rather than refusing to start, as it would on an unknown `config.toml` key. One writer path works whether or not Meko runs. AgentK's terminals are WebSockets, hijacked from the server, so they'd stay open otherwise. |
| **Settings are taken up without dropping agents** (`webListener` in `internal/cli/web.go`): `meko ui start` and `stop`, and the handoff below, build a new server and swap it in under the same socket. The port is taken again only when the address it's bound to changes (remote access on or off, the web UI on or off with remote access), after the requests in flight finish; if the new address can't be taken, the old one is taken back. A certificate is read again at each change, and TLS serves the new one at once | One listener carries every agent's connection, so restarting it for a setting would drop them all. |
| **TLS has no Host list**; Origin must be `https://<Host>`. Plain HTTP, which comes only from this computer, must name `127.0.0.1`, `localhost` or `[::1]` with the port | As AgentK had it: a DNS-rebound page can't pass TLS for another name. People reach the host by its FQDN, short name or address alike. |
| **The certificate is `[tls] cert` and `key`, or a self-signed pair in `certs/`** (`internal/tlscert`), made when remote access starts and, at a later settings change, again within 30 days of expiring. One that can't be read never stops `serve`: the port stays on 127.0.0.1, so agents and the CLI keep it, and `status` and `meko ui` say remote access is off and why until a later change reads one. The pair: 825 days, ECDSA P-256, naming the FQDN, the host name, localhost, 127.0.0.1, ::1 and the interface addresses. `meko status --verbose` shows its SHA-256 | Browsers cap a certificate at 825 days. Trusting the fingerprint once on a phone is the price of not needing a CA. |
| **Extensions are served at `/ext/<name>/`** (`internal/extproxy`), with the prefix stripped, to the unix socket the extension names, for each registered extension whose catalog entry has `WebUI` | One port and one access check for everything Meko runs. The extension trusts its socket (only this user can connect to it) and runs no login of its own. The proxy passes the browser's Host and Origin as they are, so the extension's own same-origin checks hold; it drops the Cookie (the host's cookies, none of them the extension's) and adds no `X-Forwarded-*`. The WebSockets it upgrades are kept, so the listener's shutdown closes them (`CloseAll`). `/ext/<name>` without the slash redirects to it with one, so relative URLs resolve. When the extension isn't answering, the reply is a 502 that says to start it. |
| **Meko tells a running extension when something it reads from Meko changed**: a POST of `{"what": "<thing>"}` to `/_meko/changed` on its socket, with no Origin, 5 s at most (`extproxy.Proxy.Notify`), to each extension with a web UI that answers. Today the one thing is `cloud`, the Meko Cloud link ([cloud.md](cloud.md)), posted when it changes and once at each start of `serve` | An extension reads such settings from `meko token --json`; this tells it to read again at once rather than poll. It's best effort: a failure is logged, and an extension that doesn't know the path answers 404, which is fine. |
| **`/api/v1/extensions`** lists every extension Meko knows: its name, title and description, whether it's installed (registered), its path while it's served, whether it accepts a connection on its socket (`extproxy.Answers`), the release Meko installed and whether Meko can update it (`version`, `updatable`: a `Managed` extension's release install, read from its `VERSION`, no network; `not_updatable` says why not for an installed one: a build from source, or an AgentK still in its old home), what the last check found (`latest`, `latest_url`, `update_available`, `checked_at`, `check_error`, from `update.json`), the update on probation (`pending`), the versions rolled back (`rolled_back`), **Update automatically** (`auto_update`), why an automatic update waits (`waiting`), and its last action (`auto` when Meko started it on its own) | The web UI's sidebar links to the running ones, and its Extensions page shows the rest. A socket file an extension left when it died refuses the connection, so it doesn't count as running. |
| **The Extensions page installs, updates, starts and stops extensions** (`POST /api/v1/extensions/<name>/install\|update\|start\|stop`), as `meko extension install`, `meko extension update` and the extension's own `start` and `stop` do, run by `serve` (`webListener.RunExtension`) as a background job, one per extension at a time, kept in memory with its last 16 KiB of output. The jobs belong to `serve`, not to one server, so they outlive the swap of one for another. An install from here never asks questions (`--non-interactive`, no stdin) and has 15 minutes. An install or a start of an extension with a web UI, or an update that leaves it running, ends only once the extension answers on its socket, or fails after 30 s (`extensions.ListenTimeout`). An update has 15 minutes too. The output and error have the client token blanked; the log gets only the extension, action and outcome. The list leaves out a failed install or start once the extension is installed and running (`overtaken`), and keeps every other failure | Installing takes minutes, longer than a request should be held open, so the page polls the list. Only known extensions, from the configured release repo, and only for the owner (a browser, local or remote, with the Origin and site checks, or the admin token): no more than they can already do through AgentK's terminals. The installer is given the client token on its command line, but nothing promises it never echoes it, and the output is a reply to a browser. AgentK's `start` returns once its service is up, before its server listens, so the page would otherwise see it not running and stop looking. A job is only what the page started, so `meko extension install` or `me_koder start` in a terminal never changes it: without `overtaken`, a failed Install would stay on the card of an extension installed from a terminal until Meko restarts. Only a running extension overtakes a failure, because an install can fail after registering the extension (it never answers on its socket, or a registered one's own `install` fails again), and a stopped extension doesn't prove its stop worked. |
| **The Status page checks for and installs Meko's own updates** (`GET /api/v1/update`, `POST /api/v1/update/check` and `/update/apply`), through `serve`'s own `update.Updater`: the same check and install as the scheduled ones and `meko update`. The update lock (`update.Lock`: a mutex in `serve` and a `flock` on `run/update.lock`) keeps the page's, the scheduled ones, the extensions' and `meko update`'s apart, so they never stage at once: a scheduled check skips its turn while another holds it, the page's check and install answer 409 while `meko update` runs, and `meko update` refuses while `serve`'s runs. An install is a background job (checking, installing, restarting) and answers 202; once the new version is current, `serve` stops as for an automatic update: under the service it exits 0 for the service manager to start `app/current`, and started by hand it execs `app/current/bin/meko` with its own arguments, as a rollback does, unless a stop (`meko stop`, `restart` or `destroy`) arrived while it was stopping. It's refused (409) on a build from source, on a release install whose updater couldn't be set up (the card says why), while an update is on probation, while a check or an install runs, and while an Extensions-page action runs. `[update] channel = "off"` and `auto = false` stop only the scheduled ones | A helper `meko update` can't do it from inside the service: restarting the unit kills everything in it (`KillMode=mixed`), the helper too. Refusing while an extension's action runs keeps the restart, which waits for it, from hanging for the minutes an install takes. Only the owner reaches these routes (a browser, or the admin token), never an agent's client token: installing software is the owner's call, and the CLI has `meko update`. |
| **Check now and Update automatically** (`POST /api/v1/extensions/<name>/check`, `PATCH /api/v1/extensions/<name>` with `{"auto_update": bool}`). Check now runs the updater's check in the request (60 s), one release list for Meko and every extension, and answers with the row, or `409 UPDATE_BUSY` with the row while an update holds the update lock. The switch is saved in `extensions.json`. An update from the page holds the update lock too, so it waits for no other and fails at once while one runs. AgentK's own page calls these routes and the update one from the browser: it's served on this origin, with the same access | One check, one GitHub call, for everything Meko updates. AgentK's page keeps its banner and its Update button, and the job runs in Meko, so it survives AgentK's restart. |
| **The installer runs inside `serve`**, so in Meko's service unit: stopping or restarting Meko stops it, with everything it started (it has a process group of its own, which is killed), and the job fails, "stopped". **A self-update waits for running jobs** before it restarts Meko. Start and stop run to their own 2-minute limits. A command's output pipe is closed 5 s after it exits (`extensions.PipeWait`) | An install cut off part-way is repaired by Install again, which re-runs AgentK's own `install`. An update arrives on its own, so it shouldn't cut one off; a stop or restart someone asked for shouldn't wait 15 minutes. AgentK's server itself runs in AgentK's own services, so it doesn't stop with Meko. A process a command left running would otherwise hold the pipe open and keep the job running forever. |
| **Knowledge-file links follow the request** | Upload and download links are built for `http://127.0.0.1:<port>`; asked by a browser, they're given its own scheme and Host, which it can reach (from another computer, with remote access). |

## Settings

| Key | Env | Default | What |
|---|---|---|---|
| `[server] port` | `MEKO_PORT`, `--port` | 7777 | Meko's one port, for agents, the CLI and browsers. `[web] port` and `MEKO_WEB_PORT` are refused. |
| `[web] access` | `MEKO_WEB_ACCESS` | `"local"` | `"local"` or `"remote"`. |
| `[web] name` | | this host's FQDN | The host name links use with remote access. |
| `[web] enabled` | | `true` | `false` keeps browsers out: `meko ui stop` and `meko ui start` set it in `web.toml`, and `meko install --no-ui` sets it off. |
| `[tls] cert`, `key` | | a self-signed pair | PEM files, both or neither. |

Meko never writes `config.toml`. The web settings it chooses itself go in **`web.toml`** beside it
(`config.WebFile`), which a `[web]` or `[tls]` key in `config.toml` overrides key by key. They're a
file of their own because a release from before the web UI refuses `config.toml` keys it doesn't
know, so a rollback after an update that failed its probation, or a downgrade, would leave a Meko
that can't start; releases from before the web UI never read `web.toml`, and later ones ignore its
keys they don't know. Meko writes its access and name once, when neither file sets one
(`config.AddWeb`), keeping `enabled`, and never a port (an older Meko's `port` there is ignored, and
dropped at the next write):

- **`meko install`** writes it with `--access`, or by AgentK's old rule (remote over SSH or on Linux
  with no display, else local), unless AgentK is on this computer: its handoff decides then.
- **The handoff** writes it from what AgentK had (below).

`meko ui start` and `stop`, and `meko install --no-ui`, write `enabled` there any time
(`config.SetWebEnabled`), keeping the rest.

## The handoff from AgentK

An AgentK install that served browsers itself (on its own port, with its own certificate, and a
login) hands them to Meko. At every start `serve` asks each registered extension with a web UI
`<command> _handoff --json` (15 s; `internal/extensions` `Handoff`):

```json
{"socket": ".../web.sock",
 "legacy": {"bind": "0.0.0.0", "port": 7777,
            "tls": {"cert": "...", "key": "...", "self_signed": true},
            "owner": {"username": "...", "pw_scrypt": "scrypt$...", "totp_secret": "..."}}}
```

- **`socket`** is where the proxy sends `/ext/<name>/`, kept in `settings` too, for a start whose
  handoff fails. When it's gone or refuses connections (the extension stopped, or its home moved
  and its socket with it), Meko forgets it and asks again on the next request that needs it.
- **`legacy`** is there only for an AgentK that served browsers itself. Meko takes it over once
  (recorded as `extension_took_over.<name>` in `settings`): the extension keeps reporting it, and a
  `web.toml` the owner removed mustn't come back. Even then it fills in only what Meko doesn't
  have:
  - `web.toml` with its access (loopback is local, anything else remote), never its port: Meko's is
    `[server] port`, where agents connect too, and moving it would move every agent's URL;
  - its self-signed pair, copied into `certs/` (or its own `[tls]` files, named in `[tls]`), so
    phones that trusted its fingerprint still do.

  Its `owner` (its old login) is ignored: Meko has none.
- **It runs once the port serves**, so `meko start` doesn't wait for it. An extension that can't
  hand over yet is asked again every 30 s, each failure logged once; when a later handoff changes
  `[web]` or `[tls]`, Meko takes them up (above). An AgentK too old to answer still holds 7777, and
  then `serve` doesn't start at all: it says the port is in use, and what to do.
- **An extension registered while Meko runs** (`meko extension install`) is asked on the first
  request that needs its socket, and again at most every 10 s.

Secrets in the reply never reach a log.
