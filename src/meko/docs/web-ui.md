# Meko backend: web UI

A light UI for one person, on their own machine or, with remote access, from their other devices:
browse, edit and search a datapack (all sources or one), add memories and keep, promote or delete
several at once, upload and manage knowledge files, download artifacts, read conversations, see what Meko couldn't answer
and teach it, see its analytics, and connect the agents on this computer (or copy the URL any other MCP client connects to). It calls the REST routes
and MCP tools in [api.md](api.md) and `/api/v1/auth/status`; the data routes it added are
`/usage` and Context Gaps' (`/questions`).

## Decisions

| Decision | Why |
|---|---|
| **Its own small app in `src/meko/web_ui`**, not Meko Cloud's web app: React, Vite, Tailwind and lucide-react, with Meko Cloud's colors | Cloud's web app is built for accounts, and most of it (billing, sharing, onboarding) has nothing to do on one machine. This one is about 100 KB gzipped, with three runtime dependencies. |
| **Served on Meko's one port (`[server] port`, 7777) from `web_ui/dist` on disk**, found as the context engine is: `[web_ui] dir` (or `MEKO_WEB_UI_DIR`), else `<bin>/../web_ui/dist` | `go build` and `go test` don't need Node. Without a built UI, `/` says how to build one and the API is unchanged. The CLI, MCP clients and Kode use the same port with their Bearer tokens, which no browser holds ([web.md](web.md)). |
| **No login, with either `[web] access`. `local`** (127.0.0.1, plain HTTP): a request is let in when it's local by Kode's loopback rule (a loopback peer, Host `localhost`, `127.0.0.1` or `[::1]`, no `Forwarded`, `X-Forwarded-*` or `X-Real-IP`, `Sec-Fetch-Site` `same-origin` or `none`, and its own Origin). **`remote`** (every address, HTTPS for browsers): any request another site's page didn't send (`Sec-Fetch-Site` and Origin alone). `meko ui` just opens the web URL | The owner opens the URL and gets the page, from this computer or, with remote access, any device that reaches the port. Anyone who reaches it has the memories, the knowledge and Kode; `meko ui stop` keeps browsers out (and with remote access takes the port off the network) when the web UI isn't needed ([web.md](web.md)). The site checks keep another site's page from using the API through the owner's browser. |
| **The page asks `/api/v1/auth/status` first**, then shows the app. The old sign-in and account addresses lead into it: `/signin?next=<path>` to `next`, `/setup` to `/`, `/account` to Settings. A page outside the app (an extension's, `/signin?next=/ext/kode/…`) is loaded itself (`location.replace`) rather than routed. A later 401 `UNAUTHORIZED`, which only local access sends, says the request wasn't recognized as local; remote access refuses only another site's page, with a 403 the page shows as an error | Bookmarks and older extensions' pages still link to the old addresses. `next` is followed only when it's a page on this site, read the way the browser will read it (`safeNext`), so a crafted link can't send anyone elsewhere. With local access a 401 means something between the browser and Meko, such as a proxy, made the request look remote; the page says to use `meko ui` on the host, or set `[web] access = "remote"` in `config.toml`. |
| **Meko takes its own origin from a browser, and only it**, and sends no CORS headers | Another site's page can't call the API or read its replies. With local access the Host check also stops DNS rebinding. |
| **The UI's files need no credential**; catch-all `/api/*` and `/mcp/*` routes keep API paths off the UI's route | It's static and holds nothing secret. The credential check keys on the matched route alone, and an unknown API route stays a 401 without a credential and a 404 with one. |
| **Frames refused, `Content-Security-Policy` of `self`**, assets cached for good (their names are hashed) and `index.html` never | Another site can't frame the page to trick clicks on it, and a rebuilt UI loads at once. |
| **Search and Add memory go through Meko's own `POST /datapacks/:id/search` and `/memories` routes**, which run `context_search` and `memory_add` on the datapack as `/mcp` would | The UI shows what an agent would get, without an MCP session of its own. Its calls are recorded as agent `meko_web_ui`, which the agent counts leave out. |
| **Search shows only memories at 0.40 cosine or above** (rounded to the two places shown), and every hit's cosine similarity; a knowledge-base result that is a promoted memory carries a "promoted memory" badge | `context_search` applies no floor to memories, as Cloud's doesn't: an agent weighs them beside the other sources, and a floor costs recall on names and IDs. A person reading the list needs only the matches. With Meko's embedder, right answers measured 0.40 to 0.72 and unrelated memories 0.11 to 0.29; a 0.65 floor would drop most right answers. |
| **Overview leads with Cloud's three context tiles**: context size (tokens, KB · memory · conversations), context efficiency (% saved, ~sent vs ~baseline a search, a *live* badge once there are searches) and context quality (% of results that are relevant) | The numbers Meko Cloud's datapack page leads with. Efficiency and quality use Cloud's formulas; size counts with efficiency's weights (a chunk 1,000 tokens, a memory 200, a turn by its length), so the two tiles read against each other ([api.md](api.md#context-efficiency-and-quality)). `datapack_metrics` gives agents the same three. *Live* means measured from real searches, not polled. |
| **Metrics is Cloud's Analytics dashboard on the same `/metrics` payload and datapack counts**, plus a Usage section from `/usage` | The cards read what Cloud's read, so the two can't drift; Refresh reloads all three. Token counts are the context size tile's (`context_size` from `/metrics`). Usage (per-tool latency and errors, agents, the latest calls) is Meko's own: the call log already holds it. |
| **Metrics picks 7, 30 or 90 days** (`?days=` on `/metrics` and `/usage`); a recent call opens its steps' timings; **Status** reads `/api/v1/server` | Without `days`, `/metrics` keeps Cloud's windows for Cloud-shaped clients. `/api/v1/status` stays the CLI's (admin token); `/api/v1/server` gives the same reply to the web UI and the client token, since it describes nothing but the user's own install. |
| **Invite opens a banner pointing to Meko Cloud** (`cloud.mekodata.ai`) | Sharing needs the datapack in Cloud, so Meko has none; the button says where it lives instead of leaving the user to look for it. |
| **The sidebar's Extensions group**, under Agents, starts collapsed on every load. Its label opens the Extensions page (`/extensions`); its chevron shows the installed extensions under it, each with a dot: a running one with a web UI is a plain link to it (`/ext/kode/`, `/ext/present/`) that replaces the page, any other links to the Extensions page. Kode and Present show their logos (`public/kode-logo.png`, `public/present-logo.png`, bundled so they show while the extension is stopped), any other a puzzle piece; the Extensions page shows the same logo on each card | Meko serves the extensions with the same access as the UI. Extensions refuse to be framed, so it's never shown inside Meko's page. The label and the chevron are two targets so that opening the page doesn't also open the group. |
| **The sidebar's datapacks are one list** from `GET /datapacks`, by name, with no location in any request: each row opens where its `web_url` says. A path (`/datapacks/<id>`, a datapack Meko serves here) opens its pages here; a full URL (a linked Meko Cloud's datapack) opens Meko Cloud's web app in a new tab, with an external-link icon; null (a web app that isn't known) shows the row disabled, pointing to Settings › Meko Cloud. A row from a server older than the UI, with no `web_url`, opens here. An address here for a datapack the list opens in Meko Cloud's web app (`/datapacks/<id>[/<tab>]`, as extensions link every datapack) goes on to its `web_url`, its Context Gaps tab to `/gaps/<id>`, in place of the address so Back skips it. One shared with the account ends with a two-people icon. With no datapack in the address, the first row that opens here is shown; when every row opens in Meko Cloud's web app, the page says the datapacks are in Meko Cloud rather than that there are none. After 50 rows a **Show all N** row shows the rest (and **Show fewer** hides them again, until the page reloads). A listing that failed (while linked, Meko Cloud's failure fails the whole listing) is one note in the list's place, linking to Settings › Meko Cloud when the key was refused or the link has no API URL; a datapack in the address still opens, and doesn't wait for the listing (which waits for Meko Cloud while it's linked), so this Meko's datapacks stay reachable by their links while Meko Cloud is down or slow. The list loads again when Settings › Meko Cloud links or unlinks, and, while linked, from the refresh beside **+**. Whether Meko Cloud is linked comes from `/settings/meko-cloud`. While linked, **+** makes the datapack in Meko Cloud (Meko decides; the create names no location) and says so in its tooltip and dialog; the new datapack opens here only when the create's reply `web_url` is this UI's path, so a link the UI hasn't noticed yet never opens a Meko Cloud datapack's id here. Either way it shows in the reloaded list. **A Find a datapack box** under the heading narrows the list to the names that hold what's typed (ignoring case); while it holds a query, every match shows, with no Show all, and when nothing matches it says so. × or Esc clears it | The UI never decides where a datapack lives: Meko routes each one by its id, and gives each row its link. Once linked, new datapacks are made in Meko Cloud, so a list of only this Meko's would hide the user's current work; the datapacks already here keep working until they're moved. A Meko Cloud datapack is browsed in Cloud's web app, since Cloud has no API for this UI's usage, memory map, history or export. Extensions link a datapack here without knowing which side has it, so the UI sends Meko Cloud's on. The two-people icon is the one Meko Cloud's web app marks shared datapacks with. The cap keeps an account with hundreds of datapacks from making the sidebar endless; the route and the CLI still give every row. The box is Meko Cloud's sidebar's; it filters in the browser because the list is already loaded, and a match is the row being looked for, so the cap doesn't hide it. |
| **The Extensions page** lists the installed extensions (registered with Meko, `extensions.json`) and the ones available to install, each with its description and state (and the release Meko installed, for Present), and **Install**, **Start**, **Stop** (asking first, since stopping Kode ends its sessions), **Update** for an extension whose releases Meko installs (asking first: it restarts it; once done, the card shows the update's last line, such as "is running X" or "it runs at its next start"), shown only while its last check found a newer release that wasn't rolled back (`update_available`) or while an update runs, and **Open**. An action runs on the server as the extension's job ([web.md](web.md)), and a start or an install lasts until the extension answers; the page polls the list every 2 s while one runs, shows its output, and shows the error and output when it fails. A Kode installed by its own installer shows as available: Install registers it, re-running its `install` with Meko's URL and token | "Installed" is the test Meko serves an extension by, so the page never offers an Open that can't work. The sidebar and the page share the list (`lib/extensions.ts`) and reload each other when an action starts or ends. |
| **Works on a phone**: below `md` the sidebar is a drawer opened from a top bar (closed on every navigation, and hidden from the tab order while closed); the datapack header's actions go icon-only and its tabs, like segmented options, scroll sideways; dialogs fit the screen and scroll; inputs are 16px | Remote access means the UI is opened from a phone. iOS zooms the page into any input under 16px. The sidebar's dialogs render outside it, because its slide-in transform would otherwise trap them inside it. |
| **Status is the sidebar's first link**, with a dot for the context engine's state (polled every 30 s); pages render inside an error boundary | It's where someone looks when something seems off. A page that throws (as against a server older than the UI, between a rebuild and a restart) says so and suggests `meko restart` instead of going blank. |
| **Status has an Updates card**: the running version, the newest release the server found (with its release notes), when it last checked and why a check failed, **Check now** and **Update to X**. While it installs, the card polls `/api/v1/update`; once Meko stops to restart (the job's restarting step, or a poll that fails while it installs a version, since Meko stops at once), it polls `/healthz` and reloads the page when the version changed, or when Meko answers again after it stopped answering (a rollback brings back the old version); after 3 minutes it says Meko hasn't come back. The version it asked for is kept in `sessionStorage`, so after the reload it says whether the update worked, was rolled back (`rolled_back`, from `bad-versions`) or didn't start. A build from source says it doesn't update itself. **The sidebar's version gets an Update chip** to Status while a newer release is out (read every 30 minutes) | Without it, a server the service doesn't run with `[update] auto` only reports updates, and installing one needs `meko update` in a terminal. The new web UI comes with the new binary, so the page must reload into it. The Status page keeps showing while a refresh fails, so the card can wait out the restart. |
| **Projects (`/projects`, `/projects/<id>`), linked under Extensions in the sidebar**: a card per project (name, description, datapacks and folders counted, the folders' names) with a box that finds one by its name or a folder's, and **New project** (name, description, and a layout from `/projects/themes` whose folders it starts with, or a first folder for Custom). A project's page has **Folders**: the folder list with **Add folder**, and the open folder's description, **Add datapacks** (this Meko's, each saying where it's filed now, which it moves from), edit and delete; each datapack with its counts, a link to it and **Remove**, which unfiles it. **Activity** is the project's activity log in the knowledge base's log, and **Settings** its totals and **Delete project**, confirmed by its name. **Edit** changes the name and description | Meko Cloud's projects ([api.md](api.md#projects)), on the same routes, so a project means the same on both. Deleting a folder or a project, and Remove, never delete a datapack: only the datapack's own Delete does, as in Cloud. Meko Cloud's datapacks aren't offered: its projects are in its web app. |
| **Settings is a page (`/settings`), opened from the gear at the foot of the sidebar, beside the theme toggle, as in Kode's rail**: in this order, a link to the Meko Cloud link; switches for **Memory extraction** and **Search answers** under "Uses your Claude Code" (each turned on after the server's test call, with a note while it runs and the error when it fails; extraction's line shows the model, interval, waiting turns and last run); an **Access** card that shows only Local or Remote, from `[web] access`; **Calls** (the **Keep call contents** switch, how long they're kept and what's kept now, **View calls**, and **Clear contents** after a confirmation); and **Anonymous usage stats** (`/settings/usage-stats`). Every switch saves as soon as it's flipped | The two features spend the user's Claude quota, so they're opt-in, and a switch is easier to find than a command; the server finds Claude Code itself, as it does for the Agents card, so the browser never names a program. When `config.toml` or the environment turned usage stats off, its switch is off and disabled and says which. Their card says Anonymous because the report carries counts, enums, versions and the install's random id, never a name, content, query, path, host or token. |
| **A Join us on Discord link sits just above the sidebar's footer** (the version line), opening `https://mekodata.ai/discord/` in a new tab, with Discord's mark in the text colour | Someone who installed Meko and got stuck can find where to ask without going back to the README. It sits outside the page links because it leaves Meko. |
| **The Calls page (`/calls`), reached from Settings only, not the sidebar**: every call Meko answered, this Meko's and the ones sent on to Meko Cloud alike, newest first, 50 at a time with **Load older**, each with when, the tool, the agent, **By** (Kode for a call that came with `X-Meko-Client: kode`, else Agent), its results and time; filtered by an agent id and a tool typed and applied with Enter, and **Kode's only** and **Failed only**, which apply at once. The filters are the address's query (`?agent=`, `tool`, `client`, `failed`), so a filtered page can be linked to and reloads as it was. A call opens the decision trace's dialog, which adds **Sent** and **Got back** (JSON indented, each with copy) when its contents are kept, else says they weren't | One place to see what an agent asked Meko and what it was told, for every agent and extension. It's a tool for looking into a session, not a place to visit, so the sidebar stays as it is. The page is the call log's, whose rows hold no text; the contents come from `/calls/:id` only while Settings keeps them ([api.md](api.md#call-contents)). |
| **The Meko Cloud link at `/settings/meko-cloud`** (from Settings): its state; **Sign in with Meko Cloud** (**Sign in again** while linked), with a Sign up link while unlinked; under *Or paste an API key*, the key (never shown; its last four characters), Sign up and Log in links to the web app that goes with the MCP URL as it's typed (`lib/mekourls.ts`, worked out as the server does) and Meko Cloud's Settings URL to copy; under *Your own Meko server* the MCP, web app and API URLs; **Check and link** (or save), a second press to confirm a switch to another host (for a sign-in too), and **Unlink** after a confirmation. Signing in sends the tab to Meko Cloud, which sends it back to `/settings/meko-cloud/callback`: the page takes the code out of the address, finishes the sign-in (once) and says it's linked, or why Meko Cloud didn't sign the person in | The link is Meko's, for every extension ([cloud.md](cloud.md)). Signing in is the way a person links without making a key by hand ([cloud.md](cloud.md#signing-in)); the same tab rather than a pop-up, which a browser may block. Switching hosts leaves existing projects' datapacks on the old one, so it's confirmed. The server checks and refuses; the page shows its message. After a link or unlink, one line says which agents it moved (back to this Meko) and which it couldn't, with why (the reply's `agents`); nothing when it moved none, or from an older server. |
| **The Agents page (`/agents`), linked under Status, above Extensions, in the sidebar (lucide `Bot`)**: the agents installed on this computer (`GET /agents`), that they connect to Meko on this computer, which sends their calls to Meko Cloud while it's linked, and each one's state: Connected, Needs reconnecting (a meko server on this computer that isn't exactly the target), Connected elsewhere with its URL, or Not connected; with **Connect** for any not connected and **Disconnect** for a connected or stale one, then the list read again. Under the agent go its notes, the reply's, a reminder that running sessions need a restart, or Meko's error. With none installed it names the agents Meko works with. Under them, the URL any other MCP client connects to (the reply's `target.url`, with a copy button), with the token `meko token` prints; a server without the route (a 404) gets a note to run `meko agent connect <agent>` or update. A datapack has no Connect tab: its old address (`/datapacks/<id>/connect`) goes to `/agents` once, before the app reads its route, as the old sign-in addresses do | Agents connect to Meko itself, with its one client token, and pick a datapack on each call, so connecting them is the install's page, not a tab repeated under every datapack. Meko owns the agent connections ([api.md](api.md)), so one press does what `meko agent connect` does, without a terminal. The browser never gets the client token (`provision-status` gives a browser `""`), so the page shows no token or `claude mcp add` command, only where to get them; the URL comes from the same `GET /agents` reply, so the page needs no datapack. No dot or count on the sidebar link: listing the agents can take 3 s while Meko reads the login shell's PATH. Connect replaces a meko server that points elsewhere and the reply says so; Disconnect is offered only for Meko's own. Nothing polls: the list is read when the page opens and after each press. |
| **Each conversation turn has a decision trace**: what the agent looked up, its reasoning and plan, and what it saved, each call opening its step timings | The call log already records every call's conversation, result counts and steps, and the turn stores the reasoning and plan the agent sent, so no new data is collected. Lookups and actions are grouped by each tool's own read-only flag. The reasoning and plan are only as good as what the agent sends. The calls go back to the conversation's start (an earlier conversation under the same id doesn't leak in) and include calls that failed before their datapack was known; the call log keeps 90 days, so an older turn says its calls may be gone. |
| **Overview leads with the collective-learning ribbon** (conversations → memories → learnings → collective memory, each opening its tab); **Knowledge** ends with its activity log (uploads with their chunks, promotions); collective memories can be deleted | As Cloud's datapack page shows them, from routes Meko already serves (the datapack's counts, `activity-log`, `DELETE /promoted-memories/:id`). |
| **A new datapack's Overview starts with "Get started"** (connect an agent, which opens the Agents page, add a memory, upload a file, run a search), each ticked from the datapack's counts and gone for good once all are done; **`/` jumps to Search** from anywhere outside a field or a dialog (from Status, to the first datapack's), and Esc closes dialogs | Meko Cloud's datapack page shows the same first steps. The agent and search steps come from the call log, which forgets after 90 days, so the browser remembers a datapack that got started rather than showing the card again. |
| **The Memories tab's Graph view draws its scope's memories by meaning, and Search's Graph view shows where a question lands among everything it searched** (`/memory-map`, `/search-map`; List or Graph, remembered in the browser per page, on every Search source): the Memories map is one dot per memory, alike ones close and linked, colored by state (learning, kept or collective, with a legend); Search's is the 100 memories, knowledge-base chunks and conversation turns nearest the question, colored by source (the legend hides or shows each), with the question as a star and lines to what the search returned, listed beside with their scores. A dot hovered or focused shows its score above it. A click only picks a dot: the map can't be selected or take a focus outline, which browsers paint over it. **2D or 3D** (remembered in the browser): 3D adds the third main direction as depth, nearer dots larger and bolder, drawn far to near; it turns slowly until touched (not at all with reduced motion) and a drag turns it | Plain SVG, no chart library, 3D included: a few hundred dots rotate cheaply in JavaScript, where a WebGL library would add its weight and replace the click, hover and legend code. Depth is stretched to the map's spread, since the third direction varies less and would draw nearly flat; 2D stays the default, as 3D is harder to read when still. The projection runs on the server, which holds the vectors; all three sources share one embedding model, so one map places them. 100 nearest, not the whole datapack, keeps Search's map readable however large the datapack, and drawing a turn once (at its nearest chunk) keeps a long turn from being several dots. Search lights what its own results list, so List and Graph show the same matches; the question lives in one place, Search, rather than a second box on Memories. A turn's decision trace draws the same map small, lighting the memories its searches returned (the ids the call log records for each memory search). |
| **Overview's counts open their tabs** (memories, knowledge files, conversations, artifacts; searches and agents open Metrics), as real links; **a memory's "where it came from" opens its conversation at the turn it came from**, scrolled to, ringed with a brief pulse and labeled | A count invites a click, and a conversation can be long: the link carries the turn as the address's `#fragment`, so the page can point at it and the link still works pasted elsewhere. |
| **Search writes an answer above its results when answers are on** (`meko answers use claude`): the user's own Claude Code reads up to 10 of them, taken in turn from each source, and answers citing them as [n], each listed below with its source; off, a line links to Settings and names the command | An answer from what the search found, without a model to download: the same reasoning as memory extraction ([memory-extraction.md](memory-extraction.md#search-answers)). |
| **A Context Gaps tab lists the questions Meko couldn't answer** (`/datapacks/<id>/gaps`, after Search): the datapack's searches that found nothing, or found only memories each scoring below 0.75, grouped by question, latest asked first, 100 at a time (`GET /datapacks/:id/questions`), filtered Open, Taught, Dismissed or All (`/datapacks/<id>/gaps/taught`, `/dismissed` or `/all` opens on that filter, as Kode's tour links Taught). Each shows how often and by which agents it was asked, its conversations (each opening it), and its best scores; **Teach** saves what the user writes (up to 2,000 characters) as a memory in the datapack and marks it taught, **Dismiss** sets it aside and **Restore** opens it again. A mark an agent made names its conversation. Overview has a line while any are open (*9 questions Meko couldn't answer · 5 found nothing · 4 nothing relevant*), opening the tab, and none on a server without the route. A linked Meko Cloud's datapack has the same list on a page of its own, `/gaps/<id>` (named from Meko Cloud's listing, its conversations not links), which `/datapacks/<id>/gaps` goes to for such a datapack | Meko sees every agent's search when it answers it, so it records the poor ones itself, per datapack, by the rules in [api.md](api.md#context-gaps). Teaching right where the gap shows closes it: a later search that finds the answer takes the question off the list. |
| **Overview warns while memory extraction is off** (a reusable `Banner`, which the Invite notice uses too), linking to Settings, with `meko memory-extractor use claude` to copy; closing it lasts until the datapack has more conversations, and it's hidden for a datapack that opted out. **Status** has a Memory extraction card (the tool, the interval, what waits, the last run and error, or a link to Settings while off); an extracted memory is tagged **extracted** | Extraction runs through the user's own AI tool ([memory-extraction.md](memory-extraction.md)), turned on in Settings or the CLI. |
| **Each memory has an Origin**: who saved it and during which conversation turn (or directly, with `memory_add`), each update with its old and new text, and, where the page knows it (the Learnings and Collective scopes and the graph), whether it's a learning, kept or collective | Its conversation comes from the memory's `conversation_id`. An extracted memory names its turn (`message_id`), and the dialog says Meko extracted it from that turn; any other memory's turn is the first one stored at or after it, since an agent saves memories before the turn they belong to; with none (not stored yet, or past the 100 turns loaded), no turn is quoted. mem0 already records every change in `memory_history`; `GET /memories/:id/history` reads it, so an agent's edits (`memory_update`) can be seen and checked. The page fetches it as it fetches everything, with no credential (Meko takes its browsers by their access), then saves it. |
| **Uploads use Cloud's presigned flow** (`upload-url`, then the multipart POST), hashing the file in the browser | The same path Kode and Cloud's web app take, so nothing new is trusted. |

## Develop

```sh
cd src/meko
make web_ui                      # npm ci when the lockfile changes, then web_ui/dist
./bin/meko start && ./bin/meko ui
cd web_ui && npm run dev         # Vite on :5178, proxying the API to MEKO_URL (default http://127.0.0.1:7777)
```

With `npm run dev`, open `http://localhost:5178/`. The proxy sends Meko its own Host
and origin, so with local access the page needs no token.
