Design · v0.16 (implemented)

AgentK Local

A self-hosted workbench for Claude Code. It runs headless on your devserver, and you reach it from a browser on the corp network. Projects sit in a rail on the left. Every task gets its own git worktree and its own Claude session, and each task moves from design to a merged PR in one place. Each project records its work in Meko datapacks.

Architecture

There are three long-lived pieces on the host: the web server, the tmux server that owns every Claude process, and the state directory at ~/.agent-k-local. The server is stateless enough to be killed at any time. tmux and the on-disk state are what carry your work.

Terminal path

When you open a tab, the browser opens a WebSocket. The server spawns tmux -L agentk attach -t ak-… in a pty and pipes it through. Closing the tab kills only that pty, and Claude keeps running.

Status path

Each session starts with claude --settings pointing at an agent-k hooks file. The SessionStart, UserPromptSubmit, Notification and Stop hooks post to a unix socket, which drives the badges in the rail. Your global Claude settings stay untouched.

The app

The left rail holds projects, each with its repo's folder name in small type under the project name and the most urgent session state shown on it. The top tabs hold that project's sessions. The main pane is the live Claude terminal, and the footer shows where the session is working: branch, diff size, tokens, the project's Meko datapack (Meko:<datapack>) and stage.

New project

A new project starts from a repo you already have. The dialog lists every git repo directly under your repos folder (~/code by default), with the most recently touched first. A repo can back several projects: one that already has a project is marked with its name (In "infra", or In 2 projects) and can still be picked. Each project on a repo gets its own datapack, Meko agent id, settings, sessions and worktrees; project names must differ within a repo. Their session branches share the repo, so a branch name that another project already uses gets a number added (ak/fix-tests-2). Per-repo files such as .agent-k/stages/ overrides apply to every project on the repo.

What the list shows

For each repo: its folder name, the origin remote, the current branch, and when it was last touched. The server scans the folder when the dialog opens, so repos you clone by hand appear straight away.

What it leaves out

Folders that aren't git repos, and git worktrees (a .git file rather than a directory), are left out. Only the top level is scanned by default. The scan depth and the list of folders are both settings.

Clone from URL

Paste a git URL and the server clones it into ~/code/<name> using your existing git credentials, then selects it. "Other folder" takes any repo path on the host.

You type the project name; it isn't filled in from the repo. The dialog suggests a new dedicated datapack named adlc/proj/<repo>/<project> from the repo and the name you type. You can rename it, or switch to an existing datapack, before creating the project.

New session

You give it a name and, optionally, a first prompt and a base branch (the default is the project's default branch). The server fetches the base from origin and fast-forwards your local base branch to it when that's safe, then creates the worktree and branch from it, starts Claude inside it, and focuses the tab. If the local base can't be fast-forwarded (it has commits origin lacks, or local edits would be overwritten), the session starts from origin/<base> and the activity log says why.

Changes

Clicking the +N −N numbers in the footer opens a side panel with every file changed on the branch since it left the base: committed, uncommitted and untracked (ignored files are left out). Each file has a kind (A, M, D, R, U), its line counts, an uncommitted tag when it has uncommitted edits, and a collapsible diff. Single-file diffs are cut at 256 KB and the whole panel at 4 MB; past that only line counts are shown. A changed image (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO) is shown as Before and After side by side with its size, instead of "Binary file"; GET /api/sessions/:id/changes/image serves the base's version from git or the worktree's from disk, only for those types, only inside the repo (no .., no symlinks out), up to 20 MB, and with a sandboxing content policy so the bytes can never run as a page. The footer counts use the same comparison, so they always match. The file list is the header's Files menu, with a filter, so you can jump to any file from anywhere in a long diff; each file's header shows its position (4 / 12), and [ / ] step to the previous or next file.

Review comments

Click + beside a line of any diff (shift-click a second line for a range) to leave a comment, as on a PR. Comments are drafts in state.db until you click Send N comments, which pastes them into Claude as one prompt, grouped by file, with the lines each one is about. If Claude is mid-turn or waiting on a permission prompt, they queue and go out when it's back at its prompt in the Code or Review stage. Each comment keeps an excerpt of its lines, so it follows them when Claude moves code, and is shown as outdated (still sendable) when they're gone. Sent comments are kept and shown with Show sent.

Design panel

During Design the panel opens as soon as the design exists and again whenever it's revised, at about 60% of the work area. An Artifact design is shown in a sandboxed frame (scripts allowed, no same-origin access, and a content policy that blocks network requests and limits scripts, styles and fonts to what Artifacts use), so the page can't read the login cookie or call the API. Open on claude.ai links to the published Artifact. A markdown design is rendered as sanitized HTML.

Side panels

The design doc and the changes panel open on the right of the terminal, one at a time. Drag the panel's left edge (or focus it and use the arrow keys) to resize it; double-click the edge to switch between normal and widest. Each panel's width is remembered in the browser. The design doc also opens full page in a new tab (/p/<project>/s/<session>/design), where it can still be approved.

Starting

Claude Code can take a while to load its plugins, MCP servers and startup hooks. While a session starts, the terminal shows its steps (updating the base branch and creating the worktree, starting Claude Code, loading, sending your task) with the current one animated and timed, plus the stage the session opens in. The session's tab shows the current step in its tooltip.

Keyboard

⌘1–9 switches projects, ⌃Tab cycles sessions, and ⌘K opens a palette to jump to any session, create one, or search the project's datapacks. Keys pass through to the terminal whenever it has focus. To copy from the terminal, drag across the text: tmux selects it and sends it as OSC 52, which the page puts on the clipboard. Shift-drag (Option-drag on a Mac) selects in the browser instead, and then Ctrl+C (⌘C) copies rather than interrupting Claude. Clipboard access needs HTTPS or localhost.

Notifications

A browser notification fires when any session moves to needs you or finishes a turn while its tab is hidden. You can mute it per project.

On a phone

At 760 px wide or less the app switches to a phone layout. The rail becomes a drawer behind a top app bar (the Back gesture closes it, and it holds Search and commands in place of ⌘K). The session header and footer details move into a ⋯ sheet, and the stage bar fits on one line with its gate button. Dialogs open as bottom sheets. The app follows the visible viewport, so the on-screen keyboard shrinks it instead of covering the prompt. On touch screens the terminal gets a key bar (Esc, Tab, Shift+Tab, arrows, Ctrl+C, Enter) and a compose box whose text goes in as one bracketed paste, then Enter. Swiping scrolls tmux's history through mouse-wheel reports. Tapping the terminal only brings up the keyboard in typing mode (the keyboard key). Phones default to an 11 px terminal font (about 48 columns), adjustable in the ⋯ sheet and remembered per browser.

Projects, worktrees and sessions

A project is a git repository on the host, picked from your repos folder (~/code) or cloned into it at creation. The project only points at the repo. The one change it makes there: when a session starts, it fast-forwards the local base branch to origin. That's a merge --ff-only where the branch is checked out (git refuses if it would overwrite local edits), or a ref update where it isn't. It never rewrites, resets or discards anything in your main checkout. A session is one task. It has one worktree, one branch and one Claude conversation. Worktrees live outside the repo so they never show up in git status.

Why SQLite

You get transactions across projects, sessions and datapacks, an event history for the activity feed, and crash safety without hand-rolled atomic file writes. It's still one file you can back up or inspect with the sqlite3 CLI.

Settings

journal_mode=WAL, synchronous=FULL (so a host crash never loses a committed session record), foreign_keys=ON and busy_timeout=5000. There are so few writes that FULL sync costs nothing noticeable. Old session_events are pruned after 30 days.

Not on NFS

SQLite locking is unreliable on network filesystems. The installer checks the filesystem type of ~/.agent-k-local. If it's NFS, the installer puts state.db on local disk ($XDG_STATE_HOME, then /var/tmp/$USER) and records the path in config.toml.

config.toml keeps only what's needed before the database opens: the port, TLS paths, repo roots, the update channel and the database path. Everything the UI changes lives in state.db.

Task lifecycle

Every session is a task that moves through stages, from design to a merged PR with the branch cleaned up. This first pipeline covers six stages of the development lifecycle. The pipeline is defined as data, so later stages such as test, deploy and monitor can be added without reworking sessions.

There are three gates that only you can pass: approving the design, opening the PR, and merging. Everything between the gates runs on its own.

AgentK in the loop

AgentK doesn't re-review on push, so after fixes the header offers Request another round, which posts /agentk review. If AgentK declines a PR (for example, because it's too large), the refusal is shown with a Force review button. Forcing is always your call.

Repos AgentK doesn't watch

Each project has a reviewer setting: AgentK or People only. It's detected from recent PRs in the repo. With people only, the Review stage waits for CI and the required approvals.

Stage prompts

Each stage's instructions to Claude come from a template. The defaults live in state.db, and a repo can override one with .agent-k/stages/<stage>.md. This lets a team change how designs are written or PRs described without changing agent-k-local. Review comments from the Changes panel go out through the comments template ({{count}} and {{comments}}).

Branch names

The branch prefix is a project setting, ak/ by default, because some orgs enforce a branch-name prefix with rulesets.

Datapacks

One per project

Dedicated datapack

It's created with the project, named adlc/proj/<repo>/<project_name> by default, or you can pick an existing one. It is the only place session transcripts and extracted memories are written.

Zero or more

Shared datapacks

These are attached from your datapack_list: a team knowledge base, org conventions, another project's memory. They are read-only from this project's point of view, and one datapack can be attached to many projects.

Each session is launched with this environment:

MEKO_DATAPACK_ID=dp_7f3…                 # dedicated: capture + memory writes
MEKO_AGENT_ID=claude_code:billing-api     # one memory bucket per project, not per worktree dir
MEKO_DATAPACK_IDS=dp_7f3…,dp_a01…,dp_c9e… # everything this session may read
AK_SESSION=billing-api/fix-retry-backoff

A short --append-system-prompt also lists the attached datapacks by name and purpose, so Claude knows to pass the right datapack_id when it searches them.

No Meko plugin change needed

The Meko hooks already take MEKO_AGENT_ID over the folder name, and they read the datapack pin from ~/.claude/meko-capture/pin-<agent id>.json. AgentK Local sets MEKO_AGENT_ID=claude_code:<project> for every session and writes that pin when the project is created. So every worktree of a project shares one memory bucket, and capture goes into the dedicated datapack. MEKO_DATAPACK_ID is set too, for when the hooks learn to read it.

Folder trust

Claude Code asks "Do you trust this folder?" the first time it runs somewhere new, and fires no hooks until that's answered. For a worktree, Claude keys that decision by the main repository, so the server marks the project's repo as trusted in ~/.claude.json when the project is created, and checks again before each launch (other Claude processes can overwrite a fresh entry when they start, so it re-checks after a moment). If the prompt still appears, the session shows needs you with an explanation.

Meko is required

AgentK Local doesn't run without Meko. Datapacks are how a project keeps track of its work, so there is no mode without them.

  • At install: the installer needs a Meko API key. It reuses MEKO_API_KEY from ~/.claude/settings.json if one is there, and asks for one otherwise. It also checks that the meko-agent-skills plugin is installed at a version that honours the env vars above. The install stops if the key doesn't work or the plugin is missing.
  • At project creation: a dedicated datapack is mandatory. Create project stays disabled until one is chosen or created.
  • At session start: every session gets the Meko environment. The server refuses to start a session for a project whose dedicated datapack it can't resolve.
  • If Meko goes down: running sessions keep going, and the rail shows a "Meko unreachable" banner. The Meko hooks capture from the transcript on disk, so they catch up once the service is back. New projects can't be created until then.

Token usage

Claude Code writes every model response to the session transcript with its token counts. The server reads new lines from each session's transcript, and from any subagent transcripts under <session>/subagents/, after every turn (on the Stop hook), when a session ends or is archived, and once a minute. It remembers the byte offset it reached, so each line is read once.

One response spans several transcript lines with the same message id, so usage is stored once per message: usage_messages(session_id, message_id, agent, model, at, input, output, cache_read, cache_write). Totals per session, project, model and day are sums over that table, and archived sessions keep counting toward their project.

Plan limits. On Pro and Max plans, Claude Code passes the account's 5-hour and weekly usage (rate_limits.five_hour / seven_day: percent used and reset time) to its status line command. Sessions are launched with AgentK Local's own status line (run/statusline.sh, set in the --settings file). It sends inputs that carry limits to the server over the hook socket, in the background, and then runs the user's own status line command with the same input, so the terminal looks unchanged. That command is found at launch (local project settings, then project, then user settings) and passed as AK_USER_STATUSLINE; sessions launched before this existed use the user-level command saved in run/user-statusline; its padding and refreshInterval are copied. The newest report from any session wins, since they all share one account. It is kept in the kv table, and the rail shows each window with a bar, its reset time and how old the reading is, turning amber at 80% and red at 95%. A window disappears once its reset time passes. The numbers only move when a session gets a reply, so the rail says when they were last reported.

Where it shows

The session footer and tab tooltip show the session's total and output tokens. The rail tooltip shows the project total. The project home has a Token usage section: headline numbers, a 14-day chart with a table view, and breakdowns by session and by model.

What's counted

Four numbers, kept separate: uncached input, cache writes, cache reads and output. Cache reads dominate long sessions, so the headline total is shown next to output. Only tokens are tracked; dollar estimates aren't, since most people use a subscription.

In Meko

When a task is cleaned up, its token totals are included in the "shipped" summary written to the project's dedicated datapack.

Login and security

The terminal is a shell running as your Unix user, so the web login protects the same thing as your SSH key. Each install serves exactly one owner. Sharing the app means other people install their own copy.

First run

The installer prints a one-time setup link: https://host:7777/setup?token=…. You open it, choose a username and password, and can optionally enrol TOTP. The token stops working after it is used.

Sessions

Passwords are hashed with scrypt. After login you get an HttpOnly, Secure, SameSite=Strict cookie that lasts 14 days, renewed as you use the app. Every WebSocket upgrade checks both the cookie and the Origin header.

TLS is mandatory

Any address other than localhost requires HTTPS. You can point it at your own certificate from the corp CA, or let it generate a self-signed pair and show the fingerprint so you can trust it once on your laptop.

Guard rails

Failed logins are rate-limited, with a lockout after repeated failures. There is an audit log of logins and new sessions. Hooks use the local unix socket with a per-session token, never the network port. The Design-stage edit guard asks the server over the same socket; if it gets no answer it lets the edit go ahead, so Claude is never stuck.

Later: passkeys (WebAuthn), and single sign-on with Google Workspace or another OIDC provider.

Surviving crashes, restarts and updates

Two systemd user units run with lingering enabled, so they start at boot without anyone logging in:

  • agent-k-local-tmux.service owns the tmux server on socket agentk. It is never restarted by updates.
  • agent-k-local.service is the web server, with Restart=always. Updates restart only this unit.

Keeping tmux in its own unit is the key point. If tmux were a child of the server's unit, systemd would kill every Claude session on each update.

A turn that was in progress when the host died is lost, but the conversation up to that point comes back. Auto-continue is on by default, with guards:

Only sessions that were working

The session's status is written to state.db on every hook event, with full sync. A session whose last status was working is resumed with a continue prompt. Sessions that were idle or waiting on you come back exactly as they were.

Check before continuing

The prompt says the host restarted mid-turn. It asks Claude to check the worktree and the last commands (and, in the Review stage, the PR threads) before continuing, so finished steps aren't repeated and replies aren't posted twice.

No crash loops

A session is auto-continued at most once every 15 minutes. After two recoveries in an hour, it's parked as needs you instead. Each project can turn auto-continue off.

Releases and auto-update

On every PR

CI

Typecheck, lint and unit tests. Integration tests run against real tmux and git, with a stub claude binary that fakes the TUI and fires the hooks.

On push to main

Versioning

Versions are 0.YYYYMMDD.N: the UTC date, and N counting from 0 for each release that day. A push with any feat, fix or perf commit since the last release runs the tests and cuts the next version; its Conventional Commit subjects become the release notes.

After the tests

Build matrix

Self-contained tarballs are built for linux-x64 and linux-arm64. Each bundles the Node 22 runtime, node-pty (built with gcc-toolset-13) and the web assets. Each release also includes SHA256SUMS, a build provenance attestation and install.sh. Afterwards, releases beyond the newest 5 in each lane (stable, or the prerelease identifier such as beta) are deleted; their tags stay.

glibc

RHEL 8 devservers ship glibc 2.28, and node-pty is a native module. Linux builds run in an AlmaLinux 8 container rather than on ubuntu-latest, so the binary loads on older hosts.

# what it does
#  1. checks for tmux ≥ 2.7, git, claude, and the meko-agent-skills plugin
#     verifies the Meko API key (reuses MEKO_API_KEY from ~/.claude/settings.json, or asks)
#  2. unpacks to ~/.agent-k-local/app/<ver>, points app/current at it
#  3. installs both systemd user units and enables linger if allowed
#  4. asks for your repos folder (default ~/code) and writes config.toml
#  5. prints the one-time setup link

Update loop. The server checks the GitHub Releases API at startup and every 6 hours. The channel can be stable, prerelease or off. When a newer version appears, the server:

  1. downloads the tarball and verifies it against SHA256SUMS, and against the attestation if gh is available;
  2. unpacks it next to the current version and runs its self-test;
  3. snapshots the database with VACUUM INTO state.db.bak-<old-ver>, lets the new version run its migrations on start, and points app/current at the new version;
  4. restarts only the web server unit. Sessions keep running;
  5. if /healthz fails within 30 seconds, points back to the previous version and marks the new one as bad.

Once a version has been healthy for 30 seconds, the server deletes installed versions under app/ beyond the newest 5 in each lane, never the running one.

The rail shows "Updated to v0.4.1" with a link to the changelog. Updates never need a maintenance window, because they never touch tmux.
